# 에디터

::: fw flutter

**이 패키지의 화면은 셋이고**, React 패키지에 있는 `wysiwyg`가 빠져 있습니다. `wysiwyg`는 문서를 그리고 그려진 자리에서 편집하는 화면으로, `contenteditable`에 전적으로 의존합니다. 브라우저가 트리 변경 시도를 컴포넌트에 알리면, 컴포넌트가 그것을 거절하고 대신 마크다운을 고치는 구조입니다. `EditableText`가 문자열을 소유하는 Flutter에는 이런 구조가 없습니다. 텍스트 필드이면서 동시에 문서인 화면을 그리려면 문서 구조를 따로 들고 있는 두 번째 모델이 필요한데, 모델이 둘이면 조금이라도 특이한 문서에서 서로 다른 해석을 내놓습니다.

그래서 화면은 `plain`, `split`, `preview` 셋이고, 그려지는 화면은 뷰어로 남습니다. 이 페이지의 나머지 내용은 거의 전부 여기에도 해당합니다. 명령과 원문에 입히는 색, 아래쪽의 숫자, 글자 찾기가 모두 같은 이름의 같은 함수이고, 코드가 바뀔 때마다 parity 검사가 그 넷을 React 패키지의 것과 대조합니다. 예외는 열기와 저장이며, 그 절에 이유를 적어 두었습니다.

```dart
MawyEditor(
  defaultValue: '# Hello',
  onChange: save,
);
```

:::

Mawy의 에디터는 화면이 여럿인 컴포넌트 하나입니다. `plain`은 마크다운 원문을 텍스트로 편집하고, `preview`는 그려진 문서를 보여주며, `split`은 둘을 한 번에 보여줍니다. 세 화면 모두 같은 값을 보여주고, 이것이 이 설계의 출발점입니다.

<MawyDemo name="editor/basic" flutter="editor/basic" :height="520" />

```tsx
import { MawyEditor } from 'mawy-react';

export function Page() {
  return <MawyEditor defaultValue="# 안녕하세요" onChange={save} />;
}
```

## 여러 화면, 한 값

흔한 구성은 위지윅 에디터에 "소스 모드"를 덧붙이는 것입니다. 이때는 화면을 전환할 때마다 한쪽 모델에서 직렬화하고 다른 쪽 모델로 파싱합니다. 그 왕복에서 반대쪽이 표현하지 못하는 각주와 HTML 블록, 목록 기호의 정확한 표기가 사라지는데, 사라졌다는 사실은 어디에도 표시되지 않습니다.

여기서 문서는 마크다운 문자열 하나이고, 모든 화면은 그것을 보는 방법입니다. 전환은 어느 화면이 마운트되는지를 바꿀 뿐 아무것도 다시 직렬화하지 않으므로, 그대로 들어온 문서는 그대로 나갑니다.

## 모드

| 모드        | 편집 가능 | 보여주는 것               |
| ----------- | --------- | ------------------------- |
| `'plain'`   | 예        | 마크다운 원문             |
| `'preview'` | 아니오    | 그려진 문서               |
| `'split'`   | 예        | 둘을 나란히               |
| `'wysiwyg'` | 일부      | 그려진 문서를 그 자리에서 |

툴바가 어느 것을 제시할지는 `modes`가 정하고, 하나만 주면 전환 컨트롤 자체가 사라집니다.

```tsx
<MawyEditor defaultValue={document} modes={['plain']} />
```

<MawyDemo name="editor/source" />

`mode` / `defaultMode` / `onModeChange`는 익숙한 그 셋입니다. `mode`를 넘기면 애플리케이션이 정하고, `defaultMode`를 넘기면 에디터가 갖고 있으며, `onModeChange`는 어느 쪽이든 호출됩니다.

`split`에서 미리보기는 파일의 위치 비율이 아니라 **블록**을 기준으로 스크롤합니다. 원문 맨 위에 있는 줄이 미리보기 맨 위에 올 블록을 정하고, 그 사이는 블록에서 블록으로 곧게 이어집니다. 비율로는 맞출 수 없습니다. 코드 블록은 원문 예순 줄이 화면에서도 예순 줄이지만 양옆의 산문은 그렇지 않아서, 비율로 맞추면 곧바로 어긋납니다.

**두 판 사이의 바는 잡고 끌 수 있습니다.** 5:5 비율이 언제나 알맞지는 않습니다. 넓은 창에서 초고를 읽을 때는 미리보기가, 글을 쓸 때는 원문이 더 넓은 편이 낫습니다. 끌어도 되고, 포커스를 준 뒤 화살표를 써도 됩니다. `Shift`는 더 큰 걸음, `Home`과 `End`는 양 끝, `Enter`나 더블 클릭은 다시 5:5입니다. 양쪽 가장자리에는 한참 못 미쳐 멈추는데, 폭이 0까지 밀린 판은 다시 끌어낼 수 없기 때문입니다.

바의 위치는 읽는 사람이 화면을 보는 동안만 유지되고, 여기에 해당하는 프롭은 없습니다. 판의 경계는 스크롤 위치와 같은 종류의 값이라 저장 대상으로 두지 않았습니다. 저장할 만한 값은 문서이고, 그것은 `value`와 `onChange`가 다룹니다.

두 판이 위아래로 쌓이는 너비에서는 바를 그리지 않습니다.

**미리보기는 읽기 전용이라 거기서는 아무것도 편집하지 않습니다.** 미리보기를 클릭해도 원문의 커서는 움직이지 않습니다. 이것이 이 판과 `wysiwyg`의 차이입니다. 그려진 문서를 편집하는 화면은 `wysiwyg` 하나입니다. 왼쪽에서 글을 쓰는 동안 오른쪽 클릭이 커서를 옮기면 어느 쪽에서 쓰고 있는지가 모호해집니다. 링크와 체크박스, 코드 블록의 복사 버튼은 그대로 동작하고, 나머지는 일반 페이지처럼 선택하고 복사할 수 있습니다. 뷰어는 읽기 좋은 폭을 지키지만 미리보기는 판의 너비를 다 씁니다. 읽는 페이지가 아니라 지금 쓰는 문서이기 때문입니다.

## 원문 편집 화면

::: fw react

진짜 `<textarea>`이고, 같은 글자를 색칠한 사본이 그 바로 아래 정확히 겹쳐 있습니다.

이 구성은 의도한 설계입니다. textarea는 직접 다시 만들기 어렵고 없으면 곧바로 티가 나는 기능을 이미 갖고 있습니다. **IME**(한글은 자모 단위로 조합되고, 조합을 가로채는 에디터는 글자를 잃습니다), 모바일 키보드, 자동 수정, 맞춤법 검사, 플랫폼의 모든 텍스트 선택 제스처가 그렇습니다. textarea가 못 하는 일은 색을 입히는 것뿐이므로, 글자를 투명하게 만들고 커서와 선택 영역만 남긴 뒤 뒤쪽 레이어가 같은 글자를 색으로 그립니다.

글자가 놓일 자리를 결정하는 값은 스타일시트에 한 번만, 두 레이어 모두에 선언됩니다. 글꼴과 크기, 줄 간격, 자간, 탭 크기, 줄바꿈, 그리고 왼쪽 시작점을 정하는 패딩이 그렇습니다. 이 선언이 두 레이어를 어긋나지 않게 맞춥니다. 에디터의 고정폭 서체를 컴포넌트가 정하지 않고 `--mawy-font-mono`에서 읽는 것도 같은 이유입니다.

육백 줄을 넘어가는 문서는 한 줄에 한 행씩 그리지 않습니다. 아래쪽 사본을 덩어리로 나누고, 화면 근처의 덩어리만 문법을 색칠한 행으로 그립니다. 나머지는 같은 글자를 한 덩이의 텍스트로 담는데, 높이는 똑같고 요소 수는 훨씬 적습니다. 빠지는 글자가 없으므로 브라우저의 찾기는 여전히 문서 전체에 닿고, 인쇄하면 전부 종이에 올라가며, 사본의 높이도 필드와 정확히 같습니다. 색칠이 따라오지 못할 만큼 빠르게 스크롤하면 한 프레임 동안 색 없는 글자가 제자리에 보이고, 빈자리가 남지는 않습니다.

:::

::: fw flutter

`EditableText` 하나이고, 그 자리에서 색이 입혀집니다.

이 라이브러리에서 Flutter 쪽이 더 쉬운 유일한 자리입니다. 브라우저는 텍스트 필드 *안*을 색칠할 방법을 주지 않아서, React 패키지는 두 레이어를 그린 뒤 서로 어긋나지 않게 맞춰야 합니다. `TextEditingController`는 그릴 스팬을 그대로 받으므로 `MawySourceController`가 그것만 넘기면 됩니다. 레이어가 하나여서 맞출 그리드도 없고, 필드가 플랫폼의 것이므로 커서와 선택 영역도 플랫폼 동작 그대로입니다.

그 필드에 딸려 오지 않는 것이 포인터 처리입니다. 맨 `EditableText`는 탭한 자리에 캐럿을 놓고 거기서 멈춥니다. 드래그해도 선택되지 않고, 더블 탭은 단어를 잡지 않으며, 길게 눌러도 핸들이 뜨지 않습니다. 그 전부를 `TextSelectionGestureDetectorBuilder`가 처리하고, `TextField`가 자기 필드에 두르는 것을 이 위젯도 자기 필드에 두릅니다. 이 빌더는 Material이 아니라 `package:flutter/widgets.dart`에 있으므로, 이것을 써도 Material을 함께 들이지 않습니다.

두 가지는 이 패키지가 아니라 플랫폼이 제공하고, 둘 다 Flutter가 아닌 Cupertino에 있습니다. iOS에서 세게 눌렀을 때 뜨는 돋보기와 선택 툴바입니다. 시작만 하고 끝맺지 못하는 제스처를 남기지 않으려고 force press는 꺼 두었습니다.

여기서도 `lineNumbers`로 거터를 끕니다. 기본은 켜짐이고, 번호는 같은 텍스트를 한 번 더 배치하지 않고 필드가 이미 배치해 둔 줄에서 그립니다. 그래서 줄바꿈된 줄은 화면에서 두 행이고 옆에서는 번호 하나입니다. 배치가 하나뿐이라 둘이 어긋나지 않습니다.

육백 줄을 넘어가는 문서는 보이는 곳만 색칠하고, 나머지는 쓰인 글자 그대로 넘깁니다. 필드는 어느 쪽이든 문서 전체를 배치합니다. 레이어가 하나뿐인 구조에서는 피할 수 없는 비용이면서, 커서와 선택 영역과 모든 측정값이 그대로 유지되는 이유이기도 합니다. 여기서 아끼는 비용은 키 입력마다 모든 줄을 읽는 일입니다. 색칠할 구간은 프레임이 끝난 뒤에 정해지므로, 그보다 빠르게 스크롤하면 다음 프레임까지 색 없는 글자가 제자리에 보입니다.

:::

문법 강조는 Mawy 파서의 토큰 이름을 쓰지만 파서 자체를 쓰지는 않습니다. 타이핑 중인 줄은 대부분 절반만 쓰인 상태여서, `**bold`가 닫히기를 기다렸다가 반영하는 하이라이터는 키 입력마다 깜빡입니다. 그래서 한 줄씩 근사적으로 읽고, 아직 닫히지 않은 마커는 그대로 둡니다.

::: fw react

`lineNumbers`로 거터를 끕니다. 기본은 켜짐이고, 두 레이어가 하나의 그리드를 공유하므로 줄바꿈된 텍스트에서도 번호가 어긋나지 않습니다.

:::

## 문서 편집 화면

`wysiwyg`는 문서를 그리고, 그려진 그 자리에서 편집합니다. 동작을 짐작하기 쉬운 화면이라 아래에 하나씩 적어 둡니다.

<MawyDemo name="editor/document" />

뒤에 두 번째 모델은 없습니다. 화면에 보이는 것은 마크다운을 그린 결과이고, 기준이 되는 값은 마크다운 문자열입니다. 모든 키 입력을 거절해 그 문자열을 고치는 편집으로 바꾸고, 바뀐 문자열에서 문서를 다시 그립니다. 브라우저가 바꾸려던 트리를 되읽지 않습니다. 이 패키지에 DOM → 마크다운 직렬화기는 없고 앞으로도 두지 않습니다. 구현이 둘이면 조금이라도 특이한 문서에서 서로 다른 해석을 내놓기 때문입니다.

**전환 스위치가 처음으로 내놓는 화면입니다.** 링크와 이미지의 주소는 옆에 뜨는 막대에서 편집하고, 그려지는 원시 HTML은 캐럿이 들어가면 쓰인 글자 그대로 펼쳐지므로, 이 화면에는 바꿀 수 없는 것이 없습니다. 이 두 가지가 해결되기 전까지는 기본 목록에 넣지 않았습니다. 이 화면을 제공하지 않으려면 `modes`에서 빼면 됩니다.

```tsx
<MawyEditor defaultValue={document} modes={['plain', 'split', 'preview']} />
```

**코드 블록과 알림 블록에는 전용 막대가 있습니다.** 커서가 펜스 코드 블록 안에 있으면 블록 위쪽 가장자리의 먼 끝에 작은 막대가 뜹니다. 블록의 언어를 고르는 메뉴(언어가 없는 `일반 텍스트` 포함)와 빨간색 블록 삭제 버튼이 있습니다. 언어를 고르면 여는 펜스에 쓰고, 포커스는 커서가 있던 문서 자리로 돌아갑니다. 커서가 알림 블록 안에 있으면 막대에 다섯 종류가 있고 지금 종류가 눌린 상태로 보이며, 알림 블록 삭제 버튼이 있습니다. 종류 버튼을 누르면 `[!NOTE]`가 그 종류로 바뀝니다. 커서가 표 안에 있으면 쓰는 행에 더 가까운 표 막대가 대신 뜹니다. 원문 화면은 이 모두를 글자로 보여 주므로 이런 막대가 없습니다. 알림 블록 위에 그리는 `참고`나 `주의` 같은 이름은 문서에 쓴 글자가 아니라 이 라이브러리가 종류를 부르는 말이므로, 커서를 둘 수 없고 입력한 글자도 들어가지 않습니다. 종류는 막대에서 바꿉니다.

**디렉티브의 라벨은 그려진 자리에서 고칩니다.** `:::callout[제목]{kind=note}`의 `제목`은 애플리케이션이 등록한 컴포넌트를 거쳐 화면에 오는데, 다른 글줄처럼 그 자리에서 입력하고 지울 수 있습니다. 라벨은 한 줄이라 `Enter`를 눌러도 아무 일이 없고, 붙여 넣은 글은 그 줄에 이어 붙습니다. 입력하거나 붙여 넣은 대괄호는 앞에 백슬래시를 붙여 씁니다. 그냥 쓴 `[`나 `]`는 라벨을 끝내 버려서 그 줄이 더는 디렉티브가 아니게 되기 때문입니다. 라벨 아래 줄의 맨 앞에서 누른 `Backspace`는 디렉티브의 첫 줄을 건드리지 않습니다. `[]`로 쓴 라벨은 입력할 빈자리로 그리고, 대괄호 없이 쓴 디렉티브에는 이 화면에서 입력할 라벨이 없습니다.

**체크박스를 누르면 할 일이 체크되거나 풀립니다.** 그려진 문서에서 상자를 누르면 원문에 `[x]`나 `[ ]`를 씁니다. 체크박스 목록에서도, 표 셀에서 할 일로 쓴 줄에서도 같고, 커서는 그 자리에 그대로 둡니다. 미리보기와 뷰어는 읽는 문서라 상자를 누를 수 없고, `readOnly`인 그려진 문서도 마찬가지입니다.

**문서는 판의 너비를 다 쓰고, 미리보기도 마찬가지입니다.** 뷰어는 읽기 좋은 폭을 지키지만, 글을 쓰는 곳의 가장자리는 에디터의 가장자리여야 하고 미리보기는 바로 그 문서이기 때문입니다. `--mawy-doc-edit-measure`로 둘 다 따로 폭을 줄 수 있고, 그 폭 바깥 여백을 눌러도 커서는 옆줄에 놓입니다. 포커스를 가진 동안 문서 둘레에 테두리를 그리지 않는 것은 원문 화면과 같은 규칙입니다. 포커스가 어디 있는지는 커서가 이미 보여 줍니다.

되는 일은 이렇습니다. 문단과 제목, 목록 항목, 인용, 표의 셀, 코드 블록처럼 **글자가 들어갈 수 있는 곳이면 어디서나** 타이핑과 삭제가 됩니다. 선택 영역 대체와 `Shift`+`Enter` 하드 브레이크, 타이핑하는 자리에서 곧바로 서식이 되는 약칭, 툴바의 모든 명령도 됩니다. 툴바 명령에는 새로 필요한 코드가 없었습니다. 명령이 원문과 선택만 받는 순수 함수라서 화면에 따라 달라지는 코드가 없습니다.

편집은 파일에 쓰인 글자가 아니라 **화면에 그려진** 글자를 기준으로 동작하고, 이것이 이 화면의 핵심입니다. `**bold**`에서 `bold` 뒤에 놓인 커서 앞에는 파일에서는 별표가, 화면에서는 `d`가 있습니다. 거기서 `Backspace`는 `d`를 지웁니다. 이미지와 하드 브레이크는 통째로 지워집니다. 읽는 사람에게는 각각 한 글자이고, 텍스트만 훑을 때는 보이지 않는 요소입니다. 선택 영역을 지울 때는 글자를 통째로 지운 서식의 기호도 함께 지우므로, 굵은 단어를 다 지워도 `****`가 남지 않습니다. 문서 전체를 선택하고 지우면 브라우저가 선택을 어디까지 늘였든 첫 단어 앞의 `#`까지 포함해 문서 전체가 지워집니다.

**선택이 링크나 코드 조각을 반만 덮고 있으면 서식은 그 전체를 감쌉니다.** 링크는 화면에 글자만 그려지고 파일에는 `[글자](주소)`로 쓰입니다. 그래서 링크의 글자에서 그 뒤의 글자까지 선택하면 파일에서는 대괄호 사이에서 선택이 시작됩니다. 여기에 굵게를 걸면 `one [**link](https://example.org) two**`가 되어 링크도 아니고 굵은 글자도 아니었습니다. 코드 조각, 굵은 글자, 그림처럼 자기 기호를 가진 인라인은 모두 화면보다 파일에서 길기 때문에 똑같이 잘렸습니다. 이제 선택의 한쪽 끝이 인라인의 기호 사이에 있고 다른 쪽 끝이 그 인라인 바깥에 있으면 그 끝을 인라인의 경계로 옮깁니다. 양쪽 끝이 같은 인라인 안에 있으면 그대로 둡니다. 링크의 글자만 선택하고 굵게를 걸면 `[**link**](url)`이 되는데, 그것이 요청한 그대로이기 때문입니다. 원문 화면에서는 기호가 눈에 보이는 글자이고 일부러 가로질러 선택할 수 있으므로 아무것도 옮기지 않습니다.

화면이 그릴 수 없는 자리의 커서도 같은 문제입니다. 마크다운은 줄 끝의 공백을 남기지 않으므로, 문단 끝에 입력한 공백은 파일에는 있고 화면에는 그려지지 않습니다. 커서는 그 앞으로 돌아올 수밖에 없습니다. 그래서 커서가 **있으려던** 자리를 실제로 놓인 자리와 함께 기억해 둡니다. 다음 글자가 공백 뒤로 가게 하기 위해서이고, 이것이 없으면 `One two`를 한 단어씩 칠 수조차 없습니다. 이때 `Backspace`는 커서 앞에 지울 그려진 글자가 없으므로 그 공백을 지웁니다.

`Enter`는 어느 컨테이너에서 눌렸는지에 따라 다르게 동작합니다. 컨테이너마다 빈 줄의 뜻이 다르기 때문입니다.

| 어디서       | `Enter`가 하는 일                                                              |
| ------------ | ------------------------------------------------------------------------------ |
| 블록 사이    | 빈 줄                                                                          |
| 목록 항목 안 | 기호를 이어받은 새 항목. 비어 있으면 한 단계 밖으로, 맨 바깥에서는 기호를 없앰 |
| 인용 안      | 문단을 끝냄. 인용을 이어가려면 *빈 인용 줄*이 필요합니다                       |
| 코드 블록 안 | 줄바꿈 하나, 그게 전부                                                         |
| 표 안        | 셀 안의 줄바꿈. `<br>`로 씁니다                                                |

블록 맨 앞에서 누른 `Backspace`는 그 블록을 앞 블록과 합칩니다. 목록 항목 둘이 이어지고, 문단이 위의 제목과 합쳐집니다. 합치지 않는 경우가 둘 있습니다. 표의 셀을 옆 셀과 합치면 사이의 파이프가, 코드 블록을 위의 블록과 합치면 펜스가 사라집니다.

**빈 문단은 빈 줄 두 개입니다.** 마크다운에 빈 문단은 없지만 빈 줄은 있고, 이 화면은 그 빈 줄을 그립니다. 두 블록 사이에 꼭 필요한 빈 줄 하나는 화면에 아무것도 그리지 않습니다. 그 뒤로 빈 줄이 두 개 늘 때마다 빈 문단이 하나 생기는데, 문단 끝에서 `Enter`를 누르면 쓰이는 모양이 바로 이것입니다. 입력할 줄 하나와 그 아래 빈 줄 하나입니다. 그래서 `Enter`를 세 번 누르면 빈 문단이 세 개 그려지고, 원문에도 그 문단을 만드는 줄바꿈 여섯 개가 들어가며, 커서가 다른 곳으로 가도 문단은 그대로 남습니다. 문서의 맨 앞과 맨 끝에서는 가를 상대가 한쪽에 없으므로 첫 빈 줄부터 셉니다. 섹션 사이에 손으로 빈 줄을 하나 더 넣어 둔 것은 문단으로 치지 않으므로, 다른 곳에서 쓴 문서도 원래 모습대로 그려집니다.

빈 문단에서 `Backspace`를 누르면 그 문단 하나만 지워집니다. 위에 빈 문단이 있는 블록의 맨 앞에서 누르면 위의 빈 문단이 지워집니다. `Delete`는 같은 일을 반대쪽에서 합니다. 목록 항목을 그만두면 커서는 목록 바로 아랫줄이 아니라 이런 빈 문단에 놓입니다. 아랫줄에 쓴 글자는 항목의 게으른 연속(lazy continuation)으로 읽혀 목록 안으로 들어가기 때문입니다. 그 빈 문단에 목록 기호를 입력하면 목록이 이어집니다. 빈 줄이 사라지고 그 줄이 목록의 다음 항목이 됩니다. 그대로 두면 CommonMark가 그 줄을 목록에 붙이면서 느슨한 목록으로 읽어, 항목마다 문단이 되고 항목 사이가 벌어집니다. 기호 바로 뒤에 `-1`처럼 글자를 이어 쓰면 빈 줄을 되돌려 놓아 그 줄은 다시 문단이 됩니다. 미리보기와 뷰어는 같은 원문을 다른 마크다운 렌더러와 똑같이 그립니다. 빈 줄은 블록을 가르는 구분일 뿐입니다.

**목록 가운데에서 빠져나오는 일은 무언가를 칠 때까지 아무 값도 치르지 않습니다.** 항목 사이의 빈 항목에서 `Enter`를 누르면 기호가 사라지고 빈 줄이 남는데, 빈 줄 하나는 목록을 끝내지 않습니다. `- one`, 빈 줄, `- two`는 CommonMark에게 느슨한 목록 하나이고, 항목마다 문단이 되어 서로 멀어집니다. 커서가 그 줄에 있는 동안에는 첫 글자를 치면 만들어질 모양, 곧 목록 둘과 그 사이의 빈 문단으로 그려서 칠 자리를 줍니다. 거기에 글자를 치면 그 줄은 문단을 목록에서 떼어 놓는 빈 줄로 남습니다. 아무것도 치지 않고 커서를 옮기면 그 줄도 함께 사라지므로, 목록은 아무도 청하지 않은 느슨한 목록이 아니라 원래의 그 목록입니다. 기다릴 것 없이 그 문단에서 `Backspace`를 누르면 목록이 도로 붙고, `Delete`도 반대쪽에서 같은 일을 하며, 되돌리기도 같습니다.

**코드 블록은 아래로 내려가야 빠져나옵니다.** 코드 블록 안의 모든 것은 쓰인 글자 그대로이므로 `Enter`는 몇 번을 눌러도 줄바꿈입니다. 연달아 두 번 누르면 코드 안에 빈 줄이 둘 생길 뿐 빠져나오지 않습니다. 마지막 줄에서 `ArrowDown`을 누르는 것이 나가는 길입니다. 블록 맨 앞에서 `Backspace`를 누르면 펜스가 사라지고 안에 있던 내용이 문단으로 남습니다. 문서 끝에 있는 코드 블록이나 구분선, 요소로 그려진 HTML 뒤에는 커서가 갈 줄이 없으므로, 그 아래를 누르면 그 자리에 문단이 생깁니다. 문서 끝에 있는 코드 블록의 마지막 줄이나 표의 마지막 행에서 `ArrowDown`을 눌러도 같고, 문서 맨 앞에 있는 블록 위로 `ArrowUp`을 누르면 위에 문단이 생깁니다. 빈 코드 블록도 한 줄 높이로 그려서 안의 커서가 보입니다.

**그런 블록이 둘 붙어 있으면 그 사이를 눌렀을 때 문단이 생깁니다.** 구분선 두 개가 이어지면 둘 사이에는 각자의 여백이 남긴 공간뿐이어서, 그 자리를 눌러도 커서가 문서 자체에 얹혔습니다. 글자를 칠 수도, 양옆 구분선을 지울 수도 없었습니다. 이제 그 자리를 누르면 문단이 생깁니다. 커서가 그 안에 있는 동안만 그려지고, 무언가를 쳐야 문서에 쓰입니다. 그 문단에서 `Backspace`를 누르면 위쪽 구분선이, `Delete`를 누르면 아래쪽 구분선이 사라집니다. 구분선은 두 키가 가져갈 글자를 하나도 그리지 않아서, 그 자리에서는 구분선을 없앨 방법이 달리 없었기 때문입니다.

**아무것도 선택하지 않고 굵게, 기울임, 취소선, 코드를 누르면 다음에 입력할 글자에 서식을 걸어 둡니다.** 원문 에디터라면 커서를 가운데 둔 채 기호를 써 넣겠지만, 이 화면에서는 맞지 않는 답입니다. 한 줄에 `****`만 있으면 구분선이고, `~~~~`는 코드 펜스이며, 그 밖의 자리에서도 무언가를 입력할 때까지 네 글자가 그대로 그려집니다. 그래서 버튼을 누를 때는 아무것도 쓰지 않습니다. 버튼만 눌린 모습이 되고, 처음 입력하거나 조합한 글자를 기호로 감싸 쓰면서 커서를 기호 안쪽에 두므로 이어서 쓰는 글자에도 서식이 이어집니다. 커서가 이미 굵은 글자 안에 있을 때 같은 버튼을 누르면 거기서 쓰는 글자의 굵기를 풉니다. 굵은 구간의 끝이면 구간 뒤에 쓰고, 가운데면 새 글자 앞에서 구간을 닫았다가 뒤에서 다시 엽니다. 커서를 옮기면 걸어 둔 서식은 풀립니다. 단어 안에서는 `_`가 기울임으로 읽히지 않으므로 기울임을 `*`로 씁니다. 이 네 버튼은 기호를 선택했을 때뿐 아니라 커서가 해당 서식 안에 있기만 해도 눌린 모습으로 표시됩니다.

**코드 스팬이나 서식의 끝에서 `ArrowRight`를 누르면 커서가 닫는 기호 뒤로 넘어갑니다.** `` `code` ``의 끝은 화면에서는 한 자리지만 문서에서는 백틱 앞과 뒤 두 자리이고, 그 자리에 놓인 커서는 늘 앞쪽이었습니다. 그래서 문단 끝에 있는 코드 스팬에서는 밖으로 나와 글을 쓸 수 없었습니다. 화면의 커서는 움직이지 않고 다음 글자가 기호 뒤에 들어가며, `ArrowRight`를 한 번 더 누르면 평소처럼 움직입니다. 시작 자리에서 `ArrowLeft`도 방향만 반대로 같습니다.

조합 입력(IME)만은 **거절할 수 없어서** 반대로 다룹니다. 조합은 통째로 브라우저에 맡깁니다. `compositionstart`부터 `compositionend`까지는 아무것도 막지 않고 다시 그리지도 않습니다. 조합이 끝나면 그 텍스트를 직전 내용과 비교해서, 해당 위치의 마크다운에 차이만 반영합니다.

조합을 거절하면 조합 자체가 되지 않습니다. 한글은 자모 하나씩 조합되므로, 그 하나하나를 막는 에디터에서는 한국어를 쓸 수 없습니다. `Enter`를 누르고 빈 문단에 바로 조합해 넣는 것도 됩니다. 들어갈 텍스트가 아직 없을 때는 블록 자체를 기억해 둡니다.

**링크와 이미지는 옆에 뜨는 막대에서 편집합니다.** 그려진 `<a>`는 링크 텍스트만 화면에 올리고 `(url)`은 올리지 않으며, 이미지는 그림 말고는 아무것도 올리지 않으므로, 이것들을 쓴 글자는 화면에서 입력할 자리가 없습니다. 캐럿이 링크 안에 있으면 그 줄 아래에 막대가 뜹니다. 주소와 링크 텍스트를 한 줄에 하나씩, 앞에 이름표를 붙여 담은 입력란 두 개, 링크를 여는 버튼, 텍스트는 두고 링크만 해제하는 버튼, 그리고 링크와 텍스트를 함께 지우는 빨간색 버튼이 있습니다. 이미지를 누르면 이미지가 선택되고(선택 색을 덮어 그리지는 않습니다), 막대에는 주소와 설명 입력란, 빨간색 삭제 버튼이 있습니다. 입력란에 쓴 내용은 `Enter`를 누르거나 입력란을 벗어날 때 쓰이고, `Escape`는 입력란을 되돌립니다. 텍스트를 바꾸지 않았으면 원래 서식이 남습니다. 캐럿이 안에 있어도 링크는 링크로, 이미지는 이미지로 그립니다. 전에는 쓰인 글자로 펼쳐졌고, 이미지 가장자리를 누르면 이미지가 `![...](...)`로 바뀌었습니다.

**링크 양 끝에서 친 글자는 링크 안이 아니라 옆에 들어갑니다.** 링크는 글자만 그려지므로, 그 끝에 놓인 캐럿은 문서에서 두 자리를 동시에 가리킵니다. 마지막 글자 뒤와 `)` 뒤입니다. 지금까지는 늘 앞쪽이었고, 거기서 친 공백은 링크 안으로 들어갔습니다. 마크다운은 링크 글자 양 끝의 공백을 버리므로 아무 일도 일어나지 않은 것처럼 보였고, 그 뒤에 친 글자는 모두 링크의 일부가 됐습니다. 반대쪽 끝도 같습니다. 링크로 시작하는 문단은 그 앞에 글자를 쓸 자리가 아예 없었습니다. 링크 글자 자체를 고치려면 글자 사이에 캐럿을 두거나 막대의 입력란을 쓰면 됩니다. 그 입력란이 그러라고 있는 것입니다.

**툴바의 링크는 주소부터 묻습니다.** `link`와 `Mod`+`K`, 그리고 `image`와 `Mod`+`Shift`+`K` 또는 그 메뉴의 _이미지 링크 넣기_는 선택한 글과 `https://`로 시작하는 주소를 담은 막대를 캐럿 자리에 띄우고, 주소를 쓰고 `Enter`를 누르면 링크나 이미지를 씁니다. `Escape`를 누르거나 문서로 돌아가면 아무것도 쓰지 않고 취소합니다. 원문 화면에서는 같은 버튼이 지금처럼 `[](url)`을 씁니다.

**캐럿이 들어간 원시 HTML은 쓰인 글자 그대로 펼쳐지고**, 캐럿이 떠나면 다시 원래 모습으로 그려집니다. 에디터가 포커스를 가진 동안에만 그렇습니다. 펼쳐 놓으면 그 글자가 곧 원문이고, 이 화면의 모든 규칙이 그대로 적용됩니다.

**마커까지만 쓰이고 그 뒤가 아직 비어 있는 블록도 같은 방식으로 펼쳐집니다.** `#` 하나는 CommonMark에서 빈 제목이고, 파서도 그렇게 읽습니다. 그런데 빈 제목은 글자를 하나도 그리지 않아서, 방금 타이핑한 `#`이 타이핑하는 동안 화면에서 사라집니다. 문장 안에 `#` 기호를 쓰려던 사람은 만들지도 않은 제목을 되돌려야 합니다. 펼쳐 놓으면 화면에도 `#`이 남고, 공백을 한 번 더 치면 제목이 됩니다. `-`, `>`, `1.`, `- [ ]`도 같습니다. 글자가 사라진 자리에 글머리 기호나 세로줄, 번호, 체크박스만 남습니다. 펼치는 대상은 그런 블록 중 가장 바깥쪽입니다. 빈 항목 하나를 든 목록에서는 항목이 아니라 목록을 펼칩니다. 직접 쓴 `-` 옆에 글머리 기호가 또 그려져도 나아지지 않기 때문입니다. 펼친 글자는 펼친 링크처럼 회색 상자에 넣지 않고 문단 글꼴 그대로 그립니다. 곧 지나칠, 방금 입력한 글자일 뿐이기 때문입니다.

**글자가 아니라 요소로 그려지는 원시 HTML도 같은 방식으로 펼쳐집니다.** `sanitize`와 `raw` 양쪽에서 그렇습니다. `dangerouslySetInnerHTML`로 페이지에 닿은 마크업은 React가 내부를 알지 못하고 되돌릴 수도 없어서, 그려진 형태에는 캐럿이 들어갈 자리가 없습니다. 펼쳐 놓으면 그 자리가 생깁니다. 기본값인 `escape`에서는 처음부터 일반 텍스트이므로 다른 텍스트와 똑같이 편집됩니다.

## 입력 규칙

그려진 문서에서는 타이핑한 약칭이 그 자리에서 곧바로 그것이 뜻하는 서식이 됩니다. `# `은 제목, `- `과 `* `은 글머리 기호, `1. `은 번호, `> `은 인용, `- [ ] `은 체크박스입니다.

**이 대부분은 따로 구현한 기능이 아닙니다.** 키 입력마다 마크다운에서 문서를 다시 그리므로, 문단 맨 앞의 `# `은 공백이 닿는 순간 _이미_ 제목입니다. 파서가 그렇게 읽고 화면이 따라 그릴 뿐입니다. 설정하거나 끌 항목도 없습니다.

공백이 닿는 순간이고, 그전에는 바뀌지 않습니다. `#` 하나는 제목 안에 무언가가 들어가기 전까지 쓰인 글자 그대로 그려집니다. 이것은 입력 규칙이 아니라 [문서 편집 화면](#문서-편집-화면)이 속이 빈 블록을 펼쳐 두는 동작이고, 덕분에 문장 안에 `#`을 타이핑할 수 있습니다.

따로 적어 둔 규칙은 둘입니다. 마커 하나가 손대지 않은 텍스트의 뜻까지 바꾸는 경우입니다.

- **백틱 셋은 펜스를 열고, 펜스는 닫는 것이 나올 때까지 이어집니다.** 문서 중간에서 그것을 타이핑하면 아래에 있는 모든 것이 코드 블록 안에 들어가고, 닫는 펜스를 타이핑할 때까지 거기 남습니다. 그래서 펜스는 _닫힌 채로_ 열립니다. 커서는 둘 사이로 가고 그 줄에 있던 것은 안으로 들어갑니다. 코드 블록 버튼이 하는 일과 같습니다. 목록 항목이나 인용 안에서는 새로 만드는 두 줄이 그 컨테이너의 접두사를 함께 가져갑니다. 그러지 않으면 펜스가 자기를 연 항목 바깥에서 닫힙니다.
- **구분선에는 글자가 없습니다.** 자기 줄에 홀로 있는 `---`는 셋째 하이픈이 닿는 순간 구분선이 되고, 그러면 커서가 글자를 하나도 그리지 않는 블록 안에 놓여 화면에서 자리를 잃습니다. 그래서 구분선 아래에 이어서 타이핑할 빈 줄을 하나 만듭니다. `***`, `___`, `- - -`도 같습니다. 글이 이어지고 있는 줄 아래의 `---`는 건드리지 않습니다. 그 자리에서는 문단의 밑줄, 곧 setext 제목이고, 파서가 읽은 대로가 맞습니다.

코드 블록 안에서는 이 중 어느 것도 일어나지 않습니다. 그 안에 있는 모든 것은 쓰인 글자 그대로이기 때문입니다. 안에서 타이핑한 펜스는 코드에 넣고 싶은 글자 셋이므로 블록을 닫지 않고, 대신 블록의 펜스가 길어집니다. 안에 백틱 셋짜리 줄을 담은 블록은 백틱 넷으로 쓰입니다. 마크다운 안에 마크다운을 보여주는 파일이 모두 그렇게 쓰여 있고, 이 표기법이 바로 그런 경우를 위해 가진 규칙입니다. 붙여넣은 펜스도 같습니다.

줄바꿈을 만드는 규칙은 되돌리기 스택에서 한 단계를 따로 차지합니다. 그래서 규칙이 발동한 직후의 `Mod`+`Z`는 주변의 타이핑 전체가 아니라 그 규칙을 일으킨 글자만 돌려줍니다.

원문 화면에는 입력 규칙이 없습니다. 타이핑한 글자가 곧 문서이고, 줄 맨 앞의 `# `은 그 자체로 이미 제목입니다.

## 공백 하나, 빈 줄 하나

**연속한 두 번째 공백은 입력되지 않고, 두 번째 빈 줄도 마찬가지입니다.** 마크다운은 이어진 공백을 하나로 그립니다. 그래서 공백 세 개를 담은 문서는 그려진 곳과 쓰인 곳에서 서로 다른 말을 했습니다. 서식 화면에서는 하나, 옆의 원문에서는 셋이고, 파일에 무엇이 들어 있는지는 어느 쪽에도 나오지 않았습니다. 남는 글자를 그려서 해결하지는 않습니다. 파서가 버리는 공백을 그리는 일이기 때문입니다. 대신 그것을 쓰는 키 입력을 막고, 어떤 규칙인지 짧은 문장을 커서 아래에 띄웁니다. 1.5초 뒤에 저절로 사라집니다. 그 두 문장은 [`MawyStrings`](../api/types/locale)의 `oneSpace`와 `oneBreak`입니다.

줄바꿈 두 개는 두 블록을 나누는 빈 줄이므로 거기까지는 이어질 수 있습니다. 세 번째는 두 번째 빈 줄이고, 어느 화면도 높이를 보여 줄 수 없는 빈 문단입니다. 그래서 원문에서는 `Enter` 두 번이 새 문단이고, 서식 화면에서는 한 번입니다. 이미 빈 문단에 커서가 있을 때 한 번 더 누르면 아무것도 쓰이지 않습니다.

**공백을 그대로 두는 자리가 셋 있습니다.** 코드 블록 안과 원시 HTML 안에서는 모든 글자가 쓰인 그대로입니다. 표에서 셀과 파이프 사이를 띄우는 공백은 사람이 친 것이 아니라 에디터가 쓴 것입니다. 그리고 줄 맨 앞의 공백은 목록 항목을 한 단계 넣고 들여쓴 코드 블록을 만드는 것이므로, 글 사이에 이어진 공백이 아니라 들여쓰기입니다.

막는 것은 키 입력뿐입니다. 붙여넣은 문서, 파일에서 연 문서, 애플리케이션이 건넨 문서는 함께 온 공백과 빈 줄을 그대로 지킵니다. 문서가 들어오는 것은 누군가 타이핑하는 것이 아니기 때문입니다. 그리고 강제 줄바꿈에는 전용 키가 있습니다. 두 화면 모두에서 `Shift`+`Enter`가 그것을 이루는 공백 두 개를 씁니다.

## 서식

툴바의 모든 버튼은 키보드 단축키도 함께 가진 명령을 실행합니다. 툴바로만 실행할 수 있는 명령은 두지 않았습니다. 그런 명령이 있으면 포인터 없이는 에디터를 쓸 수 없기 때문입니다.

|                         |                                  |
| ----------------------- | -------------------------------- |
| `Mod` + `B`             | 굵게                             |
| `Mod` + `I`             | 기울임                           |
| `Mod` + `Shift` + `X`   | 취소선                           |
| `Mod` + `E`             | 코드                             |
| `Mod` + `K`             | 링크                             |
| `Mod` + `Shift` + `K`   | 이미지                           |
| `Mod` + `Shift` + `.`   | 인용                             |
| `Mod` + `Shift` + `8`   | 순서 없는 목록                   |
| `Mod` + `Shift` + `7`   | 순서 있는 목록                   |
| `Mod` + `Shift` + `9`   | 체크 목록                        |
| `Mod` + `Shift` + `E`   | 코드 블록                        |
| `Mod` + `Shift` + `,`   | 구분선                           |
| `Mod` + `Alt` + `F`     | 각주                             |
| `Mod` + `1`~`6`         | 제목 1~6                         |
| `Mod` + `0`             | 본문                             |
| `Mod` + `F`             | 찾기와 바꾸기                    |
| `Mod` + `S`             | 저장                             |
| `Mod` + `Shift` + `U`   | 이미지 올리기                    |
| `Tab` / `Shift` + `Tab` | 들여쓰기, 내어쓰기               |
| `Mod` + `Z`             | 되돌리기                         |
| `Mod` + `Shift` + `Z`   | 다시 하기. `Ctrl` + `Y`도 됩니다 |
| `Enter`                 | 목록 기호를 다음 줄로            |
| `Shift` + `Enter`       | 블록 안에서 줄만 바꾸기          |
| `Home` / `End`          | 줄의 양 끝으로                   |

`Mod`는 그 기기의 Command 또는 Control입니다. 어느 쪽인지 추측하지 않고 둘 다 받습니다.

각주는 Word와 Google Docs가 쓰는 키이고, 여기서 `Shift` 대신 `Alt`로 부르는 유일한 명령입니다. 목록과 인용은 GitHub 댓글 입력란과 같은 키를 쓰고, 체크 목록은 그다음 숫자를 씁니다. 이미지와 코드 블록은 링크와 코드에 `Shift`를 더한 키입니다. 구분선을 쓰는 `-` 키는 이미 쓰이고 있어서(`Mod`+`Shift`+`-`는 Chromium과 Firefox에서 화면을 축소합니다) 구분선은 `,`에 두었습니다. 숫자와 문장 부호는 입력되는 글자가 아니라 키의 자리로 읽습니다. `Shift`를 누른 `7`은 키보드에 따라 `&`가 되기도 하고 `/`가 되기도 하기 때문입니다. Windows와 Linux의 Firefox에서 `Ctrl`+`Shift`+`K`와 `Ctrl`+`Shift`+`E`는 개발자 도구를 여는 키인데, 에디터 안에서만 이 명령이 되고 페이지의 다른 곳에서는 그대로 개발자 도구를 엽니다.

::: fw flutter

이 표에서 이 패키지가 처리하지 않는 줄은 `Mod`+`S`와 `Mod`+`Shift`+`U`입니다. 저장할 곳도 이미지를 올리는 기능도 없어서이고, 자세한 내용은 [열기와 저장](#열기와-저장)에 있습니다. 되돌리기는 이 패키지가 아니라 플랫폼이 담당하며([되돌리기](#되돌리기)), 나머지는 모두 같습니다.

:::

**각주는 두 쪽을 한 번에 씁니다.** `footnote`과 `Mod`+`Alt`+`F`는 커서 자리에 `[^1]`을, 문서 끝에 `[^1]: `을 쓰고 커서를 내용 쪽에 둡니다. 두 쪽을 함께 쓰는 이유는 파서에게 내용 없는 참조는 아무것도 아니기 때문입니다. `[^1]`만 쓰고 마는 버튼은 문서를 조금도 바꾸지 못합니다. 번호는 문서에서 아직 아무도 쓰지 않은 첫 번호이고, 파서가 읽은 것이 아니라 문서에 쓰인 모든 `[^…]`을 세어 고릅니다. 그래서 아직 아무도 가리키지 않는 각주도 자기 번호를 지킵니다. 글자를 선택한 채로 누르면 참조가 그 끝에 붙습니다. 각주 표시가 놓이는 자리가 거기이기 때문입니다.

**`headingLevels`는 메뉴가 어떤 제목을 보여 줄지 정합니다.** 기본값은 여섯 수준 전부입니다. 마크다운의 제목이 여섯 수준이고, 메뉴에서 빠진 수준은 에디터가 쓸 수 없는 제목이기 때문입니다. 수준을 줄이는 쪽은 페이지가 제목을 자기 `h1`으로 쓰고 문서는 `##`부터 시작하는 애플리케이션을 위한 것입니다. 제목 2, 3, 4를 주면 그 셋과 본문을 보여 주고, `Mod`+`2`, `Mod`+`3`, `Mod`+`4`가 그 제목을 켜고 끄며, `Mod`+`1`은 그 키를 다루는 다른 쪽에 넘깁니다. 수준은 문서 자신의 깊이, 곧 적은 `#`의 개수입니다.

::: fw react

```tsx
<MawyEditor value={post.body} onChange={setBody} headingLevels={[2, 3, 4]} />
```

`headingBase`는 그 반대편으로, 문서의 내용은 바꾸지 않습니다. 그려진 문서와 미리보기가 `#`을 무엇으로 그릴지 정하며, [뷰어](./viewer#제목-레벨)에서와 뜻이 같습니다. 그래서 그런 페이지 옆의 에디터는 페이지가 그릴 모습대로 그립니다.

:::

::: fw flutter

```dart
MawyEditor(value: post.body, onChange: setBody, headingLevels: const [2, 3, 4]);
```

1에서 6 사이가 아닌 수는 빼고 씁니다.

:::

**밑줄은 없습니다.** 마크다운에는 밑줄을 쓰는 방법이 없고, 문서가 밑줄을 쓸 수 있는 유일한 방법은 raw HTML인 `<u>`입니다. 기본값인 `html="escape"`에서는 글자 그대로 보이고, 그릴 HTML이 아예 없는 Flutter 패키지에서도 그렇습니다. 이것을 쓰는 버튼을 두면, `sanitize`로 설정한 뷰어에서는 한 가지로 읽히고 같은 파일을 읽는 다른 모든 곳에서는 다르게 읽히는 문서가 생깁니다. 문서에 이미 있는 `<u>`는 `sanitize`와 `raw`에서 밑줄로 그립니다.

모든 명령은 **토글**입니다. 굵은 글자에 `Mod`+`B`를 누르면 굵기가 풀리고, 지금 걸려 있는 서식은 툴바에서 버튼이 눌린 모습으로 표시됩니다. 마커는 쌓이지 않고 서로를 대체하므로, 순서 있는 목록을 순서 없는 목록으로 바꾸면 `- 1. 항목`이 되지 않고 순서 없는 목록이 됩니다. 코드 블록은 그 안 어디서 눌러도 풀립니다. 코드 블록 안에서 코드 블록을 요청하는 것은 블록을 그만두겠다는 뜻이기 때문입니다. 그리고 그 안에서 대답하는 명령은 이것 하나뿐입니다. 코드 블록 안의 모든 것은 쓰인 글자 그대로여서 켜고 끌 서식이 없습니다. 코드 안의 낱말을 감싼 `**`는 별표 둘과 낱말이고, 누가 타이핑한 `>`는 부등호입니다. 그래서 커서가 코드 블록 안에 있으면 나머지 버튼과 키는 모두 비활성화되고, 코드 안의 기호를 서식으로 읽어 버튼을 눌린 모습으로 그리지도 않습니다. 아직 아무것도 없는 줄에서 목록, 인용, 제목 명령을 누르면 앞으로 쓸 글을 위한 기호를 먼저 씁니다. 커서는 줄 전체를 선택한 상태로 바뀌지 않고 원래 있던 글자 사이에 그대로 남습니다.

목록 항목 끝에서 `Enter`를 누르면 기호가 다음 줄로 이어지고 순서 있는 목록은 번호가 올라갑니다. 항목의 첫 줄뿐 아니라 그 항목이 이어지는 둘째 줄에서 눌러도 같습니다. 아직 비어 있는 항목에서 한 번 더 누르면 기호를 하나 더 만들지 않고 없앱니다. 이 동작이 없으면 목록에서 빠져나올 때마다 에디터가 방금 넣어 준 기호를 직접 지워야 합니다.

**목록에서 빠져나올 때는 빈 줄 하나를 두고 나옵니다.** 목록 항목 바로 아래 줄에 쓴 글자는 CommonMark에게 그 항목이 이어지는 줄이고, 그 항목 끝에 붙어서 그려집니다. 그래서 줄바꿈 하나만 두고 기호를 없애면 커서가 위 항목에 붙는 자리에 남았고, 거기서 `Enter`를 한 번 더 누르면 파서가 항목으로 읽는 줄 위에서 눌린 셈이라 기호가 다시 내려왔습니다. 목록 끝에서는 기호가 빠지면서 빈 줄이 들어갑니다. 목록 한가운데에서는 빈 줄을 넣을 자리가 없습니다. 두 항목 사이에는 이미 빈 줄이 하나 있고, 둘째 빈 줄은 두 화면 모두 쓰지 않는 줄이기 때문입니다. 그래서 그 줄은 기다렸다가, 거기에 처음 친 글자가 빈 줄을 쓰면서 자기 문단이 됩니다.

**`Home`과 `End`는 줄의 양 끝으로 갑니다.** 맥에서 이 두 키는 플랫폼에게 문서를 뜻합니다. `End`는 커서를 둔 채 문서 맨 아래로 스크롤하고, `Shift`+`End`는 문서 끝까지 선택합니다. 에디터에서는 두 키 모두 이름값을 못 한 셈입니다. 원문 화면이 말하는 줄은 거터가 번호를 매기는 줄입니다. 세 행으로 줄바꿈된 문단도 줄 하나이고 번호도 하나이며, 이 라이브러리의 모든 오프셋은 판의 폭에 따라 길이가 달라지는 행이 아니라 문서를 기준으로 셉니다. 문서 편집 화면은 번호를 매기지 않고 행을 그리므로, 거기서는 행이 줄입니다. `Shift`를 누르면 커서가 옮겨 가는 대신 선택이 늘어나고, 수식 키를 함께 누른 경우는 플랫폼이 쓰는 키이므로 건드리지 않습니다.

**`Shift`+`Enter`는 블록 안에서 줄만 바꿉니다.** 두 화면 모두 그렇습니다. 공백 두 개와 줄바꿈인데, 눈에 보이지는 않아도 세상의 거의 모든 마크다운 파일이 강제 줄바꿈을 이렇게 씁니다. 표의 셀에서는 `<br>`입니다. 표의 한 행이 파일의 한 줄이라 줄바꿈을 넣으면 행이 끝나기 때문입니다. 코드 블록 안에서는 그냥 줄바꿈입니다. 그 안에 있는 모든 것은 쓰인 글자 그대로이기 때문입니다. 새로 시작하는 줄은 커서가 들어 있는 컨테이너가 자기 줄마다 쓰는 것으로 엽니다. 인용의 `>`, 목록 항목이 둘째 줄부터 유지하는 들여쓰기가 그것입니다. 그래서 인용 안에서 줄을 바꾸면 그 줄도 인용으로 남습니다. 앞줄을 따라가서 인용처럼 읽히기만 하는 줄이 아닙니다. 코드 블록 안에서는 이 앞부분을 블록 자신의 줄이 시작하는 자리에서 읽습니다. 그 안의 `> `는 인용이 아니라 코드이기 때문입니다. 원문 화면은 이 키를 입력란에 그냥 넘겨서 줄바꿈 하나만 써 왔는데, 그것은 마크다운 파서에게 공백 한 칸입니다. 같은 키가 두 화면에서 서로 다른 뜻이었던 것입니다.

**조합 입력이 진행 중일 때는 어떤 키에도 답하지 않습니다.** 한글은 자모 하나씩 조합되고, 음절을 끝내는 키는 평범한 키입니다. `Enter`가 음절을 확정하는데, 브라우저는 그 키를 혼자 삼키지 않고 `isComposing`을 붙여 페이지로 보냅니다. 여기에 답하면 조합이 아직 바꾸는 중인 문서에 글을 쓰게 되고, 그것을 쓰려고 옮기는 커서가 조합을 그 자리에서 끝내 버립니다. 그래서 한글 목록 항목 끝에서 `Enter`를 누르면 조합 중이던 음절이 사라지고 그 자리에 빈 항목이 남았습니다. 조합이 끝나면 키가 다시 오고, 그때가 키가 제 뜻대로 동작할 때입니다. `Escape`만 예외입니다. 조합을 끝내는 것이 그 키가 하는 일이기 때문입니다.

편집은 브라우저 자신의 텍스트 삽입 명령으로 들어갑니다. 커서와 스크롤 위치, 진행 중인 조합을 있던 자리에 그대로 두기 때문입니다. 값을 직접 써 넣는 방식은 그중 어느 것도 보장하지 않습니다. 되돌리기는 더 이상 이 선택의 이유가 아니며, 그 내용은 아래에 절을 따로 두었습니다.

`toolbar`는 `true`, `false`, 또는 그릴 컨트롤과 그릴 순서를 받습니다.

```tsx
<MawyEditor defaultValue={document} toolbar={['mode', 'separator', 'bold', 'italic', 'link']} />
```

| 항목 |  |
| --- | --- |
| `'mode'` | 화면 전환 |
| `'undo'`, `'redo'` | 기록을 한 단계 되돌리고 다시 합니다. 할 단계가 없으면 비활성화됩니다 |
| `'heading'` | 제목 여섯 수준과 본문 메뉴. `headingLevels`를 주면 그 수준들 |
| `'bold'`, `'italic'`, `'strikethrough'`, `'code'`, `'link'`, `'image'` | 인라인 서식 |
| `'quote'`, `'bulletList'`, `'orderedList'`, `'taskList'`, `'codeBlock'`, `'rule'` | 블록 |
| `'table'` | 누른 크기의 빈 표를 넣는 격자. [표](#표)를 보세요 |
| `'find'` | 찾기 바를 엽니다. [찾기](#찾기)를 보세요 |
| `'open'`, `'save'` | 마크다운 파일을 읽고 내보냅니다. [열기와 저장](#열기와-저장)을 보세요 |
| `'colorScheme'` | 라이트·다크·시스템 설정 |
| `'separator'` | 묶음을 나누는 가는 선 |

::: fw react

**버튼을 다 담기에 좁은 바는 들어가는 만큼만 두고 나머지를 끝의 메뉴에 넣습니다.** 뒤에서부터 묶음 단위로 옮기고, 묶음은 구분선으로 나눕니다. 그래서 `toolbar`의 순서를 바꾸면 무엇이 먼저 밀려날지도 함께 바뀝니다. 화면 전환은 어느 너비에서도 메뉴로 들어가지 않습니다. 글 쓰는 사람이 가장 자주 누르는 컨트롤이기 때문입니다.

툴바가 자기 너비를 재서 결정하며, 설정할 수 있는 값은 아닙니다. 이전에는 두 번째 줄로 넘겼는데, 툴바 위의 레이아웃에 그 줄이 들어갈 자리가 없었습니다. 버튼이 늘어나는 동안 바의 높이는 그대로여서 아랫줄이 바 밖으로 나갔습니다.

:::

::: fw flutter

**버튼을 다 담기에 좁은 바는 옆으로 스크롤합니다.** 메뉴로 숨기지 않습니다. 줄이 `SingleChildScrollView` 안에 있어서 들어가지 않는 버튼은 한 번 밀면 나오고, 줄을 따라 포커스를 옮기는 화살표도 그 버튼을 화면 안으로 끌어옵니다.

React 패키지는 같은 문제를 바 끝의 메뉴로 해결하며, 이 차이는 플랫폼에서 옵니다. 터치 스크린에서는 손가락으로 미는 줄이, 포인터를 쓰고 바를 옆으로 끌 방법이 뚜렷하지 않은 페이지에서는 메뉴가 자연스럽습니다.

:::

## 표

**툴바의 `table` 버튼은 크기를 물어보고 그 크기의 빈 표를 넣습니다.** 열 열 개, 행 여덟 개짜리 격자가 열리고, 모서리부터 포인터가 올라간 칸까지 불이 켜집니다. 머리글도 행 하나로 셉니다. 화살표로 켜진 크기를 바꾸고 `Enter`로 넣으며, 스크린 리더에는 크기마다 따로 된 버튼으로 알려 줍니다.

**표의 행과 열은 커서 옆에 뜨는 막대에서 바꿉니다.** 커서가 표 안에 있고 에디터가 포커스를 가진 동안, 커서가 있는 셀 조금 아래에, 커서가 그 셀에 들어온 위치부터 작은 막대가 뜹니다. 같은 셀 안에서 커서를 옮기거나 글자를 선택하는 동안에는 막대가 그 자리에 머뭅니다. 화면에서 셀 아래에 자리가 없으면 셀 위에 뜹니다. 위나 아래에 행 추가, 앞이나 뒤에 열 추가, 커서가 있는 행이나 열 삭제, 그 열의 왼쪽·가운데·오른쪽 정렬, 그리고 맨 끝에 빨간색으로 표 전체 삭제가 들어 있습니다. 원문에서는 커서가 있는 줄 아래에 뜹니다. 막대는 커서를 따라다니므로, 화면보다 긴 표에서도 표의 먼 끝이 아니라 지금 쓰는 행 옆에 있습니다. 막대가 커서 아래 행을 덮기 때문에 그 행을 누르려다 막대를 누를 수 있어서, 추가 버튼은 커서에 가까운 쪽에, 삭제 버튼은 먼 끝에 둡니다. 커서 너머에 막대가 들어갈 자리가 없으면 커서에서 반대쪽으로 뻗고 버튼 순서도 뒤집어서, 삭제 버튼은 여전히 먼 끝에 있습니다. 막대를 눌러도 포커스를 가져가지 않으므로, 다음 글자는 커서가 있던 셀에 그대로 들어갑니다. 결과는 GitHub 표입니다. 명령마다 줄당 셀 하나만 넣거나 빼고 표 전체를 다시 쓰지 않으므로, 구분 행의 정렬과 다른 셀에 쓴 내용은 그대로 남습니다. 명령마다 단축키가 있습니다.

|                                       |                |
| ------------------------------------- | -------------- |
| `Mod` + `Alt` + `T`                   | 표 넣기        |
| `Mod` + `Enter`                       | 아래에 행 추가 |
| `Mod` + `Shift` + `Enter`             | 위에 행 추가   |
| `Mod` + `Alt` + `Enter`               | 뒤에 열 추가   |
| `Mod` + `Alt` + `Shift` + `Enter`     | 앞에 열 추가   |
| `Mod` + `Shift` + `Backspace`         | 이 행 삭제     |
| `Mod` + `Alt` + `Shift` + `Backspace` | 이 열 삭제     |

`Enter`는 행을 더하고 `Backspace`는 행을 뺍니다. `Alt`를 더하면 행 대신 열이고, `Shift`를 더하면 위쪽 행이나 커서가 있는 행입니다. 글자 키가 외우기는 쉽지만 거의 모든 글자가 이미 쓰이고 있습니다. `Mod`+`Alt`+`I`는 브라우저의 개발자 도구를 열고, `Mod`+`Shift`+`T`는 닫은 탭을 다시 열며, Windows의 `Ctrl`+`Alt`는 `AltGr`이라 유럽의 여러 키보드에서 `€`나 `@`를 입력합니다. 새 표의 `T`는 `AltGr`이 건드리지 않는 몇 안 되는 글자입니다.

**열 정렬도 같은 막대에서 바꿉니다.** GitHub는 셀이 아니라 열 단위로 정렬하며, 구분 행의 대시 한쪽에 콜론을 붙이거나 가운데 정렬이면 양쪽에 붙입니다. 그래서 정렬 버튼 세 개는 커서가 있는 열의 구분 셀에 그 콜론을 쓰고, 대시 개수는 그대로 둡니다. 열에 이미 적용된 정렬 버튼은 눌린 상태로 그리고, 한 번 더 누르면 콜론을 지웁니다. 여러 셀을 선택했으면 선택이 걸친 모든 열을 정렬합니다.

**셀은 셀 단위로 선택합니다.** 한 셀에서 시작한 드래그가 다른 셀에 닿으면, 브라우저가 지나간 글자가 아니라 두 셀 사이의 사각형 셀 영역이 선택되고 그려진 문서가 그 영역을 표시합니다. 원문에서도 한 셀 안의 자리에서 다른 셀 안의 자리까지 선택하면 같은 사각형이 됩니다. 셀이 둘 이상 선택되면 막대의 버튼은 선택이 걸친 행이나 열 수만큼 작동하고 `이 행 2개 삭제`, `뒤에 열 3개 추가`처럼 개수를 말하며, 셀을 비우는 버튼이 하나 더 생깁니다. 그려진 문서에서는 `Delete`, `Backspace`, 잘라내기도 표 모양은 그대로 둔 채 셀만 비우고, 선택된 셀 위에 글자를 입력하면 셀을 비우고 첫 셀에 씁니다. 행과 열 단축키도 선택 영역에 같은 방식으로 작동합니다. 머리글 행과 모든 열을 한꺼번에 지우지는 않습니다.

단축키는 표 안에서만 동작하고, 표 밖에서는 그 키를 다루는 다른 쪽에 넘깁니다. `Mod`+`Alt`+`T`로 만든 표는 빈 열 두 개에 머리글 행과 본문 행이 하나씩이고, 새 표에는 언제나 앞뒤에 빈 줄이 붙습니다. 열 이름은 넣지 않습니다. 넣으면 인터페이스의 언어로 문서에 그대로 남기 때문입니다. 인용문이나 목록 항목 안에서는 줄마다 그 컨테이너의 접두사를 붙여 표를 그 안에 넣고, 코드 블록이나 다른 표 안에는 표가 들어갈 자리가 없으므로 격자가 비활성화됩니다. 머리글 위에는 행을 넣을 수 없고 마지막 열은 지울 수 없으므로, 그 자리에서는 막대의 해당 버튼이 비활성화됩니다. `parse`에서 `gfm`을 끄면 파서가 표를 읽지 않으므로 이 명령들도 아무 일을 하지 않습니다.

::: fw react

**셀에는 한 줄의 글만 들어가고 블록은 들어가지 않습니다.** GitHub 표의 행 하나는 파일의 한 줄이라서, 셀에는 굵게, 기울임, 코드, 링크, 그림과 `<br>`로 쓴 줄바꿈은 넣을 수 있지만 제목, 인용, 코드 블록, 목록은 넣을 수 없습니다. `- `로 시작하는 줄이 나오는 순간 표가 끝나기 때문입니다. 그래서 커서가 표 안에 있으면 제목 메뉴와 그런 블록의 버튼이 비활성화되고 단축키도 아무 일을 하지 않습니다. 전에는 행 맨 앞에 기호를 써서 표를 망가뜨렸습니다. 셀에 붙여넣은 글도 셀의 한 줄 안에 남습니다. 줄바꿈은 `<br>`이 되고 `|`는 이스케이프됩니다.

**셀 안의 목록은 셀의 줄로 씁니다.** 셀에 목록을 넣을 수는 없지만 목록처럼 읽히게 쓸 수는 있습니다. 목록 버튼과 단축키는 커서가 있는 셀의 줄, 곧 `<br>` 사이의 줄 맨 앞에 항목 기호를 쓰고 다시 누르면 지웁니다. 여러 셀을 선택했으면 선택한 셀의 모든 줄에 기호나 번호를 붙입니다. 기호로 시작하는 줄에서 `Enter`를 누르면 새 줄에도 기호가 이어지고 번호는 하나 커집니다. 기호 뒤에 아무것도 없는 줄에서 누르면 목록에서처럼 기호가 사라집니다. 그런 줄에서 `Tab`을 누르면 기호 앞에 공백 두 칸을 써서 윗줄 아래로 중첩하고, `Shift`+`Tab`은 그 공백을 지웁니다. 셀의 첫 줄은 위에 중첩할 줄이 없습니다. 셀 안의 목록에 `Tab`이 필요하므로 `Tab`으로 셀을 옮겨 다니지는 않습니다. 에디터와 미리보기, 뷰어는 그런 줄을 글머리표나 체크박스, 번호로 그리고 기호 앞의 공백만큼 들여 그리며, 기호 바로 뒤에서 `Backspace`를 누르면 기호가 지워집니다. GitHub은 기호를 글자 그대로 그리므로 `1. 하나<br>2. 둘`은 거기서도 번호 목록처럼 읽히지만 들여쓰기는 없습니다. 줄의 마지막 단어 뒤에 친 공백은 기호 뒤의 공백을 포함해 커서가 그 뒤에 있는 동안 화면에 그립니다. 마크다운은 그 공백을 남기지 않기 때문입니다.

**그려진 문서의 표는 입력하는 동안 모양이 바뀌지 않습니다.** 모든 열의 너비가 같고, 표 너비는 문서 너비와 열을 읽을 만한 너비 중 넓은 쪽이며 그보다 넓으면 옆으로 스크롤합니다. 빈 셀도 글자 한 줄 높이라서 커서가 들어갈 자리가 있고, 첫 글자를 입력해도 아무것도 움직이지 않습니다. 마크다운 표에는 열 너비를 적을 방법이 없기 때문이며, 미리보기와 뷰어는 지금처럼 내용에 맞춰 표를 그립니다.

그려진 문서에서는 **셀 안에서 `Enter`를 누르면 그 셀 안에서 줄이 바뀝니다.** `Shift`+`Enter`도 같습니다. 표의 행 하나는 파일의 한 줄이라서, 다른 곳에서 `Enter`가 쓰는 줄바꿈을 넣으면 행이 끝나 버립니다. 그래서 대신 `<br>`을 씁니다. GitHub 표도 셀에 두 줄을 넣을 때 이렇게 씁니다. 표 셀 안의 `<br>` 하나는 `escape`를 포함한 모든 `html` 정책에서, 그리고 Flutter 패키지에서도 줄바꿈으로 그립니다. 셀 안에서 줄을 바꿀 방법이 이것뿐이기 때문입니다. 그 뒤에서 `Backspace`를 누르면 `<br>`이 통째로 지워집니다. 아래에 행을 넣는 것은 `Mod`+`Enter`입니다. `ArrowUp`과 `ArrowDown`은 셀 안의 줄을 하나씩 오간 다음 같은 열의 위아래 셀로 갑니다. 브라우저에 맡기면 같은 행의 다음 셀로 가 버립니다. 마지막 행에서 `ArrowDown`을 누르면 표 다음 줄로 가고, 표가 문서 끝에 있으면 그 자리에 줄을 엽니다. 빈 셀에 입력하면 글자가 공백 사이에 들어가서, `|  |`는 `|  이름|`이 아니라 `| 이름 |`이 됩니다.

:::

::: fw flutter

여기에는 그려진 문서가 없으므로, 원문의 표 행에서 `Enter`는 React 패키지의 원문에서처럼 줄바꿈입니다. 셀에는 블록이 들어가지 않으므로 커서가 표 안에 있으면 제목 메뉴와 제목, 인용, 코드 블록, 구분선 버튼이 비활성화됩니다. 코드 블록 안에서는 서식이라는 것이 없으므로 코드 블록 버튼을 뺀 모든 버튼이 비활성화됩니다. 둘 다 React 패키지와 같은 이름의 같은 규칙입니다. 목록 버튼은 React 패키지처럼 커서가 있는 셀의 줄 맨 앞에, 여러 셀을 선택했으면 그 셀의 모든 줄에 항목 기호를 씁니다. 격자와 막대 뒤의 명령은 React 패키지와 같은 이름의 같은 함수이고, 패리티 검사가 둘을 비교합니다.

:::

## 이미지

**툴바의 이미지 버튼**은 `![](url)`을 쓰고 그 목적지를 선택해 둡니다. 바로 덮어쓰면 됩니다. 링크 버튼 앞에 `!` 하나가 붙은 것이고, 규칙도 같습니다. URL을 선택하고 누르면 그것이 목적지가 되고, 그 밖의 것을 선택하고 누르면 그것이 이미지를 보지 못하는 독자에게 주는 설명이 됩니다. 애플리케이션에서 받아야 할 것이 없어서 언제나 쓸 수 있습니다.

::: fw react

이미지가 들어오는 경로는 두 가지가 더 있습니다. 이미지가 URL을 이미 가진 경우와 아직 없는 경우를 나누어 다루기 때문입니다.

**`onUploadImage`를 주면 이 버튼은 두 항목짜리 메뉴가 됩니다.** _이미지 올리기_는 기기의 파일 선택 창을 열고, _이미지 링크 넣기_는 위의 `![](url)`을 씁니다. 휴대폰이나 태블릿에서는 파일 선택 창이 유일한 길입니다. 끌어다 놓을 파일이 없고, 사진 보관함의 사진은 클립보드에 있지 않기 때문입니다. 그래서 `image/*`를 요청하고, 플랫폼은 사진 보관함과 카메라를 보여 줍니다. 여러 장을 한 번에 고를 수 있습니다. `Mod`+`Shift`+`U`로도 같은 창이 열립니다. 고른 그림은 메뉴를 열기 전 커서가 있던 자리에 들어가고, 끌어다 놓은 파일과 같은 규칙을 모두 따릅니다. 그 규칙은 이 절의 나머지에서 설명합니다.

**웹 페이지의 일부로 붙여넣거나 끌어다 놓은 이미지**는 이미 가지고 있던 URL 그대로 들어옵니다. 이것은 이미지 기능이 아니라 [붙여넣기](#붙여넣기)가 마크업을 읽은 결과입니다. 그림이 이미 웹에 있으므로 업로드하지 않습니다.

마크업이 이기는 것은 마크업에 쓸 내용이 있을 때뿐입니다. 브라우저는 이미지를 복사할 때 파일과 함께, 그 이미지를 그린 주소를 가리키는 `<img>`를 클립보드에 넣습니다. 그 주소가 `blob:`, `file:`, `cid:`이면 다른 누구도 닿을 수 없습니다. 글자도 없고 닿을 수 있는 주소의 그림도 없는 마크업은 제쳐 두고, 곁에 있는 파일을 대신 업로드합니다.

**`data:` 주소의 그림도 업로드할 곳이 있으면 업로드합니다.** `data:` 주소는 웹 어딘가를 가리키는 주소가 아니라 그림의 바이트 자체이고, 그 바이트를 문서에 넣을지는 `onUploadImage`가 답하는 질문입니다. 함께 붙여넣은 글은 바로 들어가고, 그림은 업로드가 답하면 원래 있던 자리에 들어갑니다. `onUploadImage`가 없으면 들어온 `data:` 주소 그대로 씁니다. 그 그림을 가져온 페이지가 그렇게 적었기 때문입니다.

**워드 프로세서에서 복사한 그림은 마크업 옆의 RTF에서 꺼내 업로드합니다.** 업로드할 곳이 있을 때의 이야기입니다. Word는 클립보드에 넣는 마크업에 그림을 적는데, 일부 그림은 복사한 컴퓨터의 폴더에 있는 파일을 가리키는 `<img>`로 적는다고 보고되었습니다. 그런 주소는 어떤 페이지도 열 수 없습니다. 같은 클립보드에는 문서가 RTF로도 들어 있고 거기에는 그림마다 바이트가 모두 들어 있으므로, 아무도 닿을 수 없는 주소의 그림은 거기서 꺼내 `data:` 그림처럼 업로드합니다. RTF의 어느 그림이 어느 `<img>`의 것인지는 순서대로 세어 봐야만 알 수 있어서, 두 수가 다르면 그림을 엉뚱한 자리에 넣는 대신 그 그림들을 넣지 않습니다. 함께 들어오는 PNG 파일은 그림이 아니라 글까지 포함한 선택 영역 전체를 찍은 것이고, 마크업에 글이 있으므로 업로드하지 않습니다.

**파일**은 다릅니다. 클립보드의 스크린샷이나 바탕화면에서 끌어온 이미지는 그 바이트를 저장할 곳이 있어야 하는데, 그 한 가지는 이 라이브러리가 정할 수 없습니다. 오브젝트 스토리지에 올릴지, 업로드 엔드포인트로 보낼지, `data:` URI로 문서 안에 넣을지는 비용과 정책이 걸린 선택이라 애플리케이션이 정해야 합니다. 그래서 프롭으로 두었습니다.

```tsx
<MawyEditor
  defaultValue={document}
  onUploadImage={async (file) => {
    const { url } = await save(file);

    return url;
  }}
/>
```

쓸 URL을 돌려주면 되고, 그 주위에 무엇을 쓸지까지 정하려면 `{ url, alt, title }`을 돌려줍니다. 그러지 않으면 확장자를 뗀 파일 이름이 설명이 됩니다. 예외를 던지거나 아무것도 답하지 않으면 에디터는 이미지를 넣지 못했다고 말하고 아무것도 쓰지 않습니다. 이 알림은 그사이 다른 업로드가 몇 개 끝나든 다음 업로드가 시작될 때까지 문서 아래에 남아 있습니다.

**이유를 말하려면 `{ reason }`을 돌려줍니다.** 문서 아래 알림이 받은 이유를 그대로 보여 주므로, 인터페이스의 언어로 써야 합니다. 애플리케이션이 이미 자기 방식으로 알렸다면 `{ reason: null }`을 돌려주세요. 그러면 에디터는 그 파일에 대해 아무 말도 하지 않아서 같은 알림이 두 번 뜨지 않습니다. 던진 예외의 내용은 보여 주지 않습니다. 독자가 봐야 할 말만큼이나 개발자를 위한 네트워크 오류 메시지일 수도 있기 때문입니다.

```tsx
<MawyEditor
  onUploadImage={async (file) => {
    if (file.size > LIMIT) {
      return { reason: t('upload.tooLarge') };
    }

    return (await save(file)).url;
  }}
/>
```

여러 파일을 한 번에 넣으면 알림도 하나입니다. 들어간 파일은 화면에 보이므로 따로 말하지 않습니다. 알림은 들어가지 못한 파일의 이유를 파일 순서대로 하나씩만 말하고, 이어서 이유 없이 실패한 파일이 몇 개인지 말합니다. _이미지 3개 중 1개를 넣지 못했습니다._

**`onUploadImage`가 없으면 끌어다 놓은 파일은 거절됩니다.** 일부만 넣지도 않고 브라우저에 넘기지도 않습니다. 에디터가 그 드롭을 받아 아무것도 쓰지 않고, 문서 아래 줄에 그 사실을 표시합니다. 의도한 기본값입니다. 남은 선택지는 2 MB짜리 스크린샷을 `data:` URI로 바꿔 문서 안에 넣는 것뿐이기 때문입니다.

이미지는 놓은 자리에 들어갑니다. 끌어다 놓으면 포인터를 놓은 지점으로, 붙여넣으면 커서 자리로 가고 선택한 내용이 있으면 그 내용을 대신합니다. 선택한 내용은 파일을 붙여넣을 때가 아니라 업로드가 답할 때 바뀌므로, 업로드가 실패하면 그 글은 그대로 남습니다. 여러 파일을 한 번에 놓으면 업로드는 하나씩 이어서 하고, 편집은 마지막에 **한 번**만 합니다. `Mod`+`Z` 한 번으로 방금 놓은 파일 전체를 되돌리게 하기 위해서입니다.

**이미지가 올라가는 동안에도 글은 계속 쓸 수 있습니다.** 이미지를 넣은 자리는 그사이 생긴 모든 변경을 따라 옮겨집니다. 문장 끝에 붙여넣은 이미지는 누군가 그 문장 앞에 단어를 더 써도 여전히 그 문장 끝에 들어가고, URL이 돌아왔을 때 어느 화면이 보이든 들어갑니다. 들어갈 때 포커스를 가져가지도 않습니다. 페이지의 다른 입력란으로 옮겨 간 사람은 그 자리에 그대로 있고, 이미지가 커서 앞에 들어가면 커서도 그만큼 뒤로 밀립니다.

**읽기 전용인 문서는 그동안 끝난 업로드로도 바뀌지 않습니다.** 애플리케이션은 저장하는 동안 `readOnly`를 켜 두는데, 저장 도중에 이미지가 들어가면 화면에는 있지만 저장된 문서에는 없는 이미지가 됩니다. 그래서 이미지는 기다립니다. 문서 아래 알림은 계속 이미지를 넣는 중이라고 표시하고, `readOnly`가 풀리는 즉시 넣었던 자리에 들어갑니다.

**`onUploadingChange`는 아직 들어오는 중인 이미지가 몇 개인지** 바뀔 때마다 알려 줍니다. 애플리케이션은 이 수가 0이 될 때까지 저장 버튼을 막아 둘 수 있습니다. 그 전에 저장하면 그 이미지는 빠진 채로 저장됩니다. 에디터가 읽기 전용일 때 업로드가 끝난 이미지도 문서에 들어갈 때까지는 셉니다. 페이지에서 사라지는 에디터는 기다리던 것이 어디에도 들어가지 않으므로, 사라지면서 0을 알립니다.

```tsx
const [uploading, setUploading] = useState(0);

<>
  <MawyEditor onUploadImage={upload} onUploadingChange={setUploading} />
  <button disabled={uploading > 0} onClick={save}>
    저장
  </button>
</>;
```

:::

::: fw flutter

**여기에는 업로드가 없습니다.** 클립보드의 그림도 기기의 파일도 플러그인 없이는 위젯이 닿을 수 없고, 애플리케이션이 어떤 플러그인을 골랐는지는 마크다운 에디터가 정할 일이 아닙니다. `open`이 애플리케이션이 뜻을 정해 주는 버튼인 것과 같은 이유입니다. 선택기를 가진 애플리케이션은 파일을 고르고, 그림을 두는 곳에 저장한 뒤, [`MawyEditorHandle`](../api/components/mawy-editor#에디터-밖에서)로 커서 자리에 그림을 씁니다.

```dart
final MawyEditorHandle editor = MawyEditorHandle();

Future<void> addPicture() async {
  final Picture? picked = await pickPicture(); // 애플리케이션의 선택기
  if (picked == null) return;

  editor.insert('![${picked.name}](${await store(picked)})');
}
```

그림은 `insert`를 부른 때의 커서 자리에 들어가므로, 업로드가 오래 걸리면 그동안 쓴 글의 끝에 들어갑니다. 에디터가 읽기 전용이면 아무것도 쓰지 않습니다.

:::

## 미리보기의 코드 색

`highlight`는 미리보기 안의 뷰어로 그대로 전달됩니다. `split`과 `preview` 화면은 [뷰어와 같은 방식](./viewer#코드-블록에-색-입히기)으로 코드에 색을 입히고, 그려진 문서도 같은 하이라이터로 코드 블록에 색을 입힙니다. 필요할 때 불러오는 지연 로딩 형태도 그대로 쓸 수 있고, 그 편을 권합니다.

```tsx
<MawyEditor
  defaultValue={document}
  highlight={() => import('mawy-react/highlight').then((module) => module.mawyHighlighter)}
/>
```

**그려진 문서의 코드 블록은 입력하는 동안에도 색이 입혀집니다.** 색을 입힌 조각마다 그 화면의 다른 요소처럼 원문의 어디에서 왔는지 적혀 있으므로, 조각 안의 커서도 색이 없는 코드에서와 같은 글자로 돌아가고, 입력한 글자는 다음 렌더링에서 다시 색이 입혀집니다. 원문 화면에는 마크다운 전용 하이라이터가 따로 있어서, 거기서 코드 블록은 그 언어가 아니라 마크다운으로 색이 입혀집니다.

## 열기와 저장

`open`은 마크다운 파일을 에디터로 읽어 들이고, `save`는 문서를 다시 내보냅니다. `Mod`+`S`로도 저장합니다. 브라우저의 `Mod`+`S`는 페이지를 저장하는 기능인데, 에디터에서 글을 쓰던 사람이 그 키로 기대하는 동작은 문서 저장이기 때문입니다.

```tsx
<MawyEditor
  defaultValue={document}
  onSave={(value, name) => api.put(`/documents/${name}`, value)}
/>
```

`onSave`가 없으면 텍스트를 다운로드로 내보냅니다. Chromium에만 있는 File System Access API 대신 `download` 속성을 단 앵커를 씁니다. 어떤 브라우저에서만 동작하는 저장은 모든 브라우저에서 같게 동작하는 저장보다 못하기 때문입니다. `onSave`가 있으면 아무것도 내려받지 않고, 저장할 이름과 문서를 애플리케이션에 건넵니다.

파일을 열어 둔 상태라면 그 파일의 이름을 쓰고, 아니면 **문서의 첫 제목**을 씁니다. 폴더에서 파일 목록을 볼 때 읽기 좋은 이름이기 때문입니다. 파일 시스템이 받지 않는 글자는 떼어내고, 가져올 제목이 없으면 `document.md`가 됩니다.

`open`에 단축키를 두지 않은 것은 의도적입니다. 브라우저의 `Mod`+`O`를 그대로 두는 편이 낫고, 파일 열기는 글을 쓰는 중간에 자주 하는 동작이 아닙니다.

**에디터에 놓은 파일은 문서가 아니라 이미지로 처리합니다.** 끌어다 놓기가 이미 이미지가 들어오는 경로인 것도 이유지만, 더 큰 이유는 따로 있습니다. 파일이 떨어졌다는 이유로 쓰고 있던 문서를 갈아치우면 작업 내용이 사라집니다. 뷰어는 잃을 내용이 없어서 놓인 파일을 바로 열지만, 에디터에서는 그렇게 하지 않습니다.

그래도 그 드롭은 에디터가 처리합니다. **받지 않을 파일도 브라우저에 넘기지 않고 거절합니다.** 브라우저에 넘기면 그 파일을 페이지로 열어 버려서, 문서와 되돌리기 기록과 커서가 탭과 함께 사라집니다. 문서 아래 줄에 무슨 일이 있었는지와 어느 컨트롤을 써야 하는지 표시합니다.

**`fileDrop`은 그 규칙을 끕니다.** 이미 문서를 담고 있는 에디터가 아니라, 비어 있는 상태로 시작해서 파일을 _가져오는_ 에디터를 위한 옵션입니다. 켜면 끌어다 놓은 `.md`가 문서로 열리고, 비어 있는 미리보기 자리에 뷰어의 빈 상태가 그대로 들어가 파일 선택기를 보여줍니다. `onUploadImage`가 주어져 있으면 끌어다 놓은 이미지는 그대로 이미지로 처리하고, 그때까지 거절하던 파일만 문서로 읽습니다.

::: fw flutter

이 절은 React 패키지에만 해당합니다. 여기서 파일을 열고 되돌려 쓰는 일은 애플리케이션이 맡습니다. 파일 선택기는 위젯이 아니라 플러그인이고, 앱이 어떤 플러그인을 쓰는지는 마크다운 에디터가 정할 문제가 아닙니다. 같은 이유로 `open`은 애플리케이션이 `onOpen`으로 뜻을 정해 주는 버튼이고 그것이 없으면 그리지 않으며, `save`는 없습니다. `onChange`가 문서를 건네고, 그 문서를 어디에 저장할지는 애플리케이션이 정합니다.

:::

## 찾기

`Mod`+`F`가 원문 위에 찾기 바를 열고, 툴바의 `find` 버튼도 같은 일을 합니다. `Enter`는 다음 결과로, `Shift`+`Enter`는 이전 결과로 가고, `Escape`는 바를 닫고 포커스를 문서에 돌려줍니다.

::: fw react

브라우저의 찾기가 여기까지 닿지 못해서 따로 두었습니다. **어떤 브라우저도 `<textarea>` 안의 글자는 찾지 않는데**, 원문 화면이 바로 `<textarea>`입니다. 이 라이브러리는 다른 모든 곳에서 플랫폼이 이미 하는 일을 플랫폼에 맡기고, 여기가 유일한 예외입니다.

:::

::: fw flutter

이유는 React 패키지와 같습니다. **플랫폼의 찾기는 글이 놓인 화면까지만 닿고 텍스트 필드 *안*까지는 닿지 않는데**, 원문 화면이 바로 그 텍스트 필드입니다. 이 라이브러리는 다른 모든 곳에서 플랫폼이 이미 하는 일을 플랫폼에 맡기고, 여기가 유일한 예외입니다.

그 아래의 계산은 React 패키지와 함수 단위로 같습니다. `findMatches`, `matchFrom`, `replaceMatch`, `replaceAll`이 그렇습니다. 코드가 바뀔 때마다 `tool/parity.dart`가 `tool/searches.json`으로 둘을 대조합니다. `aaaa` 안의 `aa`를 두 개로 셀지 세 개로 셀지는 선택이 필요한 문제이고, 두 패키지가 같은 선택을 합니다.

:::

한 줄 안에서 선택한 글자가 있으면 바가 열릴 때 그 글자가 이미 상자에 들어 있습니다. 대개 그것이 지금 찾으려는 글자이기 때문입니다.

**정규식이 아니라 일반 텍스트로 찾습니다.** 마크다운 문서에는 `*`, `[`, `.`, `+`가 자주 나오는데, 이런 글자를 정규식으로 해석하면 `(` 하나에 문법 오류가 납니다. 대신 대소문자 구분 스위치를 두었고, 실제로 필요한 것은 그쪽입니다.

바꾸기와 모두 바꾸기는 두 번째 줄에 있습니다. 모두 바꾸기는 원래 문서를 한 번만 훑습니다. 그래서 `a`를 `aa`로 바꿔도 각 `a`가 한 번씩만 바뀌고, 방금 넣은 글자를 다시 찾지 않습니다.

::: fw react

바는 문서를 편집할 수 있는 `plain`, `split`, `wysiwyg`에서 나옵니다. `preview`에서는 문서가 엘리먼트로 그려져 있어서 브라우저 자신의 찾기가 동작합니다.

**`wysiwyg`에서는 화면에 그려진 글자를 찾습니다.** 검색은 여전히 바꾼 글자를 써 넣을 마크다운을 대상으로 하지만, 모든 글자가 그대로 그려진 일치 항목만 셉니다. 링크 주소에 들어 있는 `bold`는 화면에 그려지지 않으므로 세지도, 이동하지도, 바꾸지도 않고, 개수는 읽는 사람이 볼 수 있는 개수와 같습니다. 일치 항목은 서식 구간 둘에 걸칠 수 없으므로 `he**llo**`에서 `hello`는 찾지 못합니다. 표시는 엘리먼트가 아니라 CSS Custom Highlight API로 합니다. 그려진 문서는 React의 트리라서, 일치 항목을 감싸는 엘리먼트를 넣으면 React가 만들지 않은 노드가 되기 때문입니다. 이 API가 없는 브라우저에서도 개수와 이동은 동작하고, 바를 닫으면 일치 항목이 선택됩니다. 다음 항목으로 이동해도 포커스는 바에 남고, 바를 닫으면 일치 항목을 선택한 채 포커스가 문서로 돌아갑니다.

:::

::: fw flutter

바는 찾을 원문이 있는 `plain`과 `split`에서만 나옵니다. `preview`에는 찾을 필드가 없어서 버튼도 그리지 않습니다.

:::

## 들여쓰기

원문 화면에서 `Tab`은 들여쓰고 `Shift`+`Tab`은 되돌립니다. 아무것도 선택하지 않았으면 커서 자리에 공백 두 개를 넣습니다. 선택한 영역이 있으면 그 선택이 닿는 줄을 모두 옮기고 선택은 그대로 남겨서, 한 번 더 누를 수 있게 합니다. 선택한 문단을 `Tab`이 지워 버리는 동작은 어느 에디터에도 없습니다.

들여쓰기 폭은 **공백 두 개**이고, 마크다운 문법이 그렇게 요구합니다. 중첩된 목록 항목은 부모의 마커보다 더 들여써야 하는데, `- ` 아래에서는 두 칸이 그 기준입니다. 네 칸을 넣으면 위의 목록이 끝나는 순간 들여쓴 코드 블록이 됩니다. 되돌릴 때는 각 줄 앞에서 탭 하나나 공백 두 개까지를 떼어냅니다. 뗄 것이 없는 줄이 섞여 있어도 오류가 아니며, 나머지 블록은 그대로 움직입니다.

**목록 항목에서 `Tab`을 누르면 위 항목의 하위 항목이 되고**, `Shift`+`Tab`을 누르면 다시 그 항목과 같은 수준으로 돌아옵니다. 공백 두 칸은 글머리 기호의 폭일 뿐 번호의 폭이 아닙니다. `1. `은 세 칸이라, 그 아래 두 칸만 들여쓴 항목은 여전히 바깥 목록의 항목입니다. 그래서 항목은 위 항목의 글이 시작하는 자리까지 들어가고, 되돌릴 때는 자기를 품은 항목이 시작하는 자리로 나옵니다. 항목이 이어지는 줄과 그 안에 중첩된 항목도 함께 움직입니다. 번호는 그대로 두지 않고 다시 셉니다. 다른 항목 안에서 새 목록의 첫 항목이 되면 `1.`이고, 이미 있는 목록에 들어가면 그 목록의 다음 번호이며, 밖으로 나오면 자기를 품었던 항목 다음 번호입니다. 목록의 첫 항목은 들어갈 위 항목이 없으므로 `Tab`을 눌러도 글 속에 공백을 넣지 않고 아무 일도 하지 않습니다. 가장 바깥 목록의 항목도 더 나갈 곳이 없습니다.

그려진 문서에서는 **아직 아무것도 쓰지 않은 항목을 원문에 쓰지 않고 한 단계 안쪽에 붙잡아 둡니다.** CommonMark에서는 빈 항목이 위 항목 안의 새 목록을 시작할 수 없습니다. `- one` 아래에 들여써 쓴 빈 `-`는 `one`에 밑줄을 쳐 제목으로 만들고, `1. one` 아래에 들여써 쓴 빈 `1.`은 `one 1.`처럼 그 항목의 글로 이어 붙습니다. 그래서 `Tab`은 항목을 한 단계 안쪽에 그리기만 하고 원문은 그대로 두며, `Shift`+`Tab`이나 `Enter`는 항목을 다시 밖으로 꺼냅니다. 그 항목에 처음 입력하거나 조합한 글자가 들어갈 때 옮긴 자리의 항목과 글자를 함께 씁니다. 위 항목 안에 이미 있는 목록에 들어가는 빈 항목은 파서가 항목으로 읽으므로 바로 씁니다.

textarea에서 `Tab`을 가로채면 키보드 트랩이 됩니다. 포인터를 쓸 수 없는 사람은 에디터에서 빠져나갈 방법이 없어집니다. 그래서 빠져나가는 키를 따로 두었습니다.

**`Escape`를 누르고 `Tab`을 누르면 포커스가 넘어갑니다.** `Escape` 한 번이 이 상태를 열고, 그다음에 무엇이든 입력하면 다시 닫힙니다. CodeMirror와 Monaco, GitHub의 에디터가 모두 쓰는 규칙이라 그대로 맞췄습니다. 그중 하나라도 써 본 사람은 이미 알고 있는 조작이기 때문입니다. 이 사실은 스크린 리더에도 안내합니다.

그려진 문서는 목록 항목과, 표 셀에서 목록 항목으로 쓴 줄에서만 `Tab`을 잡고 원문 화면과 똑같이 항목을 중첩합니다. 그 밖에서는 포커스를 받는 요소가 하나뿐이라 `Tab`을 누르면 그대로 빠져나갑니다.

## 되돌리기

`Mod`+`Z`로 뒤로, `Mod`+`Shift`+`Z`로 다시 앞으로 갑니다. 윈도우에서 쓰는 `Ctrl`+`Y`도 같은 명령입니다. 되돌리기 기록은 화면마다 따로 두지 않고 **에디터 전체에 하나**만 둡니다.

툴바의 `undo`와 `redo` 버튼도 같은 일을 합니다. 기본 툴바에서 화면 전환 바로 뒤, 좁은 화면에서도 보이는 쪽 끝에 있습니다. 휴대폰에서는 이 버튼이 유일한 되돌리기입니다. 되돌리거나 다시 할 단계가 없으면 비활성화됩니다.

원문 화면만 보면 브라우저의 스택을 쓸 수도 있습니다. `<textarea>`의 되돌리기는 잘 동작합니다. 그런데 그려진 문서는 모든 입력을 거절하는 `contenteditable`이라 브라우저 스택에 항목이 하나도 쌓이지 않습니다. 스택을 둘로 두면 `wysiwyg`에서 한 편집을 `plain`에서 되돌릴 때 절반만 되짚다가 멈춥니다.

저장하는 값은 각 변경 *직전*의 문서와 그때 커서가 있던 자리입니다. 되돌리기가 되돌아가야 하는 상태가 그것이기 때문입니다.

한 번에 이어 친 글자는 키 입력마다 나누지 않고 **한 단계**로 묶습니다. 한 글자씩 되돌아가는 `Mod`+`Z`는 쓸모가 없기 때문입니다. 같은 종류의 변경이 같은 자리에서 짧은 간격으로 이어지는 동안은 앞 단계에 묶입니다. 조합 중인 음절도 같은 타이핑으로 셉니다. 한국어 키보드는 자모마다 앞 글자를 다시 쓰는데, 그 하나하나가 따로 떨어진 편집은 아니기 때문입니다. 줄바꿈은 앞의 묶음을 닫습니다. `Enter` 뒤에 친 글자는 새로 시작한 내용이므로, 되돌리기는 그 사이에서 멈춥니다.

::: fw flutter

**이 절은 React 패키지에만 해당하며, 이 패키지는 되돌리기 기록을 따로 두지 않습니다.** React 패키지가 기록을 두는 이유가 여기서는 생기지 않습니다. 그쪽은 편집 화면이 둘이고 그려진 쪽은 브라우저 스택에 아무것도 남기지 않으므로, 한쪽에서 한 편집을 다른 쪽에서 되돌리려면 기록을 하나로 합쳐야 합니다. 여기서 편집할 수 있는 화면은 `EditableText` 하나이고, `EditableText`는 자기 undo 스택을 갖고 있습니다.

그래서 되돌리기는 이 패키지가 아니라 Flutter가 담당하고, 애플리케이션의 다른 텍스트 필드에서와 똑같이 동작합니다. 타이핑하는 사람이 기대하는 동작이 그것입니다. 키 입력이 아니라 툴바 버튼이 만든 변경을 어떻게 다루는지도 Flutter가 정하며, 바깥에서 값을 써 넣은 다른 `TextEditingController`와 같게 동작합니다. Flutter는 0.5초 안에 이어진 변경을 한 단계로 묶으므로, 변경 직후 잠깐은 `undo` 버튼이 아직 되돌릴 것이 없다고 표시할 수 있습니다.

툴바의 두 버튼은 바로 그 기록을 따라갑니다. `preview`에는 원문이 없으므로 두 버튼 모두 비활성화됩니다.

단축키는 `WidgetsApp`뿐 아니라 원문 필드에도 직접 묶여 있습니다. 이 패키지는 `WidgetsApp`을 요구하지 않는데, 그 밖에 놓인 텍스트 필드는 기록이 있어도 키보드로 따라갈 방법이 없기 때문입니다.

:::

## 붙여넣기

**클립보드에 HTML로 있는 것은 마크다운으로 들어옵니다.** 웹 페이지의 한 부분을 복사해서 어느 화면에든 붙여넣으면 제목은 해시가, 링크는 링크가, 목록은 목록이 됩니다. 워드 프로세서에서 복사해도 마찬가지입니다.

텍스트만 있는 클립보드는 브라우저에 맡깁니다. 브라우저의 붙여넣기가 이미 올바르게 동작하고, 그대로 두면 커서와 스크롤, undo 기록이 그대로 이어집니다.

이것은 렌더러를 거꾸로 돌린 변환이 **아닙니다**. 다른 데서 온 마크업을 한 번 읽어 옮길 수 있는 만큼만 옮기고, 문서가 이 경로를 왕복하지는 않습니다. 그래서 옮기지 못하는 것은 버립니다. `<span style="color: red">`는 그 안의 글자만 남고, `<video>`는 남지 않으며, 목록에 없는 속성은 사라집니다. 모든 URL은 마크다운 링크와 같은 검사를 거치므로, 붙여넣은 `javascript:` 링크는 쓰여 있던 글자 그대로 들어옵니다.

코드 블록 안에서는 붙여넣기가 일반 텍스트로만 동작합니다. 그 안의 내용은 쓰인 글자 그대로이므로, 붙여넣은 제목은 해시로 시작하는 한 줄로 남습니다.

::: fw flutter

이 절은 React 패키지에만 해당합니다. 여기서 클립보드는 플랫폼이 제공하는 내용만 담고 있고, 일반 텍스트를 넘어 HTML 형식이나 이미지를 읽는 일은 위젯이 아니라 플러그인이 맡습니다. 그래서 붙여넣기는 플랫폼의 붙여넣기를 그대로 쓰며, HTML 한 페이지를 마크다운으로 바꾸는 일은 애플리케이션이 문자열을 건네기 전에 하면 됩니다.

:::

## 프레임

에디터도 뷰어와 같은 `frame`과 `toolbarPlacement`를 받고, 뜻도 같습니다. [프레임](./viewer#프레임)을 보세요.

기본값 `box`는 자기 배경이 있고 한쪽 끝을 툴바가 가로지르는 표면입니다. 에디터가 대개 원하는 모습입니다. 입력하는 사람이 자기가 입력하는 곳이 어디서 시작하고 페이지가 어디서 끝나는지 볼 수 있습니다. `floating`은 그것을 내려놓습니다. 쓰는 자리가 곧 페이지인 경우를 위한 값입니다.

<MawyDemo name="editor/floating" flutter="editor/floating" :height="460" />

움직이지 않는 것이 하나 있습니다. 상태 줄은 어느 쪽이든 에디터의 아래 가장자리입니다. 낱말 수는 컨트롤이 아니고 그것으로 정해지는 것도 없습니다. 아래에 뜨는 툴바는 에디터가 아니라 문서에 매달리므로, 둘이 서로 겹치지 않습니다.

## 상태 표시줄

```tsx
<MawyEditor defaultValue={document} status={['position', 'words', 'size']} />
```

`'position'`, `'selection'`, `'lines'`, `'words'`, `'characters'`, `'size'` 중에서 고르고, 아무것도 두지 않으려면 `false`를 넘깁니다.

이 중 둘은 계산 방식을 알아 둘 필요가 있습니다. **글자 수**는 코드 포인트 단위라서 이모지 하나를 한 글자로 셉니다. **단어 수**는 공백으로 나눈 수에 한자·히라가나·가타카나 글자를 각각 더합니다. 이 언어들은 공백 없이 쓰이므로 공백으로만 나누면 한 페이지가 한 단어가 되기 때문입니다. 한국어는 띄어 쓰므로 어절 하나를 한 단어로 셉니다. **크기**는 UTF-8 바이트이고 디스크에 저장될 크기와 같으므로, ASCII가 아닌 글자가 하나라도 들어가면 글자 수와 달라집니다.

## 인터페이스가 쓰는 언어

툴바의 이름표와 툴팁, 화면 전환, 상태 표시줄의 낱말, 찾기 막대, 빈 에디터의 안내문, 스크린 리더에게 주는 모든 문장은 라이브러리가 직접 쓰는 텍스트입니다. 이 텍스트의 언어는 `locale`이 정합니다.

::: fw react

```tsx
<MawyEditor defaultValue={document} locale="ko" />
```

:::

::: fw flutter

```dart
MawyEditor(defaultValue: document, locale: MawyLocale.ko);
```

:::

**영어와 한국어**를 지원하고, 기본값은 `en`입니다. 뷰어가 받는 것과 같은 프롭이며 뜻도 같습니다. 언어를 하나 더할 때 무엇을 해야 하는지를 포함한 나머지 내용은 [인터페이스가 쓰는 언어](./viewer#인터페이스가-쓰는-언어)에 있습니다.

에디터는 이것을 미리보기 안의 뷰어에도 건넵니다. 원문 화면과 그려진 화면이 서로 다른 언어인 일은 없습니다. 그리고 문서에 대해서는 아무 말도 하지 않습니다. 인터페이스가 영어인 에디터에 한국어 문서가 들어 있는 것은 평범한 경우이고, 둘은 일부러 분리된 질문입니다.

## 접근성

편집 화면은 이름표가 붙은 `textbox`이고, 툴바로 할 수 있는 모든 조작은 키보드로도 할 수 있습니다. 툴바는 실제 `toolbar` 역할을 합니다. 탭 정지점은 하나이고, 안에서는 화살표로 움직입니다. `Tab`은 포커스를 옮기지 않고 원문을 들여쓰므로, 빠져나가려면 `Escape`를 누르고 `Tab`을 누릅니다. 이유는 [들여쓰기](#들여쓰기)에 있습니다.
