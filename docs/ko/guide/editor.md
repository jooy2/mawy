# 에디터

::: fw flutter

**이 패키지의 화면은 셋이고**, React 패키지에 있는 `wysiwyg`가 빠져 있습니다. `wysiwyg`는 문서를 그리고 그려진 자리에서 편집하는 화면으로, `contenteditable`에 전적으로 의존합니다. 브라우저가 트리 변경 시도를 컴포넌트에 알리면, 컴포넌트가 그것을 거절하고 대신 마크다운을 고치는 구조입니다. `EditableText`가 문자열을 소유하는 Flutter에는 이런 구조가 없습니다. 텍스트 필드이면서 동시에 문서인 화면을 그리려면 문서 구조를 따로 들고 있는 두 번째 모델이 필요한데, 모델이 둘이면 조금이라도 특이한 문서에서 서로 다른 해석을 내놓습니다.

그래서 화면은 `plain`, `split`, `preview` 셋이고, 그려지는 화면은 뷰어로 남습니다. 이 페이지의 나머지 내용은 거의 전부 여기에도 해당합니다. 명령과 원문에 입히는 색, 아래쪽의 숫자, 글자 찾기가 모두 같은 이름의 같은 함수이고, 코드가 바뀔 때마다 parity 검사가 그 넷을 React 패키지의 것과 대조합니다. 예외는 열기와 저장이며, 그 절에 이유를 적어 두었습니다.

```dart
MawyEditor(
  defaultValue: '# Hello',
  onChange: save,
);
```

:::

Mawy의 에디터는 화면이 여럿인 컴포넌트 하나입니다. `plain`은 마크다운 원문을 텍스트로 편집하고, `preview`는 그려진 문서를 보여주며, `split`은 둘을 한 번에 보여줍니다. 세 화면 모두 같은 값을 보여주고, 이것이 이 설계의 출발점입니다.

<MawyDemo name="editor/basic" flutter="editor/basic" :height="520" />

```tsx
import { MawyEditor } from 'mawy-react';

export function Page() {
  return <MawyEditor defaultValue="# 안녕하세요" onChange={save} />;
}
```

## 여러 화면, 한 값

흔한 구성은 위지윅 에디터에 "소스 모드"를 덧붙이는 것입니다. 이때는 화면을 전환할 때마다 한쪽 모델에서 직렬화하고 다른 쪽 모델로 파싱합니다. 그 왕복에서 반대쪽이 표현하지 못하는 각주와 HTML 블록, 목록 기호의 정확한 표기가 사라지는데, 사라졌다는 사실은 어디에도 표시되지 않습니다.

여기서 문서는 마크다운 문자열 하나이고, 모든 화면은 그것을 보는 방법입니다. 전환은 어느 화면이 마운트되는지를 바꿀 뿐 아무것도 다시 직렬화하지 않으므로, 그대로 들어온 문서는 그대로 나갑니다.

## 모드

| 모드        | 편집 가능 | 보여주는 것               |
| ----------- | --------- | ------------------------- |
| `'plain'`   | 예        | 마크다운 원문             |
| `'preview'` | 아니오    | 그려진 문서               |
| `'split'`   | 예        | 둘을 나란히               |
| `'wysiwyg'` | 일부      | 그려진 문서를 그 자리에서 |

툴바가 어느 것을 제시할지는 `modes`가 정하고, 하나만 주면 전환 컨트롤 자체가 사라집니다.

```tsx
<MawyEditor defaultValue={document} modes={['plain']} />
```

<MawyDemo name="editor/source" />

`mode` / `defaultMode` / `onModeChange`는 익숙한 그 셋입니다. `mode`를 넘기면 애플리케이션이 정하고, `defaultMode`를 넘기면 에디터가 갖고 있으며, `onModeChange`는 어느 쪽이든 호출됩니다.

`split`에서 미리보기는 파일의 위치 비율이 아니라 **블록**을 기준으로 스크롤합니다. 원문 맨 위에 있는 줄이 미리보기 맨 위에 올 블록을 정하고, 그 사이는 블록에서 블록으로 곧게 이어집니다. 비율로는 맞출 수 없습니다. 코드 블록은 원문 예순 줄이 화면에서도 예순 줄이지만 양옆의 산문은 그렇지 않아서, 비율로 맞추면 곧바로 어긋납니다.

**두 판 사이의 바는 잡고 끌 수 있습니다.** 5:5 비율이 언제나 알맞지는 않습니다. 넓은 창에서 초고를 읽을 때는 미리보기가, 글을 쓸 때는 원문이 더 넓은 편이 낫습니다. 끌어도 되고, 포커스를 준 뒤 화살표를 써도 됩니다. `Shift`는 더 큰 걸음, `Home`과 `End`는 양 끝, `Enter`나 더블 클릭은 다시 5:5입니다. 양쪽 가장자리에는 한참 못 미쳐 멈추는데, 폭이 0까지 밀린 판은 다시 끌어낼 수 없기 때문입니다.

바의 위치는 읽는 사람이 화면을 보는 동안만 유지되고, 여기에 해당하는 프롭은 없습니다. 판의 경계는 스크롤 위치와 같은 종류의 값이라 저장 대상으로 두지 않았습니다. 저장할 만한 값은 문서이고, 그것은 `value`와 `onChange`가 다룹니다.

두 판이 위아래로 쌓이는 너비에서는 바를 그리지 않습니다.

**미리보기는 읽기 전용이라 거기서는 아무것도 편집하지 않습니다.** 미리보기를 클릭해도 원문의 커서는 움직이지 않습니다. 이것이 이 판과 `wysiwyg`의 차이입니다. 그려진 문서를 편집하는 화면은 `wysiwyg` 하나입니다. 왼쪽에서 글을 쓰는 동안 오른쪽 클릭이 커서를 옮기면 어느 쪽에서 쓰고 있는지가 모호해집니다. 링크와 체크박스, 코드 블록의 복사 버튼은 그대로 동작하고, 나머지는 일반 페이지처럼 선택하고 복사할 수 있습니다.

## 원문 편집 화면

::: fw react

진짜 `<textarea>`이고, 같은 글자를 색칠한 사본이 그 바로 아래 정확히 겹쳐 있습니다.

이 구성은 의도한 설계입니다. textarea는 직접 다시 만들기 어렵고 없으면 곧바로 티가 나는 기능을 이미 갖고 있습니다. **IME**(한글은 자모 단위로 조합되고, 조합을 가로채는 에디터는 글자를 잃습니다), 모바일 키보드, 자동 수정, 맞춤법 검사, 플랫폼의 모든 텍스트 선택 제스처가 그렇습니다. textarea가 못 하는 일은 색을 입히는 것뿐이므로, 글자를 투명하게 만들고 커서와 선택 영역만 남긴 뒤 뒤쪽 레이어가 같은 글자를 색으로 그립니다.

글자가 놓일 자리를 결정하는 값은 스타일시트에 한 번만, 두 레이어 모두에 선언됩니다. 글꼴과 크기, 줄 간격, 자간, 탭 크기, 줄바꿈, 그리고 왼쪽 시작점을 정하는 패딩이 그렇습니다. 이 선언이 두 레이어를 어긋나지 않게 맞춥니다. 에디터의 고정폭 서체를 컴포넌트가 정하지 않고 `--mawy-font-mono`에서 읽는 것도 같은 이유입니다.

육백 줄을 넘어가는 문서는 한 줄에 한 행씩 그리지 않습니다. 아래쪽 사본을 덩어리로 나누고, 화면 근처의 덩어리만 문법을 색칠한 행으로 그립니다. 나머지는 같은 글자를 한 덩이의 텍스트로 담는데, 높이는 똑같고 요소 수는 훨씬 적습니다. 빠지는 글자가 없으므로 브라우저의 찾기는 여전히 문서 전체에 닿고, 인쇄하면 전부 종이에 올라가며, 사본의 높이도 필드와 정확히 같습니다. 색칠이 따라오지 못할 만큼 빠르게 스크롤하면 한 프레임 동안 색 없는 글자가 제자리에 보이고, 빈자리가 남지는 않습니다.

:::

::: fw flutter

`EditableText` 하나이고, 그 자리에서 색이 입혀집니다.

이 라이브러리에서 Flutter 쪽이 더 쉬운 유일한 자리입니다. 브라우저는 텍스트 필드 *안*을 색칠할 방법을 주지 않아서, React 패키지는 두 레이어를 그린 뒤 서로 어긋나지 않게 맞춰야 합니다. `TextEditingController`는 그릴 스팬을 그대로 받으므로 `MawySourceController`가 그것만 넘기면 됩니다. 레이어가 하나여서 맞출 그리드도 없고, 필드가 플랫폼의 것이므로 커서와 선택 영역도 플랫폼 동작 그대로입니다.

그 필드에 딸려 오지 않는 것이 포인터 처리입니다. 맨 `EditableText`는 탭한 자리에 캐럿을 놓고 거기서 멈춥니다. 드래그해도 선택되지 않고, 더블 탭은 단어를 잡지 않으며, 길게 눌러도 핸들이 뜨지 않습니다. 그 전부를 `TextSelectionGestureDetectorBuilder`가 처리하고, `TextField`가 자기 필드에 두르는 것을 이 위젯도 자기 필드에 두릅니다. 이 빌더는 Material이 아니라 `package:flutter/widgets.dart`에 있으므로, 이것을 써도 Material을 함께 들이지 않습니다.

두 가지는 이 패키지가 아니라 플랫폼이 제공하고, 둘 다 Flutter가 아닌 Cupertino에 있습니다. iOS에서 세게 눌렀을 때 뜨는 돋보기와 선택 툴바입니다. 시작만 하고 끝맺지 못하는 제스처를 남기지 않으려고 force press는 꺼 두었습니다.

여기서도 `lineNumbers`로 거터를 끕니다. 기본은 켜짐이고, 번호는 같은 텍스트를 한 번 더 배치하지 않고 필드가 이미 배치해 둔 줄에서 그립니다. 그래서 줄바꿈된 줄은 화면에서 두 행이고 옆에서는 번호 하나입니다. 배치가 하나뿐이라 둘이 어긋나지 않습니다.

육백 줄을 넘어가는 문서는 보이는 곳만 색칠하고, 나머지는 쓰인 글자 그대로 넘깁니다. 필드는 어느 쪽이든 문서 전체를 배치합니다. 레이어가 하나뿐인 구조에서는 피할 수 없는 비용이면서, 커서와 선택 영역과 모든 측정값이 그대로 유지되는 이유이기도 합니다. 여기서 아끼는 비용은 키 입력마다 모든 줄을 읽는 일입니다. 색칠할 구간은 프레임이 끝난 뒤에 정해지므로, 그보다 빠르게 스크롤하면 다음 프레임까지 색 없는 글자가 제자리에 보입니다.

:::

문법 강조는 Mawy 파서의 토큰 이름을 쓰지만 파서 자체를 쓰지는 않습니다. 타이핑 중인 줄은 대부분 절반만 쓰인 상태여서, `**bold`가 닫히기를 기다렸다가 반영하는 하이라이터는 키 입력마다 깜빡입니다. 그래서 한 줄씩 근사적으로 읽고, 아직 닫히지 않은 마커는 그대로 둡니다.

::: fw react

`lineNumbers`로 거터를 끕니다. 기본은 켜짐이고, 두 레이어가 하나의 그리드를 공유하므로 줄바꿈된 텍스트에서도 번호가 어긋나지 않습니다.

:::

## 문서 편집 화면

`wysiwyg`는 문서를 그리고, 그려진 그 자리에서 편집합니다. 동작을 짐작하기 쉬운 화면이라 아래에 하나씩 적어 둡니다.

<MawyDemo name="editor/document" />

뒤에 두 번째 모델은 없습니다. 화면에 보이는 것은 마크다운을 그린 결과이고, 기준이 되는 값은 마크다운 문자열입니다. 모든 키 입력을 거절해 그 문자열을 고치는 편집으로 바꾸고, 바뀐 문자열에서 문서를 다시 그립니다. 브라우저가 바꾸려던 트리를 되읽지 않습니다. 이 패키지에 DOM → 마크다운 직렬화기는 없고 앞으로도 두지 않습니다. 구현이 둘이면 조금이라도 특이한 문서에서 서로 다른 해석을 내놓기 때문입니다.

**전환 스위치가 처음으로 내놓는 화면입니다.** 링크의 목적지와 그려지는 원시 HTML은 캐럿이 들어가면 쓰인 글자 그대로 펼쳐지므로, 이 화면에는 캐럿이 갈 수 없는 자리가 없습니다. 이 두 가지가 해결되기 전까지는 기본 목록에 넣지 않았습니다. 이 화면을 제공하지 않으려면 `modes`에서 빼면 됩니다.

```tsx
<MawyEditor defaultValue={document} modes={['plain', 'split', 'preview']} />
```

되는 일은 이렇습니다. 문단과 제목, 목록 항목, 인용, 표의 셀, 코드 블록처럼 **글자가 들어갈 수 있는 곳이면 어디서나** 타이핑과 삭제가 됩니다. 선택 영역 대체와 `Shift`+`Enter` 하드 브레이크, 타이핑하는 자리에서 곧바로 서식이 되는 약칭, 툴바의 모든 명령도 됩니다. 툴바 명령에는 새로 필요한 코드가 없었습니다. 명령이 원문과 선택만 받는 순수 함수라서 화면에 따라 달라지는 코드가 없습니다.

편집은 파일에 쓰인 글자가 아니라 **화면에 그려진** 글자를 기준으로 동작하고, 이것이 이 화면의 핵심입니다. `**bold**`에서 `bold` 뒤에 놓인 커서 앞에는 파일에서는 별표가, 화면에서는 `d`가 있습니다. 거기서 `Backspace`는 `d`를 지웁니다. 이미지와 하드 브레이크는 통째로 지워집니다. 읽는 사람에게는 각각 한 글자이고, 텍스트만 훑을 때는 보이지 않는 요소입니다.

화면이 그릴 수 없는 자리의 커서도 같은 문제입니다. 마크다운은 줄 끝의 공백을 남기지 않으므로, 문단 끝에 입력한 공백은 파일에는 있고 화면에는 그려지지 않습니다. 커서는 그 앞으로 돌아올 수밖에 없습니다. 그래서 커서가 **있으려던** 자리를 실제로 놓인 자리와 함께 기억해 둡니다. 다음 글자가 공백 뒤로 가게 하기 위해서이고, 이것이 없으면 `One two`를 한 단어씩 칠 수조차 없습니다. 이때 `Backspace`는 커서 앞에 지울 그려진 글자가 없으므로 그 공백을 지웁니다.

`Enter`는 어느 컨테이너에서 눌렸는지에 따라 다르게 동작합니다. 컨테이너마다 빈 줄의 뜻이 다르기 때문입니다.

| 어디서       | `Enter`가 하는 일                                              |
| ------------ | -------------------------------------------------------------- |
| 블록 사이    | 빈 줄                                                          |
| 목록 항목 안 | 기호를 이어받은 새 항목. 아직 비어 있는 항목에서는 기호를 없앰 |
| 인용 안      | 문단을 끝냄. 인용을 이어가려면 *빈 인용 줄*이 필요합니다      |
| 코드 블록 안 | 줄바꿈 하나, 그게 전부                                         |
| 표 안        | 아무것도. 행이 곧 줄이고, 파일에 둘째 행이 갈 자리가 없습니다  |

블록 맨 앞에서 누른 `Backspace`는 그 블록을 앞 블록과 합칩니다. 목록 항목 둘이 이어지고, 문단이 위의 제목과 합쳐집니다. 합치지 않는 경우가 둘 있습니다. 표의 셀을 옆 셀과 합치면 사이의 파이프가, 코드 블록을 위의 블록과 합치면 펜스가 사라집니다.

문단 끝에서 누른 `Enter`는 파일만으로 화면 상태를 표현할 수 없는 유일한 자리입니다. 마크다운에 빈 문단은 없습니다. 빈 줄 하나도 빈 줄 둘도 똑같이 두 블록을 가릅니다. 그래서 이 한 자리에 한해, 커서가 안에 있는 동안만 빈 문단을 그립니다. 무엇이든 입력되는 순간 그 문단은 실제 문단이 됩니다.

조합 입력(IME)만은 **거절할 수 없어서** 반대로 다룹니다. 조합은 통째로 브라우저에 맡깁니다. `compositionstart`부터 `compositionend`까지는 아무것도 막지 않고 다시 그리지도 않습니다. 조합이 끝나면 그 텍스트를 직전 내용과 비교해서, 해당 위치의 마크다운에 차이만 반영합니다.

조합을 거절하면 조합 자체가 되지 않습니다. 한글은 자모 하나씩 조합되므로, 그 하나하나를 막는 에디터에서는 한국어를 쓸 수 없습니다. `Enter`를 누르고 빈 문단에 바로 조합해 넣는 것도 됩니다. 들어갈 텍스트가 아직 없을 때는 블록 자체를 기억해 둡니다.

**캐럿이 들어간 링크나 이미지, 원시 HTML은 목적지까지 포함해 쓰인 글자 그대로 펼쳐지고**, 캐럿이 떠나면 다시 원래 모습으로 그려집니다. 에디터가 포커스를 가진 동안에만 그렇습니다. 링크로 시작하는 문서를 아직 건드리지도 않은 사람에게 대괄호부터 보여주지 않기 위해서입니다. 그려진 `<a>`는 링크 텍스트만 화면에 올리고 `(url)`은 올리지 않으므로, 펼치기 전에는 목적지를 편집할 자리가 화면에 없었습니다. 툴바가 넣는 `[](url)`도 덮어 쓸 수 없는 자리표시자였습니다. 펼쳐 놓으면 그 글자가 곧 원문이고, 이 화면의 모든 규칙이 그대로 적용됩니다. 캐럿이 놓인 자리는 감추지 않고 드러냅니다. 링크가 링크를 만드는 글자로 바뀐 것은 눈에 보여야 하는 변화입니다.

**마커까지만 쓰이고 그 뒤가 아직 비어 있는 블록도 같은 방식으로 펼쳐집니다.** `#` 하나는 CommonMark에서 빈 제목이고, 파서도 그렇게 읽습니다. 그런데 빈 제목은 글자를 하나도 그리지 않아서, 방금 타이핑한 `#`이 타이핑하는 동안 화면에서 사라집니다. 문장 안에 `#` 기호를 쓰려던 사람은 만들지도 않은 제목을 되돌려야 합니다. 펼쳐 놓으면 화면에도 `#`이 남고, 공백을 한 번 더 치면 제목이 됩니다. `-`, `>`, `1.`, `- [ ]`도 같습니다. 글자가 사라진 자리에 글머리 기호나 세로줄, 번호, 체크박스만 남습니다. 펼치는 대상은 그런 블록 중 가장 바깥쪽입니다. 빈 항목 하나를 든 목록에서는 항목이 아니라 목록을 펼칩니다. 직접 쓴 `-` 옆에 글머리 기호가 또 그려져도 나아지지 않기 때문입니다.

**글자가 아니라 요소로 그려지는 원시 HTML도 같은 방식으로 펼쳐집니다.** `sanitize`와 `raw` 양쪽에서 그렇습니다. `dangerouslySetInnerHTML`로 페이지에 닿은 마크업은 React가 내부를 알지 못하고 되돌릴 수도 없어서, 그려진 형태에는 캐럿이 들어갈 자리가 없습니다. 펼쳐 놓으면 그 자리가 생깁니다. 기본값인 `escape`에서는 처음부터 일반 텍스트이므로 다른 텍스트와 똑같이 편집됩니다.

## 입력 규칙

그려진 문서에서는 타이핑한 약칭이 그 자리에서 곧바로 그것이 뜻하는 서식이 됩니다. `# `은 제목, `- `과 `* `은 글머리 기호, `1. `은 번호, `> `은 인용, `- [ ] `은 체크박스입니다.

**이 대부분은 따로 구현한 기능이 아닙니다.** 키 입력마다 마크다운에서 문서를 다시 그리므로, 문단 맨 앞의 `# `은 공백이 닿는 순간 _이미_ 제목입니다. 파서가 그렇게 읽고 화면이 따라 그릴 뿐입니다. 설정하거나 끌 항목도 없습니다.

공백이 닿는 순간이고, 그전에는 바뀌지 않습니다. `#` 하나는 제목 안에 무언가가 들어가기 전까지 쓰인 글자 그대로 그려집니다. 이것은 입력 규칙이 아니라 [문서 편집 화면](#문서-편집-화면)이 속이 빈 블록을 펼쳐 두는 동작이고, 덕분에 문장 안에 `#`을 타이핑할 수 있습니다.

따로 적어 둔 규칙은 둘입니다. 마커 하나가 손대지 않은 텍스트의 뜻까지 바꾸는 경우입니다.

- **백틱 셋은 펜스를 열고, 펜스는 닫는 것이 나올 때까지 이어집니다.** 문서 중간에서 그것을 타이핑하면 아래에 있는 모든 것이 코드 블록 안에 들어가고, 닫는 펜스를 타이핑할 때까지 거기 남습니다. 그래서 펜스는 _닫힌 채로_ 열립니다. 커서는 둘 사이로 가고 그 줄에 있던 것은 안으로 들어갑니다. 코드 블록 버튼이 하는 일과 같습니다. 목록 항목이나 인용 안에서는 새로 만드는 두 줄이 그 컨테이너의 접두사를 함께 가져갑니다. 그러지 않으면 펜스가 자기를 연 항목 바깥에서 닫힙니다.
- **구분선에는 글자가 없습니다.** 자기 줄에 홀로 있는 `---`는 셋째 하이픈이 닿는 순간 구분선이 되고, 그러면 커서가 글자를 하나도 그리지 않는 블록 안에 놓여 화면에서 자리를 잃습니다. 그래서 구분선 아래에 이어서 타이핑할 빈 줄을 하나 만듭니다. `***`, `___`, `- - -`도 같습니다. 글이 이어지고 있는 줄 아래의 `---`는 건드리지 않습니다. 그 자리에서는 문단의 밑줄, 곧 setext 제목이고, 파서가 읽은 대로가 맞습니다.

코드 블록 안에서는 이 중 어느 것도 일어나지 않습니다. 그 안에 있는 모든 것은 쓰인 글자 그대로이기 때문입니다.

줄바꿈을 만드는 규칙은 되돌리기 스택에서 한 단계를 따로 차지합니다. 그래서 규칙이 발동한 직후의 `Mod`+`Z`는 주변의 타이핑 전체가 아니라 그 규칙을 일으킨 글자만 돌려줍니다.

원문 화면에는 입력 규칙이 없습니다. 타이핑한 글자가 곧 문서이고, 줄 맨 앞의 `# `은 그 자체로 이미 제목입니다.

## 서식

툴바의 모든 버튼은 키보드 단축키도 함께 가진 명령을 실행합니다. 툴바로만 실행할 수 있는 명령은 두지 않았습니다. 그런 명령이 있으면 포인터 없이는 에디터를 쓸 수 없기 때문입니다.

|                         |                                  |
| ----------------------- | -------------------------------- |
| `Mod` + `B`             | 굵게                             |
| `Mod` + `I`             | 기울임                           |
| `Mod` + `Shift` + `X`   | 취소선                           |
| `Mod` + `E`             | 코드                             |
| `Mod` + `K`             | 링크                             |
| `Mod` + `1` / `2` / `3` | 제목 1, 2, 3                     |
| `Mod` + `0`             | 본문                             |
| `Mod` + `F`             | 찾기와 바꾸기                    |
| `Mod` + `S`             | 저장                             |
| `Tab` / `Shift` + `Tab` | 들여쓰기, 내어쓰기               |
| `Mod` + `Z`             | 되돌리기                         |
| `Mod` + `Shift` + `Z`   | 다시 하기. `Ctrl` + `Y`도 됩니다 |
| `Enter`                 | 목록 기호를 다음 줄로            |

`Mod`는 그 기기의 Command 또는 Control입니다. 어느 쪽인지 추측하지 않고 둘 다 받습니다.

::: fw flutter

이 표에서 이 패키지가 처리하지 않는 줄은 `Mod`+`S` 하나입니다. 저장할 곳이 없어서이고, 자세한 내용은 [열기와 저장](#열기와-저장)에 있습니다. 되돌리기는 이 패키지가 아니라 플랫폼이 담당하며([되돌리기](#되돌리기)), 나머지는 모두 같습니다.

:::

모든 명령은 **토글**입니다. 굵은 글자에 `Mod`+`B`를 누르면 굵기가 풀리고, 지금 걸려 있는 서식은 툴바에서 버튼이 눌린 모습으로 표시됩니다. 마커는 쌓이지 않고 서로를 대체하므로, 순서 있는 목록을 순서 없는 목록으로 바꾸면 `- 1. 항목`이 되지 않고 순서 없는 목록이 됩니다.

목록 항목 끝에서 `Enter`를 누르면 기호가 다음 줄로 이어지고 순서 있는 목록은 번호가 올라갑니다. 아직 비어 있는 항목에서 한 번 더 누르면 기호를 하나 더 만들지 않고 없앱니다. 이 동작이 없으면 목록에서 빠져나올 때마다 에디터가 방금 넣어 준 기호를 직접 지워야 합니다.

편집은 브라우저 자신의 텍스트 삽입 명령으로 들어갑니다. 커서와 스크롤 위치, 진행 중인 조합을 있던 자리에 그대로 두기 때문입니다. 값을 직접 써 넣는 방식은 그중 어느 것도 보장하지 않습니다. 되돌리기는 더 이상 이 선택의 이유가 아니며, 그 내용은 아래에 절을 따로 두었습니다.

`toolbar`는 `true`, `false`, 또는 그릴 컨트롤과 그릴 순서를 받습니다.

```tsx
<MawyEditor defaultValue={document} toolbar={['mode', 'separator', 'bold', 'italic', 'link']} />
```

| 항목 |  |
| --- | --- |
| `'mode'` | 화면 전환 |
| `'heading'` | 제목 1·2·3과 본문 메뉴 |
| `'bold'`, `'italic'`, `'strikethrough'`, `'code'`, `'link'`, `'image'` | 인라인 서식 |
| `'quote'`, `'bulletList'`, `'orderedList'`, `'taskList'`, `'codeBlock'`, `'rule'` | 블록 |
| `'find'` | 찾기 바를 엽니다. [찾기](#찾기)를 보세요 |
| `'open'`, `'save'` | 마크다운 파일을 읽고 내보냅니다. [열기와 저장](#열기와-저장)을 보세요 |
| `'colorScheme'` | 라이트·다크·시스템 설정 |
| `'separator'` | 묶음을 나누는 가는 선 |

::: fw react

**버튼을 다 담기에 좁은 바는 들어가는 만큼만 두고 나머지를 끝의 메뉴에 넣습니다.** 뒤에서부터 묶음 단위로 옮기고, 묶음은 구분선으로 나눕니다. 그래서 `toolbar`의 순서를 바꾸면 무엇이 먼저 밀려날지도 함께 바뀝니다. 화면 전환은 어느 너비에서도 메뉴로 들어가지 않습니다. 글 쓰는 사람이 가장 자주 누르는 컨트롤이기 때문입니다.

툴바가 자기 너비를 재서 결정하며, 설정할 수 있는 값은 아닙니다. 이전에는 두 번째 줄로 넘겼는데, 툴바 위의 레이아웃에 그 줄이 들어갈 자리가 없었습니다. 버튼이 늘어나는 동안 바의 높이는 그대로여서 아랫줄이 바 밖으로 나갔습니다.

:::

::: fw flutter

**버튼을 다 담기에 좁은 바는 옆으로 스크롤합니다.** 메뉴로 숨기지 않습니다. 줄이 `SingleChildScrollView` 안에 있어서 들어가지 않는 버튼은 한 번 밀면 나오고, 줄을 따라 포커스를 옮기는 화살표도 그 버튼을 화면 안으로 끌어옵니다.

React 패키지는 같은 문제를 바 끝의 메뉴로 해결하며, 이 차이는 플랫폼에서 옵니다. 터치 스크린에서는 손가락으로 미는 줄이, 포인터를 쓰고 바를 옆으로 끌 방법이 뚜렷하지 않은 페이지에서는 메뉴가 자연스럽습니다.

:::

## 이미지

이미지가 들어오는 경로는 셋입니다. 이미지가 URL을 이미 가진 경우와 아직 없는 경우를 나누어 다루기 때문입니다.

**툴바의 이미지 버튼**은 `![](url)`을 쓰고 그 목적지를 선택해 둡니다. 바로 덮어쓰면 됩니다. 링크 버튼 앞에 `!` 하나가 붙은 것이고, 규칙도 같습니다. URL을 선택하고 누르면 그것이 목적지가 되고, 그 밖의 것을 선택하고 누르면 그것이 이미지를 보지 못하는 독자에게 주는 설명이 됩니다. 애플리케이션에서 받아야 할 것이 없어서 언제나 쓸 수 있습니다.

**웹 페이지의 일부로 붙여넣거나 끌어다 놓은 이미지**는 이미 가지고 있던 URL 그대로 들어옵니다. 이것은 이미지 기능이 아니라 [붙여넣기](#붙여넣기)가 마크업을 읽은 결과입니다. 그림이 이미 웹에 있으므로 업로드하지 않습니다.

**파일**은 다릅니다. 클립보드의 스크린샷이나 바탕화면에서 끌어온 이미지는 그 바이트를 저장할 곳이 있어야 하는데, 그 한 가지는 이 라이브러리가 정할 수 없습니다. 오브젝트 스토리지에 올릴지, 업로드 엔드포인트로 보낼지, `data:` URI로 문서 안에 넣을지는 비용과 정책이 걸린 선택이라 애플리케이션이 정해야 합니다. 그래서 프롭으로 두었습니다.

```tsx
<MawyEditor
  defaultValue={document}
  onUploadImage={async (file) => {
    const { url } = await save(file);

    return url;
  }}
/>
```

쓸 URL을 돌려주면 되고, 그 주위에 무엇을 쓸지까지 정하려면 `{ url, alt, title }`을 돌려줍니다. 그러지 않으면 확장자를 뗀 파일 이름이 설명이 됩니다. 예외를 던지거나 아무것도 답하지 않으면 에디터는 이미지를 넣지 못했다고 말하고 아무것도 쓰지 않습니다.

**`onUploadImage`가 없으면 끌어다 놓은 파일은 거절됩니다.** 일부만 넣지도 않고 브라우저에 넘기지도 않습니다. 에디터가 그 드롭을 받아 아무것도 쓰지 않고, 문서 아래 줄에 그 사실을 표시합니다. 의도한 기본값입니다. 남은 선택지는 2 MB짜리 스크린샷을 `data:` URI로 바꿔 문서 안에 넣는 것뿐이기 때문입니다.

이미지는 놓은 자리에 들어갑니다. 끌어다 놓으면 포인터를 놓은 지점으로, 붙여넣으면 커서 자리로 갑니다. 여러 파일을 한 번에 놓으면 업로드는 하나씩 이어서 하고, 편집은 마지막에 **한 번**만 합니다. `Mod`+`Z` 한 번으로 방금 놓은 파일 전체를 되돌리게 하기 위해서입니다.

## 미리보기의 코드 색

`highlight`는 미리보기 안의 뷰어로 그대로 전달됩니다. `split`과 `preview` 화면은 [뷰어와 같은 방식](./viewer#코드-블록에-색-입히기)으로 코드에 색을 입힙니다. 필요할 때 불러오는 지연 로딩 형태도 그대로 쓸 수 있고, 그 편을 권합니다.

```tsx
<MawyEditor
  defaultValue={document}
  highlight={() => import('mawy-react/highlight').then((module) => module.mawyHighlighter)}
/>
```

**그려진 문서에는 색을 입히지 않고**, 앞으로도 그럴 예정입니다. 원문 화면에는 마크다운 전용 하이라이터가 따로 있습니다. 그려진 화면에서는 커서 위치를 항상 원문으로 되돌릴 수 있어야 하는데, 코드 블록 안의 글자를 다르게 해석하는 구현을 하나 더 두면 그 대응이 어긋납니다.

## 열기와 저장

`open`은 마크다운 파일을 에디터로 읽어 들이고, `save`는 문서를 다시 내보냅니다. `Mod`+`S`로도 저장합니다. 브라우저의 `Mod`+`S`는 페이지를 저장하는 기능인데, 에디터에서 글을 쓰던 사람이 그 키로 기대하는 동작은 문서 저장이기 때문입니다.

```tsx
<MawyEditor
  defaultValue={document}
  onSave={(value, name) => api.put(`/documents/${name}`, value)}
/>
```

`onSave`가 없으면 텍스트를 다운로드로 내보냅니다. Chromium에만 있는 File System Access API 대신 `download` 속성을 단 앵커를 씁니다. 어떤 브라우저에서만 동작하는 저장은 모든 브라우저에서 같게 동작하는 저장보다 못하기 때문입니다. `onSave`가 있으면 아무것도 내려받지 않고, 저장할 이름과 문서를 애플리케이션에 건넵니다.

파일을 열어 둔 상태라면 그 파일의 이름을 쓰고, 아니면 **문서의 첫 제목**을 씁니다. 폴더에서 파일 목록을 볼 때 읽기 좋은 이름이기 때문입니다. 파일 시스템이 받지 않는 글자는 떼어내고, 가져올 제목이 없으면 `document.md`가 됩니다.

`open`에 단축키를 두지 않은 것은 의도적입니다. 브라우저의 `Mod`+`O`를 그대로 두는 편이 낫고, 파일 열기는 글을 쓰는 중간에 자주 하는 동작이 아닙니다.

**에디터에 놓은 파일은 문서가 아니라 이미지로 처리합니다.** 끌어다 놓기가 이미 이미지가 들어오는 경로인 것도 이유지만, 더 큰 이유는 따로 있습니다. 파일이 떨어졌다는 이유로 쓰고 있던 문서를 갈아치우면 작업 내용이 사라집니다. 뷰어는 잃을 내용이 없어서 놓인 파일을 바로 열지만, 에디터에서는 그렇게 하지 않습니다.

그래도 그 드롭은 에디터가 처리합니다. **받지 않을 파일도 브라우저에 넘기지 않고 거절합니다.** 브라우저에 넘기면 그 파일을 페이지로 열어 버려서, 문서와 되돌리기 기록과 커서가 탭과 함께 사라집니다. 문서 아래 줄에 무슨 일이 있었는지와 어느 컨트롤을 써야 하는지 표시합니다.

**`fileDrop`은 그 규칙을 끕니다.** 이미 문서를 담고 있는 에디터가 아니라, 비어 있는 상태로 시작해서 파일을 _가져오는_ 에디터를 위한 옵션입니다. 켜면 끌어다 놓은 `.md`가 문서로 열리고, 비어 있는 미리보기 자리에 뷰어의 빈 상태가 그대로 들어가 파일 선택기를 보여줍니다. `onUploadImage`가 주어져 있으면 끌어다 놓은 이미지는 그대로 이미지로 처리하고, 그때까지 거절하던 파일만 문서로 읽습니다.

::: fw flutter

이 절은 React 패키지에만 해당합니다. 여기서 파일을 열고 되돌려 쓰는 일은 애플리케이션이 맡습니다. 파일 선택기는 위젯이 아니라 플러그인이고, 앱이 어떤 플러그인을 쓰는지는 마크다운 에디터가 정할 문제가 아닙니다. `MawyEditorToolbarItem`에 `open`과 `save`가 없는 것도 같은 이유입니다. `onChange`가 문서를 건네고, 그 문서를 어디에 저장할지는 애플리케이션이 정합니다.

:::

## 찾기

`Mod`+`F`가 원문 위에 찾기 바를 열고, 툴바의 `find` 버튼도 같은 일을 합니다. `Enter`는 다음 결과로, `Shift`+`Enter`는 이전 결과로 가고, `Escape`는 바를 닫고 포커스를 문서에 돌려줍니다.

::: fw react

브라우저의 찾기가 여기까지 닿지 못해서 따로 두었습니다. **어떤 브라우저도 `<textarea>` 안의 글자는 찾지 않는데**, 원문 화면이 바로 `<textarea>`입니다. 이 라이브러리는 다른 모든 곳에서 플랫폼이 이미 하는 일을 플랫폼에 맡기고, 여기가 유일한 예외입니다.

:::

::: fw flutter

이유는 React 패키지와 같습니다. **플랫폼의 찾기는 글이 놓인 화면까지만 닿고 텍스트 필드 *안*까지는 닿지 않는데**, 원문 화면이 바로 그 텍스트 필드입니다. 이 라이브러리는 다른 모든 곳에서 플랫폼이 이미 하는 일을 플랫폼에 맡기고, 여기가 유일한 예외입니다.

그 아래의 계산은 React 패키지와 함수 단위로 같습니다. `findMatches`, `matchFrom`, `replaceMatch`, `replaceAll`이 그렇습니다. 코드가 바뀔 때마다 `tool/parity.dart`가 `tool/searches.json`으로 둘을 대조합니다. `aaaa` 안의 `aa`를 두 개로 셀지 세 개로 셀지는 선택이 필요한 문제이고, 두 패키지가 같은 선택을 합니다.

:::

한 줄 안에서 선택한 글자가 있으면 바가 열릴 때 그 글자가 이미 상자에 들어 있습니다. 대개 그것이 지금 찾으려는 글자이기 때문입니다.

**정규식이 아니라 일반 텍스트로 찾습니다.** 마크다운 문서에는 `*`, `[`, `.`, `+`가 자주 나오는데, 이런 글자를 정규식으로 해석하면 `(` 하나에 문법 오류가 납니다. 대신 대소문자 구분 스위치를 두었고, 실제로 필요한 것은 그쪽입니다.

바꾸기와 모두 바꾸기는 두 번째 줄에 있습니다. 모두 바꾸기는 원래 문서를 한 번만 훑습니다. 그래서 `a`를 `aa`로 바꿔도 각 `a`가 한 번씩만 바뀌고, 방금 넣은 글자를 다시 찾지 않습니다.

::: fw react

바는 찾을 원문이 있는 `plain`과 `split`에서만 나옵니다. `preview`와 `wysiwyg`에서는 문서가 엘리먼트로 그려져 있어서 브라우저 자신의 찾기가 동작합니다.

:::

::: fw flutter

바는 찾을 원문이 있는 `plain`과 `split`에서만 나옵니다. `preview`에는 찾을 필드가 없어서 버튼도 그리지 않습니다.

:::

## 들여쓰기

원문 화면에서 `Tab`은 들여쓰고 `Shift`+`Tab`은 되돌립니다. 아무것도 선택하지 않았으면 커서 자리에 공백 두 개를 넣습니다. 선택한 영역이 있으면 그 선택이 닿는 줄을 모두 옮기고 선택은 그대로 남겨서, 한 번 더 누를 수 있게 합니다. 선택한 문단을 `Tab`이 지워 버리는 동작은 어느 에디터에도 없습니다.

들여쓰기 폭은 **공백 두 개**이고, 마크다운 문법이 그렇게 요구합니다. 중첩된 목록 항목은 부모의 마커보다 더 들여써야 하는데, `- ` 아래에서는 두 칸이 그 기준입니다. 네 칸을 넣으면 위의 목록이 끝나는 순간 들여쓴 코드 블록이 됩니다. 되돌릴 때는 각 줄 앞에서 탭 하나나 공백 두 개까지를 떼어냅니다. 뗄 것이 없는 줄이 섞여 있어도 오류가 아니며, 나머지 블록은 그대로 움직입니다.

textarea에서 `Tab`을 가로채면 키보드 트랩이 됩니다. 포인터를 쓸 수 없는 사람은 에디터에서 빠져나갈 방법이 없어집니다. 그래서 빠져나가는 키를 따로 두었습니다.

**`Escape`를 누르고 `Tab`을 누르면 포커스가 넘어갑니다.** `Escape` 한 번이 이 상태를 열고, 그다음에 무엇이든 입력하면 다시 닫힙니다. CodeMirror와 Monaco, GitHub의 에디터가 모두 쓰는 규칙이라 그대로 맞췄습니다. 그중 하나라도 써 본 사람은 이미 알고 있는 조작이기 때문입니다. 이 사실은 스크린 리더에도 안내합니다.

그려진 문서 쪽은 `Tab`을 잡지 않습니다. 포커스를 받는 요소가 하나뿐이라 `Tab`을 누르면 그대로 빠져나갑니다.

## 되돌리기

`Mod`+`Z`로 뒤로, `Mod`+`Shift`+`Z`로 다시 앞으로 갑니다. 윈도우에서 쓰는 `Ctrl`+`Y`도 같은 명령입니다. 되돌리기 기록은 화면마다 따로 두지 않고 **에디터 전체에 하나**만 둡니다.

원문 화면만 보면 브라우저의 스택을 쓸 수도 있습니다. `<textarea>`의 되돌리기는 잘 동작합니다. 그런데 그려진 문서는 모든 입력을 거절하는 `contenteditable`이라 브라우저 스택에 항목이 하나도 쌓이지 않습니다. 스택을 둘로 두면 `wysiwyg`에서 한 편집을 `plain`에서 되돌릴 때 절반만 되짚다가 멈춥니다.

저장하는 값은 각 변경 *직전*의 문서와 그때 커서가 있던 자리입니다. 되돌리기가 되돌아가야 하는 상태가 그것이기 때문입니다.

한 번에 이어 친 글자는 키 입력마다 나누지 않고 **한 단계**로 묶습니다. 한 글자씩 되돌아가는 `Mod`+`Z`는 쓸모가 없기 때문입니다. 같은 종류의 변경이 같은 자리에서 짧은 간격으로 이어지는 동안은 앞 단계에 묶입니다. 조합 중인 음절도 같은 타이핑으로 셉니다. 한국어 키보드는 자모마다 앞 글자를 다시 쓰는데, 그 하나하나가 따로 떨어진 편집은 아니기 때문입니다. 줄바꿈은 앞의 묶음을 닫습니다. `Enter` 뒤에 친 글자는 새로 시작한 내용이므로, 되돌리기는 그 사이에서 멈춥니다.

::: fw flutter

**이 절은 React 패키지에만 해당하며, 이 패키지는 되돌리기 기록을 따로 두지 않습니다.** React 패키지가 기록을 두는 이유가 여기서는 생기지 않습니다. 그쪽은 편집 화면이 둘이고 그려진 쪽은 브라우저 스택에 아무것도 남기지 않으므로, 한쪽에서 한 편집을 다른 쪽에서 되돌리려면 기록을 하나로 합쳐야 합니다. 여기서 편집할 수 있는 화면은 `EditableText` 하나이고, `EditableText`는 자기 undo 스택을 갖고 있습니다.

그래서 되돌리기는 이 패키지가 아니라 Flutter가 담당하고, 애플리케이션의 다른 텍스트 필드에서와 똑같이 동작합니다. 타이핑하는 사람이 기대하는 동작이 그것입니다. 키 입력이 아니라 툴바 버튼이 만든 변경을 어떻게 다루는지도 Flutter가 정하며, 바깥에서 값을 써 넣은 다른 `TextEditingController`와 같게 동작합니다.

:::

## 붙여넣기

**클립보드에 HTML로 있는 것은 마크다운으로 들어옵니다.** 웹 페이지의 한 부분을 복사해서 어느 화면에든 붙여넣으면 제목은 해시가, 링크는 링크가, 목록은 목록이 됩니다. 워드 프로세서에서 복사해도 마찬가지입니다.

텍스트만 있는 클립보드는 브라우저에 맡깁니다. 브라우저의 붙여넣기가 이미 올바르게 동작하고, 그대로 두면 커서와 스크롤, undo 기록이 그대로 이어집니다.

이것은 렌더러를 거꾸로 돌린 변환이 **아닙니다**. 다른 데서 온 마크업을 한 번 읽어 옮길 수 있는 만큼만 옮기고, 문서가 이 경로를 왕복하지는 않습니다. 그래서 옮기지 못하는 것은 버립니다. `<span style="color: red">`는 그 안의 글자만 남고, `<video>`는 남지 않으며, 목록에 없는 속성은 사라집니다. 모든 URL은 마크다운 링크와 같은 검사를 거치므로, 붙여넣은 `javascript:` 링크는 쓰여 있던 글자 그대로 들어옵니다.

코드 블록 안에서는 붙여넣기가 일반 텍스트로만 동작합니다. 그 안의 내용은 쓰인 글자 그대로이므로, 붙여넣은 제목은 해시로 시작하는 한 줄로 남습니다.

::: fw flutter

이 절은 React 패키지에만 해당합니다. 여기서 클립보드는 플랫폼이 제공하는 내용만 담고 있고, 일반 텍스트를 넘어 HTML 형식이나 이미지를 읽는 일은 위젯이 아니라 플러그인이 맡습니다. 그래서 붙여넣기는 플랫폼의 붙여넣기를 그대로 쓰며, HTML 한 페이지를 마크다운으로 바꾸는 일은 애플리케이션이 문자열을 건네기 전에 하면 됩니다.

:::

## 상태 표시줄

```tsx
<MawyEditor defaultValue={document} status={['position', 'words', 'size']} />
```

`'position'`, `'selection'`, `'lines'`, `'words'`, `'characters'`, `'size'` 중에서 고르고, 아무것도 두지 않으려면 `false`를 넘깁니다.

이 중 둘은 계산 방식을 알아 둘 필요가 있습니다. **글자 수**는 코드 포인트 단위라서 이모지 하나를 한 글자로 셉니다. **단어 수**는 공백으로 나눈 수에 한자·히라가나·가타카나 글자를 각각 더합니다. 이 언어들은 공백 없이 쓰이므로 공백으로만 나누면 한 페이지가 한 단어가 되기 때문입니다. 한국어는 띄어 쓰므로 어절 하나를 한 단어로 셉니다. **크기**는 UTF-8 바이트이고 디스크에 저장될 크기와 같으므로, ASCII가 아닌 글자가 하나라도 들어가면 글자 수와 달라집니다.

## 인터페이스가 쓰는 언어

툴바의 이름표와 툴팁, 화면 전환, 상태 표시줄의 낱말, 찾기 막대, 빈 에디터의 안내문, 스크린 리더에게 주는 모든 문장은 라이브러리가 직접 쓰는 텍스트입니다. 이 텍스트의 언어는 `locale`이 정합니다.

::: fw react

```tsx
<MawyEditor defaultValue={document} locale="ko" />
```

:::

::: fw flutter

```dart
MawyEditor(defaultValue: document, locale: MawyLocale.ko);
```

:::

**영어와 한국어**를 지원하고, 기본값은 `en`입니다. 뷰어가 받는 것과 같은 프롭이며 뜻도 같습니다. 언어를 하나 더할 때 무엇을 해야 하는지를 포함한 나머지 내용은 [인터페이스가 쓰는 언어](./viewer#인터페이스가-쓰는-언어)에 있습니다.

에디터는 이것을 미리보기 안의 뷰어에도 건넵니다. 원문 화면과 그려진 화면이 서로 다른 언어인 일은 없습니다. 그리고 문서에 대해서는 아무 말도 하지 않습니다. 인터페이스가 영어인 에디터에 한국어 문서가 들어 있는 것은 평범한 경우이고, 둘은 일부러 분리된 질문입니다.

## 접근성

편집 화면은 이름표가 붙은 `textbox`이고, 툴바로 할 수 있는 모든 조작은 키보드로도 할 수 있습니다. 툴바는 실제 `toolbar` 역할을 합니다. 탭 정지점은 하나이고, 안에서는 화살표로 움직입니다. `Tab`은 포커스를 옮기지 않고 원문을 들여쓰므로, 빠져나가려면 `Escape`를 누르고 `Tab`을 누릅니다. 이유는 [들여쓰기](#들여쓰기)에 있습니다.
