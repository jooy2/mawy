# 뷰어

뷰어는 마크다운 문서를 그리고, 편집하지는 않습니다.

<MawyDemo name="viewer/basic" flutter="viewer/basic" :height="520" />

::: fw react

```tsx
import { MawyViewer } from 'mawy-react';

export function Page({ document }: { document: string }) {
  return <MawyViewer value={document} />;
}
```

:::

::: fw flutter

```dart
import 'package:mawy/mawy.dart';

MawyViewer(value: document);
```

:::

이것으로 끝입니다. 채워 넣을 테마 객체도, 문서를 그리기 전에 등록할 항목도, 렌더링을 맡길 다른 라이브러리도 없습니다.

## 에디터와 뷰어를 함께 담은 이유

::: fw flutter

이는 두 패키지 사이에서도 성립하며, 검증까지 되어 있습니다. Dart 파서와 TypeScript 파서는 같은 파일, 같은 함수, 같은 규칙으로 되어 있고, `packages/flutter/tool/parity.dart`가 저장소의 모든 마크다운 파일을 둘 다에 통과시켜 트리를 비교합니다. 브라우저에서 한 뜻으로 읽히는 문서는 앱에서도 같은 뜻으로 읽힙니다.

:::

쓰는 도구와 보여주는 도구가 서로 다르면 한 가지 문제가 생깁니다. 작성자가 에디터에서 쓴 문서가 그 화면에서는 멀쩡해 보이는데 독자에게는 다르게 그려지는 것입니다. 목록이 중첩되는 방식, 줄바꿈의 처리, 닫히지 않은 강조의 해석처럼 두 마크다운 구현이 다른 지점이 모두 그 원인이 됩니다.

파서와 렌더러를 공유하면 이런 문제가 생기지 않습니다. 두 화면이 같은 코드 경로를 지나므로, 작성자가 `preview`에서 본 화면이 곧 뷰어가 그리는 화면입니다.

## `value` 없이 쓰기

::: fw flutter

Flutter 패키지에는 이 기능이 없고 `value`가 필수입니다. 파일을 열려면 파일 선택기 플러그인이 필요한데, 이 패키지는 그것을 포함하지 않습니다. 애플리케이션에는 대개 이미 있는 의존성입니다. 파일을 읽는 일은 애플리케이션이 맡고 그리는 일은 Mawy가 맡으며, 이 절 전체는 React 패키지에만 해당합니다.

:::

::: fw react

`value`는 선택 항목입니다. 문서를 넘기지 않으면 뷰어 자체가 **파일 선택기**가 됩니다. `.md` 파일을 끌어다 놓거나, 골라서 열면 됩니다.

<MawyDemo name="viewer/empty" />

어느 쪽이 되는지는 어떤 프롭을 넘겼는지에 따라 정해집니다.

| 넘긴 것        | 뷰어는                        | 파일을 놓으면                             |
| -------------- | ----------------------------- | ----------------------------------------- |
| 없음           | 받은 것을 엽니다              | 그것을 갖고, `onValueChange`를 호출합니다 |
| `defaultValue` | 거기서 시작해 스스로 갖습니다 | 그것을 갖고, `onValueChange`를 호출합니다 |
| `value`        | 넘긴 것만 보여줍니다          | 꺼져 있습니다. `fileDrop`으로 다시 켭니다 |

어느 쪽이든 `onValueChange`는 본문과 그것이 온 `File`을 함께 넘겨줍니다.

```tsx
<MawyViewer
  onValueChange={(markdown, file) => {
    console.log(file?.name, markdown.length);
  }}
/>
```

5 MB가 넘는 파일은 읽지 않고 거절합니다. 마크다운으로 백만 단어쯤 되는 양이며, 데이터베이스 덤프를 끌어다 놓아 탭이 멈추는 상황을 막기 위한 제한입니다.

**문서를 받을 수 없는 뷰어는 파일을 열자고 제안하지 않습니다.** `onValueChange` 없이 `value`만 넘기면 문서는 애플리케이션이 소유하므로, 여기서 파일을 골라도 반영할 곳이 없습니다. 그래서 빈 상태에는 보여줄 문서가 없다는 안내만 두고, 그 아래 버튼은 그리지 않으며, 툴바의 `open`은 비활성으로 둡니다. 동작하지 않는 컨트롤을 그리지 않기 위해서입니다.

:::

::: fw flutter

**마우스 휠 한 칸은 여러 프레임에 걸쳐 반영됩니다.** Flutter는 기본적으로 휠 한 칸을 받으면 다음 프레임에서 스크롤 위치를 그 자리로 옮기고, 그 사이 구간은 그리지 않습니다. 같은 문서를 브라우저에서 볼 때보다 스크롤이 덜 부드럽게 느껴지는 이유입니다. 이 플랫폼에서는 브라우저와 네이티브 애플리케이션 모두 그 사이를 그리므로 여기서도 그렇게 했습니다. 따로 켜거나 설정할 항목은 없고, 플랫폼에 움직임 줄이기를 설정해 둔 사람에게는 다시 즉시 이동합니다. 스타일시트가 `prefers-reduced-motion`에서 하는 것과 같은 처리입니다.

원문 편집 화면은 플랫폼 동작을 그대로 씁니다. 텍스트 필드는 바깥 위젯이 아니라 스스로 스크롤하므로, 그 사이에 끼어들 자리가 없습니다.

**문서의 텍스트는 읽는 사람이 선택하고 복사할 수 있습니다.** 끌면 선택되고, `Ctrl`/`Cmd`+`C`로 복사합니다. 위젯으로 그린 문서는 선택 가능한 영역 안에 넣지 않으면 아무것도 선택되지 않으므로, 이 동작은 따로 구현한 것입니다. 선택 핸들과 컨텍스트 메뉴는 없습니다. 둘 다 Material이나 Cupertino가 제공하는데, 이 패키지는 두 디자인 시스템을 쓰지 않습니다. 그래서 단축키도 `Enter`와 스페이스바처럼 문서에 적어 둡니다.

**블록이 사백 개를 넘는 문서는 보이는 곳만 만듭니다.** 그 아래면 문서가 아무리 길어도 블록을 전부 만듭니다. 선택은 이미 만들어진 글자만 가져갈 수 있으므로, 이 범위에서는 문서 전체를 선택할 수 있습니다. 사백 개를 넘으면 읽는 사람이 스크롤할 때마다 블록이 만들어지고 사라져서, 문서를 그리는 비용과 글꼴이 바뀌어 다시 배치하는 비용, 메모리 사용량이 문서 크기를 따라 커지지 않습니다. 블록 이천사백 개짜리 문서에서 렌더 오브젝트는 이만 오천 개에서 오백 개로, 글꼴을 바꾼 뒤 다시 배치하는 시간은 1초에서 0.1초로 줄었습니다.

사백 개는 긴 README나 레퍼런스 한 쪽, 책의 한 장을 넘어서는 크기입니다. 그 위에서는 목록이 들고 있는 위아래 세 화면까지만 선택할 수 있습니다. 툴바의 복사 버튼은 화면이 아니라 Markdown 원문에서 문서 전체를 가져가므로, 긴 문서를 통째로 복사할 때는 선택을 거치지 않아도 됩니다. 켜고 끌 설정은 없습니다. 블록이 배치될 때마다 그 자리를 기록해 두므로, 아웃라인과 찾기 막대, `anchors`는 화면에 없는 블록에 대해서도 계속 동작합니다.

:::

## 지원하는 문법

CommonMark, 그리고 그 위에 GitHub이 더한 것들입니다.

|  |  |
| --- | --- |
| **블록** | ATX·setext 제목, 문단, 펜스·들여쓰기 코드 블록, 인용, 순서 있는·없는 목록(깊이 제한 없음), 구분선, HTML 블록 |
| **인라인** | 강조, 굵게, `코드`, 링크, 이미지, 자동 링크, 강제 줄바꿈, 문자 참조, 백슬래시 이스케이프 |
| **GitHub** | 열별 정렬이 있는 표, 체크박스 목록, `~~취소선~~`, 맨 URL과 이메일 주소, 각주, 그리고 다섯 종류의 [알림 블록](https://docs.github.com/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts) |
| **참조** | `[label]: url "title"` 정의. 파일 어디에 쓰여 있든 해석합니다 |
| **하나 더** | 정의 목록. GitHub은 읽지 않는 것입니다 |

옵션은 `parse`에 있습니다.

::: fw react

```tsx
<MawyViewer value={document} parse={{ gfm: true, breaks: false, definitionLists: true }} />
```

:::

::: fw flutter

```dart
MawyViewer(
  value: document,
  parse: const MawyParseOptions(gfm: true, breaks: false, definitionLists: true),
);
```

:::

- **`gfm`** (기본값 `true`) — GitHub의 확장. 끄면 `|`는 그냥 세로줄이고 `~~`는 물결 넷입니다.
- **`breaks`** (기본값 `false`) — 문단 안의 줄바꿈 하나를 줄바꿈으로 볼지. CommonMark 명세는 줄바꿈으로 보지 않지만, 채팅 클라이언트와 이슈 트래커는 줄바꿈으로 처리합니다. 마크다운을 써 본 적 없는 독자는 후자를 기대하므로, 한쪽으로 정하지 않고 옵션으로 두었습니다.
- **`definitionLists`** (기본값 `true`) — 글줄 아래의 `: `을 용어와 그 뜻으로 읽을지. 아래를 보세요.

### CommonMark 준수 범위

**명세의 예제 652개 중 640개**를 통과하고, 코드가 바뀔 때마다 그 검사를 돌립니다. CommonMark 명세에는 테스트 모음이 들어 있어서 준수 정도를 숫자로 말할 수 있습니다. 그 숫자는 `packages/react/test/internal/markdown/commonmark.test.ts`에 있고, 통과하지 않는 12개가 무엇인지도 그 옆에 적혀 있습니다.

그중 셋은 구현이 모자란 것이 아니라 의도한 선택입니다. 모든 URL은 스킴 허용 목록을 거치므로 `<made-up-scheme://foo>`는 작성자가 쓴 글자 그대로 그려집니다. 다섯도 같은 종류의 선택입니다. 목적지가 비어 있으면 아무 동작도 하지 않는 `<a href="">` 대신 작성자가 쓴 낱말을 그립니다. 나머지는 목록 항목 안의 탭, 표에 없는 문자 참조, 목록 항목 안에 홀로 있는 참조 정의처럼 드문 경우입니다. 각 항목에 이유를 함께 적어 두었으므로, 이 목록은 의도적으로 줄일 때만 줄어듭니다.

Dart 파서는 이 모음을 돌리지 않아도 됩니다. 까다로운 사례 전부와 저장소의 모든 마크다운 파일에 대해 두 파서의 트리를 diff하므로, 한쪽에서 맞는 트리는 다른 쪽도 그대로 내놓습니다.

**컨테이너는 100단까지 중첩됩니다.** 그 아래로는 아무것도 열리지 않습니다. 줄은 규칙을 적용하지 않은 문단이 되고, 앞에 붙은 표시는 그냥 글자로 남습니다. 컨테이너는 저마다 자기 안쪽을 다시 읽으므로, 중첩 깊이만큼 호출이 쌓입니다. `> `를 2천 번 쓴 4 kB짜리 파일은 내용이 없어도 스택을 넘깁니다. 외부에서 받은 문서를 그리는 애플리케이션에는 누구나 그런 파일을 보낼 수 있습니다. 100단은 손으로 쓴 문서보다 훨씬 깊고, 스택이 감당하는 깊이보다는 얕습니다.

### 각주

문장 속의 `[^label]`은 번호가 되고, 그것이 가리키는 주석은 문서 아래에 그려집니다. 언급된 자리로 돌아가는 링크도 함께 붙습니다.

```md
Mawy는 자기 마크다운을 직접 파싱합니다.[^why]

[^why]: 문서의 한 조각이 어디서 왔는지 알 수 있는 것은 파서뿐이고, 나머지 기능이 모두 여기에 기댑니다.
```

알아 둘 것이 셋 있고, 셋 다 GitHub이 하는 그대로입니다.

- **번호는 처음 언급된 순서**이지 쓰인 순서가 아닙니다. 파일이 어떻게 생겼든 독자는 `1`을 `2`보다 먼저 만납니다.
- **아무도 언급하지 않은 주석은 그리지 않습니다.** 아무도 걸지 않은 `[label]: url`과 마찬가지로, 문서가 아니라 글쓴이에게 남긴 메모로 봅니다.
- **가리킬 것이 없는 `[^label]`은 쓰인 그 글자 그대로** 남습니다. 아무 데도 가지 않는 링크가 되지 않습니다.

주석 하나가 여러 블록일 수도 있습니다. 두 번째 문단이든 목록이든 코드 블록이든, 첫 줄 다음부터 네 칸씩 들여쓰면 됩니다. 파서가 본문 흐름에서 따로 떼어내므로, 문서 한가운데에 쓴 주석도 문서 아래에 그려집니다.

### 정의 목록

GitHub이 읽지 않는 유일한 문법입니다. [PHP Markdown Extra](https://michelf.ca/projects/php-markdown/extra/#def-list)의 문법을 그대로 따랐습니다.

```md
마크다운 : 쓰인 대로 읽히는 글쓰기 방식.

Mawy : 이것. : 그리고 그 옆의 에디터.
```

용어는 한 줄이고, 그 뜻은 콜론 **하나와 공백**으로 시작하는 줄입니다. 공백을 요구하지 않으면 문장 아래에 쓴 `:warning:`이 그 문장을 용어로 만들어 버립니다. 여러 용어가 한 뜻을 함께 가질 수도, 한 용어가 여러 뜻을 가질 수도 있습니다. 첫 줄 이후를 들여쓰면 뜻 하나가 여러 블록이 됩니다. 뜻 앞에 빈 줄을 두면 글머리 기호 목록에서와 똑같이 목록 전체가 성겨집니다.

`parse`에 `definitionLists: false`를 넘기면 꺼집니다. GitHub에서와 정확히 같게 읽혀야 하는 문서를 위한 옵션입니다.

## 코드 블록에 색 입히기

::: fw flutter

기본값은 색을 입히지 않는 것이며, 의도한 기본값입니다. 하이라이터는 마크다운 렌더러가 싣는 코드 중 가장 크고, 대부분의 문서에는 색을 입힐 코드가 없습니다. 그래서 인자로 두었습니다. 하이라이터를 참조하지 않은 애플리케이션은 그 뒤의 문법 표까지 빌드에서 제외됩니다. Dart 빌드가 참조되지 않는 코드를 떨어뜨리기 때문입니다.

```dart
MawyViewer(value: document, highlight: mawyHighlighter);
```

`mawyHighlighter`는 React 패키지의 하이라이터를 Dart로 옮긴 것입니다. `lib/src/highlight.dart`의 규칙이 `src/highlight.ts`와 하나씩 대응하고, `tool/parity.dart`가 양쪽이 지원한다고 밝힌 모든 언어의 조각에 대해 두 쪽의 토큰을 전부 diff합니다. 그래서 브라우저에서 색이 입혀진 코드 블록은 앱에서도 같게 그려집니다. 파서와 같은 방식으로 보장합니다.

지원하는 언어는 문서에 자주 나오는 것들입니다. `js`, `ts`, `jsx`, `tsx`, `json`, `html`, `xml`, `css`, `bash`, `python`, `yaml`, `sql`, `dart`, `go`, `rust`, `java`, `c`, `cpp`, 그리고 각각의 다른 이름들입니다. 결과는 의도적으로 **근사치**로 두었고 앞으로도 그렇습니다. 중괄호가 든 템플릿 리터럴이나 나눗셈처럼 읽히는 정규식은 조금 어긋나게 나오지만, 색은 정확해야 하는 값이 아니라 문제가 되지 않습니다.

그 이상이 필요하면 `MawyHighlighter`가 인터페이스 전부이고, 그 뒤에 어떤 문법을 두든 몇 줄입니다.

```dart
class MyHighlighter extends MawyHighlighter {
  const MyHighlighter();

  @override
  bool supports(String language) => language == 'dart';

  @override
  List<MawyCodeToken> highlight(String code, String language) => tokensFor(code);
}
```

하이라이터는 마크업이 아니라 **토큰**을 돌려주며, 라이브러리의 다른 부분과 같은 원칙입니다. 하이라이터가 돌려주는 값은 글자와 이름뿐입니다. `keyword`, `string`, `comment`를 비롯해 열 몇 가지가 있고, 각각을 무엇으로 그릴지는 이 패키지가 정합니다. 그래서 마크업이 화면에 닿지 않고, 하이라이터가 틀려도 문서에 없던 요소가 들어가지 않습니다.

하이라이터가 지켜야 할 조건은 하나입니다. 토큰을 이어 붙이면 **원래 코드와 같아야** 합니다. 돌아온 토큰을 이어 붙여 들어간 코드와 대조하고, 맞지 않는 블록은 색 없이 그립니다. 문서에 없는 내용을 화면에 보여주는 것보다 색을 포기하는 편이 낫습니다.

색 자체는 `MawyTokens`의 여덟 필드입니다. `highlightComment`, `highlightString`, `highlightNumber`, `highlightKeyword`, `highlightType`, `highlightFunction`, `highlightVariable`, `highlightPunctuation`이며, React 패키지가 `--mawy-hl-*`로 선언하는 여덟 개와 값까지 같습니다.

:::

::: fw react

기본값은 색을 입히지 않는 것이며, 의도한 기본값입니다. 하이라이터는 마크다운 렌더러가 싣는 코드 중 가장 크고, 대부분의 문서에는 색을 입힐 코드가 없습니다. 그래서 프롭으로 두었고, 그 프롭은 **함수**를 받습니다. 펜스에 언어가 적힌 문서를 실제로 그리기 전까지는 불러오지 않기 위해서입니다.

```tsx
<MawyViewer
  value={document}
  highlight={() => import('mawy-react/highlight').then((module) => module.mawyHighlighter)}
/>
```

`mawy-react/highlight`는 별도의 진입점이라, 참조하지 않은 애플리케이션의 번들에는 들어가지 않습니다. 안에는 Mawy가 직접 만든 하이라이터가 들어 있고, 문서에 자주 나오는 언어를 지원합니다. `js`, `ts`, `jsx`, `tsx`, `json`, `html`, `xml`, `css`, `bash`, `python`, `yaml`, `sql`, `dart`, `go`, `rust`, `java`, `c`, `cpp`과 각각의 다른 이름들입니다. 결과는 의도적으로 **근사치**로 두었고 앞으로도 그렇습니다. 중괄호가 든 템플릿 리터럴이나 나눗셈처럼 읽히는 정규식은 조금씩 틀리게 나오지만, 색은 정확해야 하는 값이 아니라 문제가 되지 않습니다.

그 이상이 필요하면 `MawyHighlighter`가 인터페이스 전부이고, 그 뒤에 Shiki나 Prism을 두는 것은 몇 줄입니다.

```tsx
const shiki: MawyHighlighter = {
  supports: (language) => languages.includes(language),
  highlight: async (code, language) => toMawyTokens(await codeToTokens(code, { lang: language }))
};
```

하이라이터는 마크업이 아니라 **토큰**을 돌려주며, 라이브러리 전체가 같은 원칙을 따릅니다. 하이라이터가 돌려주는 값은 텍스트와 이름뿐입니다. `keyword`, `string`, `comment`를 비롯해 열 몇 가지가 있고, 각각을 어떤 엘리먼트로 그릴지는 이 패키지가 정합니다. HTML 문자열이 화면에 닿지 않으므로, 하이라이터가 틀려도 문서에 `<script>`가 들어가지 않습니다. 목록에 없는 이름은 그냥 텍스트로 그립니다.

하이라이터가 지켜야 할 조건은 하나입니다. 토큰을 이어 붙이면 **원래 코드와 같아야** 합니다. 돌아온 토큰을 다시 이어 붙여 들어간 코드와 비교하고, 맞지 않는 블록은 색 없이 그립니다. 문서에 없는 내용을 화면에 보여주는 것보다 색을 포기하는 편이 낫습니다.

색이 입혀진 조각도 뷰어가 그리는 다른 요소처럼 원문 위치를 들고 있습니다. 코드 블록 한가운데를 클릭해도 그 글자의 원문 위치를 찾아냅니다.

색 자체는 여덟 개의 커스텀 프로퍼티입니다. `--mawy-hl-comment`, `--mawy-hl-string`, `--mawy-hl-number`, `--mawy-hl-keyword`, `--mawy-hl-type`, `--mawy-hl-function`, `--mawy-hl-variable`, `--mawy-hl-punctuation`이며, 밝은 팔레트와 어두운 팔레트 양쪽에서 `.mawy-root`에 선언되어 있습니다. 애플리케이션에서 다시 선언하면 그 값이 쓰입니다.

:::

## 디렉티브

뷰어는 마크다운이 표현할 수 있는 것을 그립니다. 그런데 문서에는 마크다운 문법에 없는 요소가 필요할 때가 있습니다. 영상, 수식, 사이트의 모든 페이지가 쓰는 사내 알림 상자 같은 것입니다. 이때 쓸 수 있는 방법이 둘 있는데 둘 다 문제가 있습니다. 하나는 원시 HTML인데, 이 라이브러리의 안전성은 HTML을 쓰지 않는다는 데 기대고 있습니다. 다른 하나는 영상을 아는 라이브러리를 넣는 것인데, 그러면 다음에는 다른 요소도 전부 알아야 합니다.

디렉티브가 세 번째 방법입니다. 파서는 **모양**만 읽고 거기서 멈춥니다. `youtube`가 무엇인지 해석하지 않으므로 문서가 어떤 요소든 담을 수 있고, 그 모양이 무슨 뜻인지는 애플리케이션이 정합니다.

셋이 있고, 콜론의 개수가 그 구분입니다.

```md
:::callout[주의]{kind=warning} 블록이고, 블록으로 파싱됩니다. **강조**, 목록, 코드. :::

::youtube{id=dQw4w9WgXcQ}

가려면 :kbd[Ctrl]을 누르세요.
```

컨테이너는 블록을 담고, 자기 길이 이상의 콜론을 만나면 닫힙니다. 그래서 `::::`가 `:::`를 담을 수 있습니다. 리프는 한 줄이고 그 아래에 아무것도 두지 않습니다. 텍스트 디렉티브는 문장 안에 들어갑니다.

::: fw react

각 이름이 어떤 컴포넌트가 되는지는 프롭 하나입니다.

```tsx
const Callout = ({ attributes, label, children }: MawyDirectiveProps) => (
  <aside className={`callout callout-${attributes.kind ?? 'note'}`}>
    {label ? <h3>{label}</h3> : null}
    {children}
  </aside>
);

<MawyViewer value={document} directives={{ callout: Callout, youtube: YouTube }} />;
```

컴포넌트가 받는 값은 `name`, `attributes`, 이미 그려진 `label`, 컨테이너라면 이미 그려진 `children`, 쓰인 자리인 `range`, 쓰인 글자인 `source`입니다. 그래서 컴포넌트는 React 엘리먼트를 조립할 뿐 마크업 문자열을 다루지 않습니다. 확장 지점이 생겨도 안전성이 그대로인 이유입니다. 마크다운과 화면 사이에 여전히 `innerHTML`이 없고, 위험한 요소를 그리는 디렉티브가 있다면 그것은 애플리케이션이 직접 그린 것입니다.

:::

::: fw flutter

각 이름이 어떤 위젯이 되는지는 인자 하나입니다.

```dart
MawyViewer(
  value: document,
  directives: <String, MawyDirectiveBuilder>{
    'callout': (BuildContext context, MawyDirective directive) => Callout(
      kind: directive.attributes['kind'] ?? 'note',
      title: directive.label,
      children: directive.children!,
    ),
  },
);
```

빌더가 받는 값은 `name`, `attributes`, `InlineSpan`으로 이미 그려진 `label`, 컨테이너라면 위젯으로 이미 그려진 `children`, 쓰인 자리인 `range`, 쓰인 글자인 `source`입니다. 그래서 빌더는 위젯을 조립할 뿐 마크업을 다루지 않습니다. 텍스트 디렉티브는 문장 안에 `WidgetSpan`으로 놓이므로, 그 빌더는 글줄 높이에 맞는 위젯을 돌려주어야 합니다.

:::

<MawyDemo name="viewer/directives" flutter="viewer/directives" :height="460" />

`{…}`는 이 문법을 쓰는 다른 곳과 똑같이 씁니다. `key=value`, `key="공백이 든 값"`, `#id`, `.a .b`를 쓸 수 있고, `#id`와 `.a .b`는 각각 `id`와 `class`로 전달됩니다. 값 없이 `key`만 쓰면 빈 문자열로 전달되며, 플래그를 적는 방법입니다. 모든 값은 문자열입니다. 문서가 넘긴 것이 문자열뿐이기 때문입니다. 그 값을 숫자로 읽을지, 없을 때 어떻게 처리할지는 컴포넌트가 정합니다.

**등록되지 않은 이름은 쓰인 글자 그대로 그립니다.** 기본 `html` 정책에서 원시 HTML을 다루는 방식과 같고, 이유도 같습니다. 뷰어가 해석할 수 없는 요소라면 문서의 일부를 조용히 버리는 대신 작성자가 쓴 글자를 보여주는 편이 낫습니다. 내용을 잃지 않는 유일한 방법이기도 합니다. 처리되지 않은 `::youtube{id=…}` 안에는 대신 보여줄 내용이 없습니다.

::: fw react

`wysiwyg` 화면에서 이 글자들은 원문과 한 글자씩 그대로 대응합니다. 그래서 등록되지 않은 디렉티브도 쓰인 자리에서 그대로 편집됩니다.

:::

이 문법이 온 [`remark-directive`](https://github.com/remarkjs/remark-directive) 확장보다 좁은 규칙이 둘 있습니다. 둘 다 문서가 이미 말한 것을 바꾸지 않기 위한 규칙입니다.

- **콜론 바로 뒤에 이름이 옵니다.** 사이에 공백이 있는 `::: tip`은 그대로 문단으로 남습니다. 이 형태로 컨테이너를 쓰고 있는 기존 문서가 뜻을 그대로 유지하기 위해서입니다.
- **인라인 디렉티브는 레이블이나 속성을 답니다.** `:name` 하나로는 디렉티브가 아니어서, 문장 속의 `Note:`나 `12:30`이나 `:warning:`은 정확히 그것들 그대로 남습니다.

그 밖에 확장이 읽는 문법은 이 파서도 읽습니다. 그래서 한쪽에 맞춰 쓴 문서를 다른 쪽에서도 읽을 수 있습니다.

## 안전

뷰어는 애플리케이션이 직접 쓰지 않은 내용을 그립니다. 그래서 기본값을 안전한 쪽으로 두었습니다.

::: fw react

**문서는 HTML 문자열이 아니라 React 엘리먼트가 됩니다.** 마크다운에서 화면까지 가는 경로에 `innerHTML`이 없습니다. 파싱된 문서의 노드는 렌더러가 `case`로 다루는 엘리먼트만 될 수 있습니다. 이스케이프를 꼼꼼히 하는 방식이 아니라, 이스케이프할 대상이 애초에 생기지 않는 구조입니다.

:::

::: fw flutter

**문서는 문자열을 거치지 않고 위젯이 됩니다.** 마크다운에서 화면까지 가는 경로에 마크업이 없습니다. 파싱된 문서의 노드는 렌더러가 `case`로 다루는 위젯만 될 수 있습니다. 이스케이프를 꼼꼼히 하는 방식이 아니라, 이스케이프할 대상이 애초에 생기지 않는 구조입니다.

:::

::: fw react

**링크는 새 탭에서 열립니다.** `linkTarget`의 기본값이 `'blank'`이고, 그러면 링크에 `target="_blank"`와 `rel="noopener noreferrer"`가 붙습니다. 뷰어는 대개 페이지 전체가 아니라 페이지의 한 부분입니다. 링크를 따라 나갔다 돌아온 사람은 문서를 두고 간 자리에서 다시 시작해야 하고, 에디터라면 그 뒤에 저장하지 않은 글이 남아 있습니다. `linkTarget="self"`는 문서를 페이지 전체로 보여주는 애플리케이션을 위한 값입니다. 각주 번호와 거기서 돌아오는 화살표는 같은 페이지를 가리키므로 어느 쪽에서도 영향을 받지 않습니다.

:::

**모든 URL은 HTML에서와 마찬가지로 마크다운에서도 검사합니다.** `[click](javascript:…)`은 HTML이 하나도 없는 순수 마크다운이므로, 스킴 허용 목록은 HTML 옵션에 속하지 않고 그 옵션과 함께 꺼지지도 않습니다. 거절된 대상은 작성자가 쓴 낱말 그대로, 링크 없이 그립니다. 독자에게는 동작하지 않는 링크 대신 문장이 보입니다.

::: fw flutter

**원시 HTML은 쓰인 글자 그대로 보이고, 바꿀 방법이 없습니다.** Flutter에는 그것을 그릴 HTML 자체가 없습니다. Flutter 패키지에 `html` 프롭이 없는 이유입니다. 이 절의 나머지 내용은 React 패키지에만 해당합니다.

**링크를 대신 열지도 않습니다.** 탭한 링크는 애플리케이션이 `onLinkTap`으로 여는 방법을 정하기 전까지 아무 동작도 하지 않습니다. URL을 플랫폼에 넘길지는 뷰어가 정할 문제가 아닙니다. 스킴 허용 목록은 이미 통과한 뒤이고, 그다음은 애플리케이션이 처리합니다.

:::

::: fw react

**문서 안의 원본 HTML은 요청하기 전까지 아무 일도 하지 않습니다.** 그것을 바꿀 수 있는 프롭은 `html` 하나입니다.

| `html`                | 문서 안의 `<div>`는                                                    |
| --------------------- | ---------------------------------------------------------------------- |
| `'escape'` _(기본값)_ | 쓰인 글자 그대로, 텍스트로 보입니다                                    |
| `'sanitize'`          | 진짜 `<div>`가 됩니다. 허용 목록 밖의 요소·속성·URL 스킴은 제거된 채로 |
| `'raw'`               | 진짜 `<div>`가 됩니다. 쓰인 그대로, **실행되는 것까지 포함해서**       |

`'sanitize'`는 문서가 붙인 이름을 전부 `user-content-` 아래로 옮깁니다. `id`는 페이지의 전역 이름이 됩니다. 어느 브라우저에서든 `<a id="config">`는 `window.config`가 되고, `name`도 `document`에 같은 영향을 주므로 `<img name="getElementById">`는 주위 스크립트에서 그 메서드를 가려 버립니다. 접두사를 붙이면 페이지의 다른 이름과 충돌하지 않습니다. 문서가 자기 이름으로 건 링크는 같이 옮기고, 제목으로 건 링크는 옮기지 않습니다. 제목의 앵커는 마크업이 아니라 작성자가 쓴 낱말이기 때문입니다. GitHub과 같은 방식으로 만들므로 GitHub용으로 쓴 문서가 그대로 동작합니다.

`'sanitize'`는 정규식이 아니라 `DOMParser`로 파싱하며, 이는 의도한 선택입니다. HTML의 오류 복구 과정 자체가 공격면이고, `<img src=x onerror=alert(1)>`을 브라우저와 똑같이 해석하는 파서는 브라우저의 것뿐입니다. `DOMParser`가 없는 서버 렌더링 환경에서는 추측하는 대신 마크업을 텍스트로 보여줍니다.

그래서 브라우저의 첫 페인트도 서버와 같은 결과를 그리고, 요소는 그다음 렌더에 나타납니다. 의도한 동작입니다. 곧바로 그리면 서버가 글자를 보낸 자리에서 React가 요소를 만나 하이드레이션 불일치가 납니다. 서버에서 그리지 않는 애플리케이션은 하이드레이션도 하지 않으므로, 첫 렌더부터 브라우저가 그려서 지연도 깜빡임도 없습니다.

`'raw'`는 아무것도 제거하지 않고 검사하지도 않습니다. 문서 안의 `<script>`가 실행되고, 이미지의 `onerror`가 실행되며, `<iframe>`이 로드됩니다. 전부 그 페이지의 출처에서, 그 페이지의 쿠키와 로그인한 독자가 접근할 수 있는 모든 것을 가지고 실행됩니다. **문서에 글자를 넣을 수 있는 사람은 애플리케이션이 할 수 있는 일을 전부 할 수 있습니다.** 세션을 읽고, 그 독자의 권한으로 API를 호출하고, 페이지를 바꿔 쓸 수 있습니다.

애플리케이션이 직접 쓴 문서이거나, 신뢰하는 도구가 이미 안전하게 만들어 둔 문서에만 켜세요. 이 값을 켠 채 신뢰할 수 없는 마크다운을 그린 경우는 취약점 신고 [범위 밖](https://github.com/jooy2/mawy/blob/main/SECURITY.md)입니다. 이 값의 의미가 문서에 그렇게 정의되어 있기 때문입니다. 외부에서 받은 문서에는 `'sanitize'`를 쓰세요.

:::

## 툴바

툴바는 문서의 내용이 아니라 문서를 어떻게 **조판할지**를 다룹니다. 독자가 글자를 키우거나 줄 간격을 넓히거나 명조로 바꿔도 문서 자체는 그대로입니다.

::: fw react

```tsx
<MawyViewer value={document} toolbar={['fontSize', 'colorScheme']} />
```

:::

::: fw flutter

```dart
MawyViewer(
  value: document,
  toolbar: const <MawyViewerToolbarItem>[
    MawyViewerToolbarItem.fontSize,
    MawyViewerToolbarItem.colorScheme,
  ],
);
```

:::

<MawyDemo name="viewer/minimal" flutter="viewer/minimal" :height="360" />

::: fw react

`toolbar`는 전부를 뜻하는 `true`, 아무것도 없음을 뜻하는 `false`, 또는 그릴 컨트롤과 그릴 순서를 받습니다.

:::

::: fw flutter

`toolbar`는 리스트를 받습니다. 전부는 `kMawyViewerToolbar`, 아무것도 없음은 `const []`, 아니면 그릴 컨트롤과 그릴 순서.

:::

| 항목              | 하는 일                              |
| ----------------- | ------------------------------------ |
| `'fontFamily'`    | 뷰어가 받은 글꼴. [아래](#글꼴) 참고 |
| `'fontSize'`      | 13~26픽셀                            |
| `'lineHeight'`    | 1.3~2.4                              |
| `'letterSpacing'` | −0.04~0.16em                         |
| `'measure'`       | 본문이 뻗을 수 있는 폭               |
| `'colorScheme'`   | 라이트, 다크, 또는 시스템 설정       |
| `'outline'`       | 제목 목록 패널을 엽니다              |
| `'copy'`          | 마크다운 원문을 클립보드로           |
| `'open'`          | 파일 선택기                          |
| `'separator'`     | 가는 구분선. 긴 목록을 묶을 때       |

::: fw flutter

여기서 그것들은 `MawyViewerToolbarItem`의 값입니다. 둘째 줄이라면 `MawyViewerToolbarItem.fontSize`입니다. 목록은 `open` 하나가 빠진 것 말고는 같습니다. 이 패키지는 파일을 열지 않기 때문입니다.

:::

목록에 없는 컨트롤을 추가하는 방법은 없으며, 이는 의도한 제약입니다. 임의의 자식을 받는 툴바는 라이브러리가 키보드 조작을 보장할 수 없습니다.

::: fw react

이 툴바는 버튼을 늘어놓은 줄이 아니라 ARIA `toolbar` 역할을 갖습니다. Tab 한 번으로 들어가고 한 번으로 나오며, 안에서는 화살표 키와 `Home`·`End`로 컨트롤 사이를 옮깁니다. 키보드만 쓰는 독자가 컨트롤 열한 개를 지나지 않고 키 두 번으로 문서에 닿게 하기 위해서입니다.

:::

::: fw flutter

모든 컨트롤은 이름과 눌린 상태를 함께 노출하는 `Semantics` 버튼입니다. 그래서 스크린 리더가 이 줄을 툴바로 읽습니다. React 패키지와 마찬가지로 탭 정지점은 하나이고, 안에서는 화살표로 컨트롤 사이를 옮깁니다. 아래 [접근성](#접근성)을 보세요.

:::

## 글꼴

기본으로 제공하는 값은 셋이며, 특정 글꼴 이름이 아니라 역할입니다. `sans`·`serif`·`mono`를 독자의 기기에 이미 있는 글꼴로 그립니다. 내려받는 파일이 없어서 로딩에 실패할 일도 없습니다.

::: fw flutter

여기서는 그 셋이 전부입니다. `MawyFontFamily`에는 네 번째 값이 없고, 값을 더할 `fonts` 목록도 없습니다. 이 절의 React 쪽에 있는 글꼴 카탈로그와 지연 로딩 스타일시트는 브라우저 환경에만 해당합니다. Flutter 애플리케이션은 싣는 글꼴을 뷰어가 만들어지기 훨씬 전에 `pubspec.yaml`에 적어 두기 때문입니다.

번들한 서체를 쓰려면 이름을 넘기면 되고, 그 인자가 `fontFamilyName`입니다.

```dart
MawyViewer(
  value: document,
  defaultTypography: const MawyTypography(
    fontFamily: MawyFontFamily.serif,
    fontFamilyName: 'Archive',
  ),
);
```

빼면 세 역할이 각각 플랫폼의 기본 서체로 이어지고, 넣으면 이름을 댄 패밀리로 이어집니다. 툴바의 이름표와 선택 상태는 여전히 역할이 정하고, 실제로 그려지는 서체는 `fontFamilyName`이 정합니다.

이 절의 나머지 내용은 React 패키지에만 해당합니다.

:::

::: fw react

웹폰트는 프롭 하나로 켜지며, 기본값으로 두지 않은 것은 의도한 선택입니다. 뷰어는 다른 사람의 페이지 안에 들어가는 컴포넌트인데, 폰트 CDN에 스스로 연결을 여는 컴포넌트는 프라이버시와 오프라인 동작, 그 페이지의 콘텐츠 정책까지 대신 결정하는 셈입니다. 그래서 목록은 라이브러리가 싣고, 사용 여부는 애플리케이션이 정합니다.

```tsx
import { MAWY_SYSTEM_FONTS, MAWY_WEB_FONTS, MawyViewer } from 'mawy-react';

<MawyViewer value={document} fonts={[...MAWY_SYSTEM_FONTS, ...MAWY_WEB_FONTS]} />;
```

`MAWY_WEB_FONTS`의 모든 글꼴은 SIL Open Font License입니다. 상업적 사용과 임베딩, 재배포가 허용되므로 목록에 라이선스를 구매해야 하는 것은 없습니다.

|  |  |
| --- | --- |
| **고딕** | Inter, IBM Plex Sans, [Atkinson Hyperlegible](https://www.brailleinstitute.org/freefont/) |
| **명조** | Source Serif 4, Literata, Lora, EB Garamond |
| **고정폭** | JetBrains Mono |
| **한글** | Pretendard, Noto Sans KR, Noto Serif KR, 나눔명조, 고운돋움 |

한글 글꼴을 목록에 넣은 것은 폴백에 맡기지 않기 위해서입니다. 글꼴 메뉴에 라틴 문자용 서체만 있으면 한글 문서는 아무도 고르지 않은 서체로 조판됩니다.

필요해지기 전에는 아무것도 내려받지 않습니다. 문서가 이미 쓰고 있는 글꼴은 뷰어가 마운트될 때, 나머지는 글꼴 메뉴를 처음 열 때 받습니다. 메뉴의 이름 하나하나를 해당 서체로 그리므로 메뉴를 열 때 받아야 합니다. 메뉴를 한 번도 열지 않는 독자는 아무것도 요청하지 않습니다.

직접 만든 목록도 같은 모양입니다.

```tsx
<MawyViewer
  value={document}
  fonts={[
    { id: 'sans' },
    { id: 'house', label: '사내 서체', stack: "'Sandoll', system-ui, sans-serif" },
    { id: 'archive', label: '아카이브', stack: "'Archive', serif", href: '/fonts/archive.css' }
  ]}
/>
```

`id`는 `typography.fontFamily`에 넣는 값입니다. `stack`의 기본값은 `var(--mawy-font-{id})`이며, 덕분에 내장된 세 역할을 스타일시트에서 계속 관리할 수 있습니다. `href`는 글꼴을 처음 그릴 때 한 번 받아오는 스타일시트입니다. 페이지가 이미 불러오는 글꼴이라면 빼면 됩니다.

:::

## 조판 값 정하기

::: fw react

모든 조판 값은 `--mawy-doc-*` 커스텀 속성으로 화면에 전달됩니다. 그래서 값을 넣는 방법이 둘이고, 결과는 같습니다.

하나는 프롭으로 넘기고 뷰어가 갖고 있게 하는 방법입니다.

```tsx
<MawyViewer
  value={document}
  defaultTypography={{ fontSize: 18, measure: 'wide' }}
  onTypographyChange={(typography) => localStorage.setItem('type', JSON.stringify(typography))}
/>
```

다른 하나는 툴바를 끄고 CSS로 직접 정하는 방법입니다.

```css
.reader .mawy-md {
  --mawy-doc-size: 18px;
  --mawy-doc-line-height: 1.8;
}
```

`typography`에서 빠뜨린 항목은 기본값을 유지합니다. `{ fontSize: 18 }` 하나만 넘겨도 됩니다.

문서의 줄 간격과 자간은 감싸는 컨테이너뿐 아니라 글자를 담은 요소에도 직접 선언합니다. 상속된 값은 그 요소에 선언된 _어떤_ 값에도 밀리기 때문입니다. 이 선언이 없으면 주변 페이지에 `article p { line-height: 28px }` 한 줄만 있어도 줄 간격 컨트롤이 화면에 반영되지 않습니다.

**이미지가 들어갈 자리를 미리 잡아 둘 수 있습니다.** Markdown에는 그림의 너비와 높이를 적을 자리가 없어서, 페이지가 얼마나 비워 둬야 할지 알 수 없습니다. 그래서 이미지가 도착하는 순간 그 아래 내용이 전부 밀립니다. 문서 안에는 이 정보가 없지만, 애플리케이션이 이미지 비율을 알고 있다면 바깥에서 지정할 수 있습니다.

```css
.my-docs {
  --mawy-doc-image-aspect: 16 / 9;
}
```

그림이 도착하기 전에 자리를 잡고, `--mawy-doc-image-fit`이 `contain`이라 비율이 다른 그림은 잘리지 않고 여백을 두고 들어갑니다. 지정하지 않는 것이 기본값이며, 그때는 자리를 미리 잡지 않습니다. 문서 안에 치수를 적는 방법도 있지만, 이 파서가 현재 읽는 문법은 아닙니다.

:::

::: fw flutter

값을 넣는 방법은 인자 하나뿐입니다. `MawyTypography`는 모든 항목에 기본값이 있는 클래스라서, 항목 하나만 지정하면 나머지는 기본값을 유지합니다.

```dart
MawyViewer(
  value: document,
  defaultTypography: const MawyTypography(fontSize: 18, measure: MawyMeasure.wide),
  onTypographyChange: (MawyTypography typography) => save(typography),
);
```

`defaultTypography`는 시작 값을 정하고, 이후 설정은 뷰어가 갖고 있습니다. `typography`를 넘기면 설정을 애플리케이션이 소유합니다. 이때도 툴바는 독자가 고른 값을 `onTypographyChange`로 알리고, 애플리케이션이 새 값을 돌려주기 전까지는 화면이 바뀌지 않습니다. `onTypographyChange`는 어느 쪽이든 호출되므로, 독자의 선택을 저장하는 코드는 양쪽에서 같습니다.

이미 가진 설정에서 하나만 바꾸는 것은 `copyWith`입니다.

```dart
setState(() => _type = _type.copyWith(fontSize: 18));
```

크기는 CSS 픽셀이 아니라 논리 픽셀이고, 폭은 560·704·880입니다. 본문 16픽셀 기준으로 같은 세 단입니다.

:::

## 인터페이스가 쓰는 언어

툴바의 이름표와 메뉴, 패널의 제목, 스크린 리더에게 건네는 모든 문장은 라이브러리가 직접 쓰는 텍스트입니다. 이 텍스트의 언어는 `locale`이 정합니다.

::: fw react

```tsx
<MawyViewer value={document} locale="ko" />
```

:::

::: fw flutter

```dart
MawyViewer(value: document, locale: MawyLocale.ko)
```

:::

**영어와 한국어**를 지원하고, 기본값은 `en`입니다. 문서 자체의 언어와는 무관합니다. 인터페이스가 영어인 뷰어에 한국어 문서를 넣는 것은 흔한 경우이므로, 두 가지를 분리해 두었습니다.

두 패키지가 같은 이름으로 같은 문장을 싣습니다. 브라우저에서 이렇게 읽히는 화면은 앱에서도 똑같이 읽힙니다. 언어를 하나 더하려면 `src/internal/i18n.ts`의 표와 `lib/src/internal/i18n.dart`의 짝을 함께 채워야 하고, 한쪽에만 있는 언어는 지원 언어로 보지 않습니다.

## 테마

::: fw flutter

팔레트는 [`MawyTokens`](../api/#mawytokens)이며, 스타일시트의 커스텀 속성을 Dart 이름으로 옮긴 것입니다. 값까지 그대로여서 `accent`는 `--mawy-accent`에 대응하고 둘 다 `#5b34ea`입니다. 밝은 팔레트와 어두운 팔레트가 `MawyTokens.light`과 `MawyTokens.dark`이고, 뷰어는 전역 설정을 읽지 않고 `colorScheme`에서 둘 중 하나를 고릅니다. 그래서 밝은 화면 안에서 문서 하나만 어둡게 할 수 있습니다.

토큰을 다시 선언하는 인자가 `tokens`입니다. 팔레트가 아니라 밝기를 받는 함수인데, 뷰어가 나머지 인자를 다 받은 다음에야 자기 밝기를 정하기 때문입니다. 밝기는 `colorScheme`에서 정하고, 그 값이 `system`이면 플랫폼을 따릅니다. 플랫폼을 따라가는 문서라면 두 팔레트 모두에 값을 준비해 두어야 합니다. 서른한 개의 색을 다시 쓰지 않고 하나만 바꾸려면 `copyWith`를 씁니다.

```dart
MawyViewer(
  value: document,
  tokens: (Brightness brightness) =>
      MawyTokens.of(brightness).copyWith(accent: const Color(0xFFB8005C)),
);
```

`MawyEditor`도 같은 인자를 받아 미리보기에 넘깁니다. 에디터와 편집 중인 문서가 서로 다른 팔레트로 그려지지 않습니다.

이 export는 문서 옆에 자기 인터페이스를 그리면서 같은 색을 쓰고 싶은 애플리케이션을 위한 것이기도 합니다.

```dart
final MawyTokens tokens = MawyTokens.of(Theme.of(context).brightness);

Container(color: tokens.backgroundSunken, child: /* … */);
```

`MawyRadius`와 `MawyMotion`도 같은 방식입니다. 모서리 반경과, 움직이는 모든 요소가 공유하는 지속 시간 하나와 곡선 하나를 담고 있습니다.

:::

::: fw react

뷰어가 그리는 모든 색은 `.mawy-root`에 선언된 `--mawy-*` 커스텀 속성이고, 하나를 다시 선언하는 것이 테마의 전부입니다.

```css
.mawy-root {
  --mawy-accent: #b8005c;
  --mawy-radius-lg: 4px;
}
```

`:root`가 아니라 `.mawy-root`에 선언한 것은 의도한 선택입니다. 컴포넌트 라이브러리가 문서 루트에 값을 쓸 이유가 없고, `:root`에서 팔레트를 읽으면 밝은 페이지 안에 어두운 문서를 넣을 수 없습니다. 문서 하나를 끼워 넣을 때 자주 필요한 구성입니다.

:::

라이트와 다크 중 어느 팔레트를 쓸지는 `colorScheme`이 정하고, 지정하지 않으면 `system`입니다. `system`은 플랫폼 설정을 따릅니다. 브라우저에서는 `prefers-color-scheme`, 앱에서는 플랫폼 밝기입니다. `light`과 `dark`는 플랫폼 설정을 따르지 않습니다. 그래서 자체 스위치가 있는 애플리케이션이 그 값으로 뷰어를 제어할 수 있고, 어두운 기기를 쓰는 독자에게도 요청한 대로 밝은 문서를 보여줄 수 있습니다.

## 원문 위치 추적

::: fw flutter

범위는 Dart 트리에도 같은 값으로 들어 있습니다. 모든 `MdNode`가 하나씩 갖고 있고 텍스트 노드도 마찬가지입니다. 없는 것은 그 값을 붙일 엘리먼트입니다. DOM이 없으므로 범위는 화면이 아니라 [`parseMarkdown`](../api/#parsemarkdown)에서 읽습니다. 속성을 다루는 이 절의 나머지 내용은 React 패키지에만 해당합니다.

:::

::: fw react

뷰어가 그린 모든 엘리먼트는 `data-mawy-range="start,end"`를 갖습니다. 넘겨받은 마크다운에서 그 조각의 첫 글자 위치와 마지막 글자 다음 위치입니다. 블록과 목록 항목, 표의 행과 셀, 그 안의 인라인 엘리먼트인 강조와 링크, 코드 스팬, 이미지가 모두 하나씩 갖습니다.

코드 블록은 범위를 두 번 답니다. 바깥의 상자는 펜스와 정보 문자열, 들여쓰기까지 통째로 가리키고, 안의 `code` 엘리먼트는 코드만 가리킵니다. 커서가 놓이는 곳은 안쪽이며, 펜스 사이가 비어 있어도 그 자리는 유지됩니다. 그때는 두 위치가 같은 값이 됩니다.

`# Title`, 빈 줄, `## Second` 이렇게 쓰인 문서라면 두 번째 제목은 이렇게 그려집니다.

```html
<h2 id="second" class="mawy-md-heading" data-mawy-range="9,18">Second</h2>
```

범위는 화면의 한 지점에서 그 지점이 그려져 나온 문서의 위치로 돌아가는 유일한 수단입니다. 에디터의 `split`은 이 값을 두 곳에서 읽습니다. 원문 맨 위 줄이 속한 블록으로 미리보기를 스크롤할 때와, 미리보기에서 클릭한 단어로 커서를 옮길 때입니다. 애플리케이션도 문단에 댓글을 달거나 제목 옆에 "이 절 편집" 버튼을 두는 데 같은 값을 쓸 수 있습니다. 오프셋은 넘긴 문자열을 UTF-16 코드 유닛으로 가리키므로, `value.slice(start, end)`가 클릭한 요소의 원문입니다.

범위가 붙지 않는 것은 텍스트 노드 하나뿐입니다. 속성을 담을 자리가 없고, 담을 필요도 없습니다. 텍스트는 양옆의 엘리먼트로 둘러싸여 있어서 그 사이에서 원문을 찾을 수 있습니다. `**bold**`로 그려진 `<strong>` 안에서 `bold`의 위치는 그 여덟 글자 중 한 곳으로 정해집니다.

:::

## 접근성

::: fw react

- 툴바는 탭 정지점이 하나이고 안에서는 화살표로 움직이는 `toolbar`입니다.
- 모든 아이콘 버튼에 이름이 있습니다. "버튼"이라고만 읽히는 것은 없습니다.
- 메뉴는 `Escape`로 닫히고, 열었던 컨트롤로 포커스를 돌려줍니다.
- 목차 항목을 따라가면 스크롤뿐 아니라 포커스도 함께 갑니다. 다음 `Tab`이 패널이 아니라 제목에서 이어집니다.
- 코드 블록의 복사 버튼은 포인터나 포커스가 닿기 전까지 보이지 않지만, 레이아웃에서 빠지지는 않습니다. 레이아웃에서 빠진 버튼은 `Tab`이 지나칩니다.
- 넓은 표와 긴 코드 줄은 각자의 상자 안에서 옆으로 스크롤되고, 각각 탭 정지점입니다. 키보드로도 오른쪽 끝에 닿습니다.
- `Escape`를 누르면 툴팁이 사라지고, 포인터를 움직이면 다시 나옵니다. 툴팁이 사라져도 정보를 잃지 않습니다. 해당 버튼이 같은 이름을 스크린 리더에 이미 전달하고 있습니다.
- 인터페이스는 자기 텍스트의 언어를 밝히고, 문서의 언어는 밝히지 않습니다. 문서의 언어는 저자가 정하는 값이고 이 라이브러리가 알 수 없습니다.
- `prefers-reduced-motion`에서는 애니메이션을 뺍니다.

**이 라이브러리가 직접 쓰는 제목 두 개는 `h2`로 고정되어 있습니다.** 목차 패널의 제목과 빈 상태의 제목입니다. 문서 자신의 제목 단계는 저자가 정하므로, 뷰어를 어디에 두든 `# `는 `h1`입니다. 페이지의 제목 계층에 `h2`가 맞지 않으면 바깥에서 스타일이나 이름을 다시 지정하면 됩니다. 각각 `.mawy-outline-title`과 `.mawy-empty-title`이며, 단계를 받는 prop을 열더라도 문서 자신의 단계는 저자가 둔 그대로 남습니다.

:::

::: fw react

코드가 바뀔 때마다 모든 화면을 [axe](https://github.com/dequelabs/axe-core)로 검사합니다. 문서를 띄운 뷰어와 파일 선택 상태의 뷰어, 에디터의 네 가지 모드, 목차를 연 상태, 메뉴를 연 상태, 찾기와 바꾸기를 연 상태를 각각 두 팔레트 모두에서 검사합니다. 거기서 나온 결과는 위 목록에 반영되어 있습니다. 체크 목록의 체크박스는 옆의 글을 이름으로 쓰고, 팔레트에서 가장 옅은 글자색은 두 배경 모두에서 AA를 넘도록 올렸습니다. 편집 화면은 `article`이 아니라 `div`인데, ARIA가 문서 구획에 `textbox`를 허용하지 않기 때문입니다. 각주에서 본문으로 돌아가는 링크에는 밑줄을 넣었습니다. 그전에는 색으로만 구분되던 링크였습니다.

자동 검사는 최소 기준입니다. 툴바 안의 화살표 이동이나 목차 항목을 따라간 뒤 포커스가 가는 자리처럼 자동 검사가 잡지 못하는 항목은 같은 테스트 모음에서 하나씩 확인합니다.

:::

::: fw flutter

- 모든 컨트롤은 이름이 있는 `Semantics` 버튼이고, 토글 컨트롤은 상태도 함께 노출합니다. 그래서 스크린 리더가 이 줄을 툴바로 읽습니다.
- 툴바는 탭 정지점이 하나이고, 안에서는 화살표로 컨트롤 사이를 움직입니다. `Home`과 `End`는 줄의 양 끝으로 가고, 포커스가 놓인 컨트롤은 `Enter`와 스페이스 바로 누릅니다.
- 메뉴는 포커스를 안에 넣은 채로 열리고, `Escape`로 닫히며, 열었던 버튼으로 포커스를 돌려줍니다. React 패키지와 달리 이렇게 열어야 합니다. 패널을 `Overlay`로 띄우므로 `Tab` 순서상 자기 버튼 근처에 있지 않고, 거기까지 가려면 문서 전체를 지나야 하기 때문입니다.
- 목차의 항목은 저마다 탭 정지점입니다. 툴바처럼 정지점 하나를 두고 화살표로 옮기지 않고, React 패키지의 `<ol>` 안 `<button>`처럼 `Tab` 한 번에 하나씩 이동합니다. 제목 몇 개짜리 목록에 별도의 조작 방법을 두지 않기 위해서입니다.
- 제목·링크·이미지는 문서 안에서 각자의 시맨틱을 갖고, 목차 항목을 따라가면 스크롤과 함께 포커스도 옮겨집니다. 그래서 다음 `Tab`이 패널이 아니라 제목에서 이어집니다. 제목 자체는 탭 정지점이 아닙니다. `skipTraversal`을 쓰며, 웹의 `tabIndex = -1`에 해당합니다. 포커스를 _놓을_ 수는 있지만 `Tab`이 지나가다 멈추지는 않습니다.
- 글자 크기는 플랫폼의 크기 설정을 따릅니다. 크기를 코드에 고정하지 않고 `MawyTypography`를 지나는 논리 픽셀로 다루기 때문입니다.
- 플랫폼의 모션 줄이기 설정이 켜져 있으면 애니메이션을 뺍니다. `MediaQuery.disableAnimationsOf`를 읽으며, 스타일시트가 `prefers-reduced-motion`으로 확인하는 것과 같은 설정입니다. 이 설정을 켜 둔 독자는 두 패키지에서 같은 화면을 받습니다.

:::

## 인쇄

인쇄할 때는 문서만 종이에 올립니다. 툴바와 목차, 상태 표시줄, 찾기 상자는 모두 눌러서 쓰는 컨트롤이라 종이에서는 쓸 수 없습니다. 그래서 인쇄하지 않으며, 각주에서 본문으로 돌아가는 링크도 마찬가지입니다.

::: fw react

나머지 셋은 화면이 아니라 종이에 맞춘 처리입니다. 높이를 지정한 뷰어는 그 안에서 스크롤하는데, 높이가 있는 상자는 한 화면 분량만 인쇄하고 나머지를 잃습니다. 그래서 종이에서는 문서 길이만큼 늘립니다. 팔레트는 독자가 무엇을 골랐든 밝은 바탕에 어두운 글자로 바꿉니다. 어두운 테마를 그대로 인쇄하면 배경 전체가 잉크로 채워지기 때문입니다. 링크의 목적지는 링크 뒤에 적습니다. 종이에서는 "문서를 보세요"만 남으면 어디를 가리키는지 알 수 없기 때문입니다.

에디터에서는 그려진 문서를 인쇄합니다. `split`에서는 원문 창을 빼고, 그려진 문서가 없는 `plain`에서는 원문을 `<textarea>`가 아니라 글자로 인쇄합니다. textarea는 자기 상자 안에 보이는 부분만 종이에 올리고 나머지를 잃기 때문입니다.

따로 켤 설정은 없습니다. 이미 가져다 쓰는 스타일시트의 `@media print`에 들어 있어서, 뷰어가 있는 페이지에서 `Ctrl`+`P`를 누르면 그대로 동작합니다.

:::

::: fw flutter

인쇄는 이 패키지가 아니라 플랫폼이 처리합니다. 앱은 플러그인이나 운영체제의 인쇄 시트를 쓰고, 넘기는 것은 페이지가 아니라 위젯 트리입니다. 이 절은 React 패키지에만 해당합니다.

:::
